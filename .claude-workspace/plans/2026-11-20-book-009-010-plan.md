# Plan: BOOK-009 booking hours + slot form, then BOOK-010 guest limits + stop (POC)

Stage: POC (tree `whatsapp-crm--book-009`, slot 1). Owner go: 2026-11-20 (`/goal` "create a worktree and
implement the feature"). Defaults taken for the open decisions (owner did not override): settings shaped
for a future location record; new hours start empty; notice/window as fixed choices; read-back = terms
acceptance in AI chat; D3 sent summary kept; written Chinese copy; BOOK-010: unverified agent bookings
hold no seats, stops show name + time, same pilot tenant.

## Design decisions (binding for briefs)
- D1 `booking_config.bookingHours` (JSONB, no migration): `{ weekly: {mon..sun: Period[]}, intervalMinutes: 15|30|60,
  noticeHours: 0|1|2|3|6|12|24, aheadDays: 7|14|30|60|90, special: {date, label?, periods: Period[] /*[] = closed*/}[],
  tableMinutes: null|90|120|150|180, terms: {zh_hk, en}, info: {address, phone, mapUrl} }`, `Period = {label?, first: "HH:MM", last: "HH:MM"}`.
  `null` = not configured (AC-5: today's behaviour). One value a future location record can own.
- D2 Pure domain service `booking-hours.ts`: `slotsFor(hours, date, ctx)`, `checkSlot(...)` → field codes
  `closed_day|outside_hours|too_soon|too_far`, `suggestTimes(hours, date, time, ctx, n=3)`, `summarize(hours, maxParty, lang)`.
  `parseBookingSubmission` takes the hours in its rules and adds those codes + `terms_required` (field `acceptTerms`).
  Every channel already calls it (page submit, PAP create, AI propose/change) — that is the single enforcement point.
- D3 Terms acceptance: migration `091_booking_terms_acceptance.sql` adds `terms_accepted_at timestamptz`,
  `terms_text text` to `booking_requests`; set when terms were shown and accepted; shown in the staff day panel / table row.
- D4 BOOK-010 (after BOOK-009 lands on its branch): `bookingHours.limits = {perSlot, perMeal}` in the same JSONB;
  table `booking_stops` (restaurant_id, date, scope day|period|slot, period_label?, time?, stopped_by, stopped_at);
  Postgres function `insert_booking_request_if_room(...)` locks `(restaurant_id, booking_date)` with
  `pg_advisory_xact_lock`, counts pending+confirmed guests, checks stops, inserts or returns `full`; every insert path
  that creates a pending row (page, PAP code step, AI create/confirm change) goes through it.

## Threat delta (R-ids)
- R1 Settings PUT stays admin-only; new fields validated server-side (lengths, https map URL, time grid), text rendered as text.
- R2 `GET /api/poppy/{publicId}/availability` signed out: same publicId gate + rate limiter as POST; `days ≤ 31`; no PII in output.
- R3 BOOK-010 stop/resume API: `getTenantContext()` + role check; restaurant scoped inside the query (BOOK-004 R1); 403 otherwise.
- R4 Terms snapshot is restaurant text, not PII; `purge-booking-pii` unchanged.
- R5 Atomic check runs as SECURITY DEFINER with fixed search_path, REVOKE from anon/authenticated, called by the service role only.
