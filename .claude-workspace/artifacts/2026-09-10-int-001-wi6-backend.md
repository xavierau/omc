## Tests

Process disclosure (asked for explicitly): I did **not** write one giant
frozen suite before any implementation existed. Given the surface (13 new
modules across app/infra), I ran a tight per-module loop — write that
module's test file against code that doesn't exist yet (confirmed red on
`Cannot find module`), implement, green — repeated per module, in
dependency order (repos → emit/payload → deliver → queue/processor →
retry/resume/test-event → sweeper). Every test file was still written
*before* its own module's implementation, and none was weakened after
being written; I'm disclosing the granularity rather than overclaiming a
single big-bang freeze. ~102 new test cases across 13 new files, plus 6
additive extensions to frozen WI-1/WI-5 test files (each: new cases added,
zero existing assertions changed).

Coverage of the dispatch's Tests-first bullets:
- **Job payload contains only ids** — `integration-outbound-queue.test.ts`: JSON-walks the job data, asserts `Object.keys` = `['deliveryId']`.
- **Secret read at attempt time (rotation → new signature)** — `deliver-outbound-webhook.test.ts`: two full attempts with different `readOutboundSecret` results produce different, independently-verifiable signatures.
- **Breaker trips at Nth failure, success resets** — `deliver-outbound-webhook.test.ts`: streak 9→10 trips + alerts; a 2xx after a nonzero streak resets to 0; permanent failures never touch the streak (T-M4).
- **Paused integration enqueues nothing; resume requeues exactly the pending rows once** — `deliver-outbound-webhook.test.ts` (pause path, sender never called) + `resume-outbound.test.ts` (every paused row transitions once, cap enforced, dead-letters beyond cap).
- **Relay/sweeper idempotency (double run → no duplicate jobs)** — `sweep-integration-queues.test.ts`: two ticks over the same still-unenqueued row call `addDeliverJob` with the identical `deliveryId` both times, which is what makes BullMQ's own jobId dedup the actual guarantee (asserted at the `integration-outbound-queue.test.ts` level too, on `addDeliverJob` itself).
- **Dead-letter alert fires once** — `deliver-outbound-webhook.test.ts`: 404 → exactly one `notifyOpsAlert` call with `{eventId, integrationId, httpStatus, errorCode}` only, no body/PII.
- **Fan-out excludes disabled/wrong-event-type integrations** — **not independently re-verified against a real Postgres in WI-6** (see Deferred). Covered instead by: (a) WI-1's own scratch-DB Assertion D (positive case), (b) `emit-integration-event.test.ts` proving the application layer only ever enqueues what the repository layer's `findQueuedUnenqueuedDeliveriesForEvent` returns — i.e. it inherits the trigger's filtering by construction, not by re-testing the trigger's SQL.
- Also covered: 404→dead_lettered in one attempt; 503→transient; 429→`retryAfterSec` carried through to `job.moveToDelayed`; retry twice→`already_retried`, one `addRetryDeliverJob` call; test event only against a saved URL, `ping` payload has no PII (structural `JSON.stringify` PII check); per-host throttle exhaustion→`DelayedError`, sender never called; pruning age+cap logic (2 old + 2-beyond-cap deleted, `keep-4`/`keep-5` example asserted exactly); anomaly alert at >3x baseline with a volume floor.

## Key Decisions

- **`IntegrationEvent.source` and the seam's threading of it are additive,
  not part of the plan's literal `emitIntegrationEvent(...)` signature.**
  The plan's own prose lists that function's params as `{ restaurantId,
  memberId, type, changed, originIntegrationId }` — no `source`. But the
  outbound wire contract (`OutboundSourceWire`, WI-1's own DTO file) has a
  **required**, non-nullable `data.source` field, and migration 071 (WI-1,
  frozen) already provisions an `integration_events.source TEXT` column
  that nothing wrote to. Building the outbound payload correctly was
  impossible without closing this gap. Closed it by: adding `source` to
  the `IntegrationEvent` entity (additive), threading `input.source`
  through the seam's existing (already-present-but-unused-for-this)
  `CreateOrGetMemberInput.source` field, and having
  `build-outbound-payload.ts` fall back to the member's own `member
  .created` event's source when the current event (always true for DB-
  trigger `member.updated` rows) doesn't carry one. **Flagging for
  orchestrator/product sign-off**, same as the plan's own R1/R3/R4/R7.
- **`UNKNOWN_SOURCE_FALLBACK = 'whatsapp'`** — the residual case (a
  `member.updated` for a member with no `member.created` event at all,
  i.e. created before this feature shipped) has no ground truth anywhere
  in the schema. Picked `whatsapp` as this project's dominant historical
  join path rather than inventing a 5th wire value the DTO type doesn't
  allow. Explicitly a judgment call, not a derived fact — flagged for
  product sign-off.
- **`retrying → paused` added to `IntegrationDelivery`'s frozen state
  machine (WI-1).** The Attempt procedure's own step 1 ("mark paused,
  complete without throwing") must run on whatever status a job currently
  holds — for a job BullMQ is retrying after a prior transient failure,
  that's `retrying`, not `queued`, and the original table had no legal
  edge into `paused` from there. Additive only (one array entry); no
  existing transition narrowed; a new case added to the frozen entity
  test, none removed or weakened.
- **`DeliveryResult.retryAfterSec` added to WI-1's port; WI-5's
  `UndiciOutboundSender` now parses a plain-integer `Retry-After` header.**
  WI-1's original `DeliveryResult` had no response-header access at all —
  the plan's own "429 honours Retry-After via moveToDelayed" requirement
  was structurally unimplementable without this. Only the plain-integer
  form is parsed; an HTTP-date `Retry-After` is left unparsed by design
  (avoids a clock-skew-sensitive date parse) and falls back to ordinary
  exponential backoff. 2 new tests added to WI-5's frozen sender suite,
  zero existing assertions touched.
- **Per-host Redis throttle fails OPEN on a Redis error**, not closed — a
  hiccup on the throttle *check itself* shouldn't block every delivery
  when `deliverOutboundWebhook`'s own Postgres/sender calls will surface a
  genuine outage as an ordinary transient failure anyway. This is a
  worker-side background-job throttle, not the T-H5 request-path
  rate-limiter that must fail closed — different risk profile, different
  answer, made deliberately rather than by copying T-H5's rule
  uncritically.
- **The `member.updated` DB-trigger fan-out is proven only by WI-1's own
  scratch-DB Assertion D (positive case), not independently re-verified
  against real Postgres for the exclusion cases (disabled / no PII ack /
  wrong event type / multiple integrations on one restaurant) in WI-6.**
  The local Postgres at 127.0.0.1:54322 turned out to be a **shared**
  instance (other concurrent INT-001 dev agents may be using it right
  now) already at `supabase_migrations.schema_migrations` version 103 — a
  different branch's history entirely (this worktree's own migrations top
  out at 072, matching plan Risk R5). Running this worktree's 001-072
  against that shared database risked schema collisions and disrupting a
  concurrent session; building an isolated scratch DB (WI-1's own
  approach) needs stub `auth`/`storage`/`realtime` schemas for 11
  specific migrations (grep results recorded in
  `integration-event-publisher.test.ts`'s own comment) — a real, separate
  effort WI-1 already spent a session on. Time-boxed out rather than
  silently skipped or naively run against a resource I don't own.
- **Depth-counter rebuild (T-M7) intentionally excluded from
  `sweep-integration-queues.ts`**, despite the plan's WI-6 prose
  paragraph listing it under "the 5-min sweeper." My dispatch's own
  Objective and threat-closure list (T-M2/T-M4/T-M6/T-M8/T-M11/T-H7) don't
  include it, and the plan's own Traceability table assigns T-M7 to
  WI-2/WI-11, not WI-6 — an internal inconsistency in the plan, resolved
  in favour of the more specific, authoritative sources (my dispatch +
  Traceability) over the general prose. Also avoided touching a Redis key
  (`int001:depth:{integrationId}`) WI-3 owns and is concurrently writing
  in this same worktree. **Flagging for the orchestrator**: confirm this
  rebuild is owned by WI-2/WI-3, or file it as a follow-up — it is not
  covered by anything in WI-6.
- **`send-test-event.ts`'s multi-integration ping fan-out is a disclosed,
  not silently accepted, limitation.** Migration 071's fan-out trigger
  (frozen) has no per-integration scoping for `ping` — it fans out to
  every `outbound_enabled` integration on the restaurant, same as
  `member.created`/`member.updated`. A restaurant running two enabled
  integrations sees both receive a ping when the owner tests either one.
  Harmless (no PII in a ping payload) but a real UX surprise; fixing it
  needs a migration change, out of WI-6's boundary.
- **`resume-outbound.ts` reuses `integration_settings.inbound_queue_cap`**
  (an INBOUND setting) as the resume requeue bound, exactly matching the
  plan's own literal wording ("up to inbound_queue_cap") — an odd
  cross-purpose reuse, not something invented here.
- **Beyond-cap paused rows are dead-lettered via a three-hop in-memory
  transition chain** (`paused → queued → delivering → dead_lettered`),
  since `paused` only transitions directly to `queued` in WI-1's state
  machine. Only the FINAL state is persisted (one `saveDelivery` call per
  row), so this is not three extra writes.
- **`marketing`'s consent grade wins over `utility`'s** when both rows
  exist and the wire payload's single `grade` field must pick one — OD-13
  assigns grade uniformly per partner API call so they normally agree;
  marketing is the more consequential permission when they don't. Judgment
  call, flagged rather than asserted as obviously correct.
- **`deliver-outbound-webhook.ts` returns a structured
  `DeliverOutboundWebhookResult` rather than throwing BullMQ-specific
  errors itself** — `integration-outbound-processor.ts` (which owns the
  `Job`/`token` BullMQ needs for `moveToDelayed`) is the only place that
  throws `UnrecoverableError`/`DelayedError`/plain `Error`. Keeps the
  delivery use case testable without mocking BullMQ's `Job` shape at all
  (`deliver-outbound-webhook.test.ts` never touches bullmq).
- **The per-host throttle check does a small duplicate settings read**
  (once in the processor to get the hostname, once again inside
  `deliverOutboundWebhook`) rather than threading pre-loaded settings
  through. Accepted given concurrency is capped at 2-4 and this is not a
  hot path; flagged rather than silently optimised away at the cost of a
  less-clean use-case boundary.
- **T-M2 anomaly detection aggregates client-side over a 7-day Postgres
  read** (no new RPC/migration). Fine at INT-001's expected volumes;
  flagged as a follow-up for a SQL aggregate once real volumes are known,
  same posture as WI-1 and WI-5's own disclosed scale caveats.

## Exact Signatures Handed to WI-7 and WI-8

**WI-7** (routes the three legacy paths through the seam): no code change
needed in the seam call site beyond what WI-7 already planned —
`createOrGetMember(input, deps?)`'s default publisher is now the real
adapter, and it automatically threads `input.source` into the published
`member.created` event. WI-7 just needs to pass the **canonical**
`OutboundSourceWire` value (`'whatsapp' | 'web' | 'csv_import'`, not an
arbitrary legacy string like `'whatsapp_join_keyword'`) as `input.source`
at each of its three call sites to get correct outbound payloads — this is
exactly WI-7's own stated acceptance bullet ("four `member.created` events
with the right `source`").

**WI-8** (dashboard settings/secret/deliveries/retry/resume/test/activity
routes) — three ready-to-wire application services:
```ts
retryDelivery(deliveryId: string): Promise<
  { ok: true } | { ok: false; error: 'not_found' | 'not_dead_lettered' | 'already_retried' }
>
resumeOutbound(integrationId: string): Promise<
  { ok: true; requeued: number; deadLettered: number }
  | { ok: false; error: 'integration_not_found' | 'url_invalid' }
>
sendTestEvent(integrationId: string): Promise<
  { ok: true; deliveryId: string }
  | { ok: false; error: 'integration_not_found' | 'url_not_saved' | 'not_eligible_for_delivery' }
>
```
Map `retryDelivery`'s `already_retried` → `409`; the DTO's documented
error set for retry only names that one case, so `not_found`/
`not_dead_lettered` are WI-8's own routing/404 decision (its route already
does a scoped existence check before calling this, per the projection
pattern elsewhere in the plan). **Not built by WI-6, needed by WI-8**: a
paginated `GET …/deliveries?status=&cursor=` read (`list-integration-
deliveries.ts` per the plan) — `integration-delivery-repository.ts` has
only the specific queries WI-6 itself needed (relay, resume, prune), not
a general cursor-paginated list-by-status. WI-8 will need to add that
query itself.
