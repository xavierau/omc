# INT-001 WI-0 — Pre-existing integration vulns fixed

Implements plan `plans/2026-09-10-int-001-member-creation-api` §WI-0. Closes threat model
items T-C4, T-H1, T-M5 (role gate on existing integration routes), OQ-5.

## Done

- Mass assignment on `PATCH /api/dashboard/pos-integrations/[id]` (T-C4) — closed with a
  hand-rolled per-field allowlist (`webhookSecret` and every other unknown key rejected,
  never silently dropped) plus a second, independent allowlist inside the application
  layer as defense in depth.
- Inbound `webhookSecret` + `credentials` served to the browser on every dashboard GET
  (T-H1) — closed with a `toPublicIntegration()` projection applied on both the list and
  detail routes; `credentials` (POS provider API keys) is excluded from the projection
  too, since T-H1's finding covers both fields on the same mapper.
- Missing role gate on state-changing integration routes (T-M5) — closed with
  `requireTenantAdmin()`, an explicit `role === 'admin'` allowlist (not a denylist),
  applied to PATCH, DELETE, and the new rotate endpoint. GET stays open to `staff` —
  the plan's test spec only requires the gate on PATCH/DELETE/rotate.
- Fetch-then-compare tenant check on GET/PATCH/DELETE (issue #111 anti-pattern, also
  under T-M5's mitigation text) — replaced with a scoped repository query
  (`findPosIntegrationByIdForRestaurant(id, restaurantId)`), so a foreign-tenant id 404s
  from the query itself rather than from an app-layer comparison after the fetch.
- Inbound secret rotation (OQ-5) — new endpoint
  `POST /api/dashboard/pos-integrations/[id]/rotate-inbound-secret`, admin-gated,
  scoped-lookup-gated, mints server-side via the existing `regenerateWebhookSecret()`,
  persists via the repository, logs to console (no migration yet — 069 lands in WI-1
  and adds the `integration_settings_audit` row), returns the new secret once in the
  response body (`{ webhookSecret }`, unwrapped, per the plan's API Contracts section).

## Key Decisions

1. **Projection lives at the route boundary, not inside `getIntegration`/`listIntegrations`.**
   `getIntegration`/`listIntegrations` still return the raw `PosIntegration` entity;
   `toPublicIntegration()` is applied explicitly in each route handler before
   `NextResponse.json`. This was necessary, not just stylistic: the existing
   `configure-pos-integration.test.ts` locks `listIntegrations` to pass through raw
   repository data verbatim (`toEqual(mockData)` against a partial mock object), and
   changing that shape would have broken a test the boundaries forbid weakening. Routes
   are also the literal "route boundary" the threat model's mitigation text names.
2. **`getIntegration`'s signature changed from `(id)` to `(id, restaurantId)`** rather
   than adding a second scoped function, since nothing outside the three dashboard
   routes called the unscoped form (confirmed by grep — the webhook-verify path and
   `process-pos-webhook.ts` call `findPosIntegrationById` from the repository directly,
   never through the application-layer `getIntegration`). No orphan left behind.
3. **`credentials` excluded from the public projection**, not just `webhookSecret`. The
   threat model's T-H1 finding text names both fields on the same `mapRow()` /
   `Object.keys` leak; `credentials` holds POS provider API keys, equally sensitive.
   `credentials` remains PATCHable per the plan's explicit API Contracts allowlist — it's
   write-only from the dashboard's perspective now.
4. **Rotate endpoint response is `{ webhookSecret }` unwrapped**, not `{ data: {...} }`,
   matching the plan's API Contracts section literally (`200 { webhookSecret }`) even
   though other routes in this file use a `{ data }` envelope.
5. **Interpreted the WI-0 test spec's compound PATCH line two ways and tested both**:
   individual disallowed keys (`webhookSecret`, `outboundUrl`, `restaurantId` each alone)
   and a compound body mixing an allowed key (`status`) with a disallowed one — all
   rejected, all leave the row unchanged.
6. **No changes to `mockPosIntegrationRepository()` in `src/test-utils/mocks.ts`** — it's
   unused elsewhere in the codebase (grep confirms only its own definition references
   it), so left as pre-existing dead code rather than extending it for a helper nothing
   calls (Surgical Changes: mention, don't silently expand unrelated dead code).

  fetch/404 → body parse/400 → update) against how you'd want a real attacker's staff

  regardless of whether the target id exists or belongs to another tenant, which avoids
