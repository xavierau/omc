## Key Decisions

**D1 fix is a DB trigger, not an app-level RPC or lazy insert-on-read.** The
brief named "same transaction/RPC or insert-if-absent on read -- pick the
one that cannot race." A trigger IS the same-transaction option taken to
its logical end: it fires inside the exact transaction that inserts the
`pos_integrations` row, so there is no window in which "integration exists"
and "settings row doesn't" can be observed by a concurrent reader -- unlike
an app-level RPC (two round-trips unless hand-wrapped in a transaction) or
lazy-insert-on-read (two concurrent first reads race each other). It also
means EVERY creation path gets the row for free, including ones this WI
didn't touch and any added later; `configure-pos-integration.ts`'s
`createIntegration` needed zero changes. This mirrors the INT-001 outbox
trigger pattern migration 071 already established
(`trg_integration_events_fanout`, `trg_member_updated_outbox`, ...), so it
matches the codebase's own convention rather than introducing a new one.
`ON CONFLICT (integration_id) DO NOTHING` makes both the trigger and the
backfill idempotent.

**D2's regression gate is a static parser, not a runtime import.** The
`response_excerpt`/`last_response_excerpt` drift would have been invisible
to a test that imports the (already-fixed) column constant and checks it
against itself. `parse-schema.ts` extracts the REAL schema by reading the
migration SQL text; `parse-repository-columns.ts` extracts what each
repository file's `.select`/`.insert`/`.update` calls actually reference,
attributed to the correct table via each call's `.from(table)` (needed
because `integration-event-repository.ts`'s `pruneOrphanIntegrationEvents`
legitimately touches BOTH `integration_events` and `integration_deliveries`
in one file). Confirmed against project memory
`principle_result_type_over_nullable_port`/the "unverified fake is
fiction" rule cited in the dispatch: this is exactly that gap closed, for
schema drift rather than a fake-vs-real behavioural gap.

**Two false positives found and fixed in the parser itself while getting D2
red for the right reason** (both caught by first RUNNING the test before
trusting it, not by inspection):
1. `phone_last4`'s migration-070 comment ("Last 4 digits only, for
   support/ops correlation...") contains its OWN comma, which a
   comment-blind top-level-comma splitter mis-parsed as a column
   separator -- fixed by stripping `-- ...` line comments before parsing.
2. `event_id` (`integration-event-repository.ts`) was being checked
   against `integration_events` (which has no such column -- its PK is
   `id`) instead of `integration_deliveries` (which does) -- fixed by the
   per-`.from()`-chunk attribution above, in place of an earlier
   one-file-one-table design.

**Cold-Redis: `.connect()` at construction + a bounded-timeout boot warm-up,
not an async `getInboundRateLimiter()`.** `getFailFastRedisOptions()`'s
`lazyConnect: true` + `enableOfflineQueue: false` (T-H5) combination means
the client only starts its TCP handshake on the FIRST command, and rejects
that very command outright since offline queueing is off -- guaranteed
`queue_unavailable` on request 1 after every restart. Making
`getInboundRateLimiter()` itself `async` would cascade through every
synchronous caller (`checkPreAuthThrottle`, `chargeAuthFailureAndDecide`,
`guardInboundRequest`, `enqueue-member-create.ts`) -- out of scope for a
defect fix. Instead: `.connect()` fires at construction (whenever ANYTHING
first touches the module), and a new `src/instrumentation.ts` (Next.js's
stable `register()` boot hook, Node-runtime-guarded) awaits
`warmInboundRateLimiter(3000)` before the app starts serving, so in the
normal case the handshake is already done by request 1. `enableOfflineQueue:
false`'s fail-closed catch stays the backstop for the remaining window
(e.g. local dev without a full boot sequence, or Redis genuinely down at
boot) -- unchanged behaviour, just a much smaller window.

## Deferred / Tech Debt

- The cold-Redis fix closes the window but doesn't eliminate it entirely:
  a request landing in the few-hundred-ms gap between process start and
  `register()` awaiting readiness could still see `queue_unavailable` once.
  Acceptable per the brief ("so the first signed request... is not
  rejected" -- not "can never be rejected"); the fail-closed catch is
  unchanged as the backstop.
- `warmInboundRateLimiter()` is NOT called from the worker process
  (`scripts/start-worker.ts`) -- the affected code path
  (`checkPreAuthThrottle`/`guardInboundRequest`) only runs in the Next.js
  app's route handlers, not the worker, so this is intentional, not a gap.
- Did not add an `IF NOT EXISTS`/idempotent-trigger-creation guard to
  migration 077 itself (a plain `CREATE TRIGGER`, matching every other
  migration in this repo -- Supabase migrations are assumed to run exactly
  once each via `supabase db push`, never re-applied blind). The scratch-DB
  idempotency test above simulates a re-apply via `DROP TRIGGER IF EXISTS`
  + recreate specifically to prove the BACKFILL half is safe to re-run,
  which is the half the acceptance criteria actually asked about
  ("077 idempotent (running twice = no change)").
- The `event_id` false positive fix (per-`.from()` chunk attribution) makes
  `parse-repository-columns.ts` correct for every file it currently checks,
  but if a future repository interleaves TWO tables inside the SAME
  function without a `row`-builder in between, the row-builder's
  "nearest-following-`.from()`" attribution heuristic could mis-attribute.
  None of the 6 current files do this; flagged for whoever next extends
  `CASES` in `integration-schema-contract.test.ts`.
