## Item 5 — Fake/real rate-limiter gap (WI-4's finding)

**Bug**: `FakeRateLimiter.incrWindow()` wrote its count into a `windows: Map<string,
{count, windowStartMs}>`, completely separate from the `counters: Map<string, number>`
that `get()`/`incr()`/`decr()` read and wrote. `get(key)` after `incrWindow(key, ...)`
on the fake always returned `0`. The real `RedisRateLimiter.incrWindow()` runs a bare
Redis `INCR` against the literal same key `incr`/`decr`/`get` use (confirmed by reading
`redis-rate-limiter.ts`'s `INCR_WINDOW_SCRIPT`), so on the real adapter `get()` correctly
reflects `incrWindow()`'s last-written count. WI-4 designed around this rather than
fixing it (a separate dedicated Redis key for its hourly send cap) — this WI closes the
actual gap so a future caller doesn't have to repeat that workaround.

**Fix**: `incrWindow` now writes its count into the same `counters` map `get`/`incr`/
`decr` already use; a new `windowStarts: Map<string, number>` tracks only each key's
window boundary (not its value), so the fixed-window reset-on-expiry behaviour is
unchanged.

**Red-then-green evidence** (both commands run, output captured):
1. Added two cases to `rate-limiter.contract.ts` (`get() reflects the count written by
   incrWindow() on the same key`; `incrWindow() and incr() on the same key share one
   counter`).
2. `npx vitest run src/infrastructure/rate-limit/__tests__/rate-limiter.test.ts` before
   the fix: **2 failed / 4 passed** (both new cases red on the fake).
3. `INT001_TEST_REDIS_URL=redis://127.0.0.1:6379 npx vitest run
   .../rate-limiter.test.ts` before the fix: **2 failed / 10 passed** — confirms the
   real adapter already passed both new cases; only the fake was wrong.
4. Applied the fix to `fake-rate-limiter.ts` only. `redis-rate-limiter.ts` was **not**
   touched (per the boundary — "Do NOT change redis-rate-limiter.ts behaviour").
5. Re-ran with `INT001_TEST_REDIS_URL` set: **12 passed (12)**, fake and real.
6. Every consumer of `FakeRateLimiter` re-run for regressions: `verify-signature-v2.test.ts`,
   `integration-inbound-guard.test.ts`, `enqueue-member-create.test.ts` — **38 passed**,
   no regressions.
7. Full repo suite: **5138 passed** immediately after this fix (before the docs test
   was added), zero failures.

No existing test was weakened, skipped, or modified — only two new cases added to the

## Load-Test Numbers

**Redis-only mode** (`REDIS_URL=redis://127.0.0.1:6379 npx tsx scripts/load/int001-inbound.ts`),
run and captured verbatim:

```
HMAC sign+hash overhead: 5000 ops in 35.2ms (0.0070ms/op)
Token bucket (rate=60/min, burst=20): 30 requests -> 20 allowed, 10 denied
Trip point assertion: PASS (exactly 20 allowed, 10 denied for a fresh key)
Redis memory for 1000 simulated int001:idem:* entries: 0.30 MB
Overall Redis memory delta this run: 0.32 MB
```

Against the plan's budgets: the 429 trip point fires exactly at the configured burst
(pass); Redis memory for 1k idempotency-shaped entries (0.30 MB) extrapolates to ~3 MB
per 10k, well inside the ≤16 MB/10k budget; signing overhead is negligible (~7 µs/op)
relative to the 60–200 ms route latency budget.

**Full HTTP mode could NOT be run here** — this is a real, named gap, not a skipped
step. What's missing, precisely:
- No `next dev` (or `next start`) server or `npx tsx scripts/start-worker.ts` worker
  was running in this environment (confirmed: `curl` to ports 3000 and 3100 both
  refused the connection).
- The only reachable Postgres/Supabase instance (`127.0.0.1:54322`, PostgREST up at
  `54321`) is a **shared** local dev database on a foreign migration lineage
  (`schema_migrations` tops out at version 103; this worktree's own migrations only go
  to 072) that other concurrent sessions in this multi-agent run may be using —
  inserting a test `pos_integrations`/`integration_settings` row or pointing an app
  server's writes at it risks colliding with a concurrent WI's data, the **exact**
  precedent WI-6's handoff already established for declining to run its own
  trigger-exclusion verification against this same instance.
- Building an isolated scratch DB (WI-1/WI-7's technique) proves migrations correctly
  but does **not** solve this: the Next.js app talks to Postgres through
  `@supabase/supabase-js` (PostgREST + GoTrue), not a raw connection, so a scratch DB
  built by `psql` alone cannot serve a running app — a full local Supabase stack on
  this worktree's own migration lineage would be needed, and `supabase start` is
  independently documented as broken in this repo (`incident_no_browser_env_for_db_features`:
  segfaults on the realtime init image).
- **What unblocks it**: a working `supabase start` (or an isolated Supabase project) on
  this worktree's own migrations, one `pos_integrations` row created through the
  dashboard, `next dev`/`next start` + the worker running, then:
  `INT001_LOAD_TARGET_URL=... INT001_LOAD_INTEGRATION_ID=... INT001_LOAD_WEBHOOK_SECRET=...
  npx tsx scripts/load/int001-inbound.ts` — the script is complete and ready to run
  as-is; nothing in it needs to change.

No number in this artifact was fabricated or extrapolated beyond what a stated
methodology supports.

## Key Decisions

- **Doc file paths follow this dispatch's explicit instructions
  (`docs/integrations/member-api.md`, `docs/integrations/member-api-ops.md`), not the
  plan's own literal WI-11 file list** (`docs/api/partner-member-api.md`,
  `docs/playbooks/integration-queues-ops.md`). A direct, more specific instruction from
  the dispatching orchestrator is treated as authoritative over the plan's earlier
  general text — but this creates a **stale pointer** in the plan's own Integration Map
  (row 26) and Traceability, which still name the old paths. **Flagged for the plan
  owner** to update, since I have no authority to edit the plan.
- **Load-test script filename follows the dispatch's name**
  (`scripts/load/int001-inbound.ts`), not the plan's `scripts/load/int001-load-test.ts`
  — same reasoning and same flagged staleness in the plan's Integration Map row 27.
- **The T-M7 depth-counter-rebuild gap (§7 of the ops playbook) is documented, not
  fixed.** It's a real operational risk WI-6's own handoff already flagged and could
  not resolve ownership for; fixing it would mean editing `enqueue-member-create.ts`/
  `process-member-create-job.ts` or adding a new sweeper task, all outside this WI's
  file list and boundaries ("no route/queue/domain changes beyond the fake fix"). The
  ops playbook gives a safe manual-recovery SQL+Redis recipe instead.
- **The partner doc corrects one aspect of the spec's `503` shape**: §8.1 of the spec
  states `Retry-After` for both `queue_depth_exceeded` and `queue_unavailable`, but
  `members/route.ts`'s actual code (`const headers = result.error ===
  'queue_depth_exceeded' ? { 'Retry-After': '5' } : undefined`) only sets it for
  `queue_depth_exceeded`. Documented what the code does, not what the spec's prose
  says — a partner integrating against the doc will not be surprised by a missing
  header. Flagging the spec/code divergence rather than silently reconciling it.
- **`origin_integration_id` echo-suppression is documented honestly as partial**, not
  as fully working. Verified in code (`build-outbound-payload.ts`,
  `create-or-get-member.ts`, `emit-integration-event.ts`) that only `member.created`
  (via the seam) ever sets a non-null `origin_integration_id`; every `member.updated`
  event is produced by DB triggers with no attribution, so it is always `null` today.
  The partner doc says this explicitly rather than implying update-echo-suppression
  works.
- **The outbound consent enum table's `grade` values were corrected mid-draft** after
  checking `build-outbound-payload.ts`: I initially wrote that `medium`/`null` don't
  arise from this API, then found `grade-consent-batch.ts` proves `medium` is a real
  value other write paths (CSV-import batch grading) produce, and the outbound payload
  reads whichever grade is on the member's **current** consent record regardless of
  which channel wrote it most recently — corrected before finalizing.
- **The docs-freshness test (`integration-member-api-docs.test.ts`) checks doc-contains-DTO-name,
  not prose correctness.** It cannot catch a doc that names a real field but describes
  its behaviour wrongly — only field/literal existence drift. Complementary, not a
  substitute for a human re-reading the doc against a future DTO change.
