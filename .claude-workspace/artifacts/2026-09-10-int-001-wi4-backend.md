## Key Decisions

- **The hourly send cap uses a DEDICATED Redis key (`int001:welcome:sent:{restaurantId}:{yyyymmddhh}`), separate from WI-3's create-time enqueue-gate key (`int001:welcome:{restaurantId}:{yyyymmddhh}`).** This is a deliberate deviation from a literal reading of "re-check the hourly cap" as "read/increment the same counter," for two independent reasons found while implementing:
  1. **Sharing the counter is unsafe in both directions.** `incrWindow`-ing it again at send time would silently halve the real budget (one unit consumed at enqueue, a second at send, for the same welcome). Reading it via `RateLimiterPort.get()` instead is *also* wrong: WI-3's counter increments on every CREATE attempt in the hour, allowed or not, so during any backfill exceeding the cap, `get()` would show a count far above the limit by the time the FIRST (legitimately allowed) jobs are processed — incorrectly zero-ing out every send, not "≤cap sends" as the plan's own acceptance bullet requires.
  2. **`FakeRateLimiter` (WI-1) and `RedisRateLimiter` (WI-2) disagree on this exact question.** The real adapter's `incrWindow`/`get` share one Redis key via native `INCR`/`GET`, so `get()` after `incrWindow()` on the same key is consistent in production. The fake stores `incrWindow`'s state in a separate in-memory map from the one `get()`/`incr()`/`decr()` read — `get()` would always return 0 for a key only `incrWindow` had touched. The port's own contract suite (`rate-limiter.contract.ts`) never exercises this cross-method case, so it isn't a documented guarantee I could safely build on. I did not touch the fake or the contract suite (out of my boundaries, and the safer fix here is architectural, not a fake bugfix) — I built a design that never needs `get()` to mirror `incrWindow()`'s window state at all.
  3. Net effect: WI-3's create-time gate is what actually bounds how many `welcome-send` jobs get enqueued in a given hour (already frozen, already tested). WI-4's own dedicated counter is a genuine second line of defense (protects the actual SEND against a race where an already-enqueued job is processed after the tenant's budget has since been exhausted by other concurrent creates), not a redundant re-derivation of WI-3's check. **Flagged for review** — this is the single largest design decision in this work item not literally specified by the plan text.
- **`decideWelcome` (WI-3's frozen pure function) is reused verbatim with fresh send-time inputs**, rather than re-implementing the evaluation order. `memberOutcome` is hardcoded `'created'` and `sendWelcomeRequested` hardcoded `true` (both already true by construction — this job only exists for members that were created with a welcome queued). This guarantees the send-time skip reason codes and the `skipped_consent_level` detail shape are byte-identical to the create-time ones the delivery log/member timeline already expect.
- **Integration inactive since create-time collapses into `skipped_off`** (by passing `newJoinTemplateId: null` into `decideWelcome` when the integration is missing/paused) rather than inventing a new reason code. The plan's own "Welcome-send job" architecture paragraph doesn't list "integration still active" as one of its re-run bullets (only the dispatch brief did) — I included the check anyway as cheap, obviously-correct defense-in-depth (a partner pausing their integration between create and send should not still receive a welcome on their behalf), reusing an existing bucket rather than adding a new one nothing else expects.
- **`skipped_member_missing` is a new reason code**, outside `decideWelcome`'s own `WelcomeDecision` union (which only models `'active'|'unsubscribed'`, not "row gone"). A genuinely deleted member between create and send has no phone to send to; retrying cannot fix it. Not in any frozen test list — a defensive completeness addition, disclosed.
- **`welcome_outcome` gets a `'sent'` value on success**, distinct from `'queued'` (create-time) and `'failed'` (exhausted retries). The spec's own US-4 text names only `queued | skipped_<reason>` as the outcome vocabulary, but the plan's OWN prose for THIS job explicitly introduces `'failed'` as a new terminal value beyond that pair ("exhausted → `welcome_outcome = failed`") — `'sent'` is the natural symmetric complement I judged more useful for the dashboard/member-timeline than leaving a successfully-delivered welcome's outcome frozen at `'queued'` forever. `welcome_detail.whatsapp_message_id` (WI-3's own flagged discriminator, since `whatsapp_messages` has no `source` column) is populated alongside it. **Flagged for review** — genuinely ambiguous between the spec's literal 2-value list and the plan's own precedent of adding job-specific values.
- **`createCampaignCoupon`'s own error-message-based retry loop cannot distinguish a code collision from a `(campaign_id, member_id)` collision** (both match `.includes('unique')` and it retries with a fresh code regardless — which cannot recover the latter, since campaign+member doesn't change across retries). Rather than modifying that shared, pre-existing, already-tested function (used by `onboard-new-member.ts` and `register-member-web.ts`, both out of my boundaries), `mint-welcome-coupon-idempotent.ts` checks-first via `findCouponByMemberAndCampaign`/`findWelcomeCouponByMember` before ever calling it, so the normal retry path never reaches `createCampaignCoupon`/`createWelcomeCoupon` at all. The catch-and-re-select fallback is belt-and-braces for a genuine concurrent race, not the primary mechanism.
- **Send failures are uniformly transient** (plain thrown `Error`, retried up to the job's configured 3 attempts via BullMQ), per the plan's own explicit text ("Send failure → transient"), rather than adopting `email-job-processor.ts`'s permanent/transient HTTP-status split. This job has no permanent-failure bucket to populate at all (every business-outcome branch is a `skipped_*` that completes WITHOUT throwing, not a job failure) — the dispatch's "permanent vs transient split per `email-job-processor.ts`" instruction is honored in SHAPE (unexpected DB/Redis errors during gate-checking naturally propagate as plain, transient errors too) even though there's no `UnrecoverableError` branch anywhere in this file.
- **`paramValues` for the template send mirrors `execute-campaign-send.ts`'s `sendViaTemplate` pattern** (`customer_name`, `code`, `discount`) rather than `onboard-new-member.ts`'s free-text-rendering `renderTemplate` vars — the latter is for the web-join fallback's own message BODY text, not an approved WhatsApp Business template send via `sendWhatsAppTemplateMessage`, which is what US-4/D2's "never a free-form text send on this path" boundary requires. `formatDiscount(null)` returns `''` for the campaign-less (direct template id) case, which `extractParameters`/`paramValues[name] ?? ''` already tolerates for any template that doesn't declare a `{{discount}}` variable.
