## Dependency Verdict — `undici@8.10.2`

**APPROVED, no conditions**, via the `supply-chain-guard` skill:
- MIT license, official `nodejs/undici` GitHub repo, published via a GitHub
  Actions **trusted OIDC publisher** (npm provenance) — strong supply-chain
  signal, not a personal-account publish.
- No `preinstall`/`install`/`postinstall` lifecycle script in the published
  package (only dev/test/build `scripts`, which never run for a registry
  dependency; its `prepare` script only fires on a git-remote install, which
  this is not).
- Not deprecated.
- `npm audit --json` before vs. after: 25 vulnerable packages both times,
  0 involving `undici` — matches WI-1's own stated 25-pre-existing baseline
  exactly, confirms zero new findings.
- Cross-checked against the local `known-advisories.json` — 0 hits for
  `undici`.
- **Considered and rejected**: Node's built-in global `fetch` (undici under
  the hood, but the `Agent`/custom-`connect.lookup` surface the resolve-and-
  pin design needs is only reachable by importing the `undici` package
  directly — there is no `node:undici` built-in module on this Node version
  (`v22.21.1`; confirmed by attempting the import, `ERR_UNKNOWN_BUILTIN_MODULE`).
- **Version choice**: latest (8.10.2) over the also-current 7.x line, since
  this is explicitly SSRF-hardening code where being on the current secure
  release outweighs the wider Node-version compatibility of 7.x. Undici
  8.10.2 declares `engines: {node: ">=22.19.0"}`; the repo has no `.nvmrc`,
  `.node-version`, or `package.json` `engines` field pinning a Node version
  and no `.npmrc` `engine-strict`, so this is not a hard install failure
  anywhere, but **flag to the user**: confirm prod's actual Node version is
  ≥22.19.0 before this ships (dev here is 22.21.1). If prod is older,
  downgrading to `undici@7.29.1` (`engines: >=20.18.1`) is a one-line pin
  change with no code changes needed on my side (I coded to the stable
  `request`/`Agent`/`connect.lookup` surface, unchanged across 7.x→8.x).

## Key Decisions

- **Undici's connector `lookup` must handle the `{all: true}` shape, not
  just `(address, family)`.** Node's Happy-Eyeballs connector calls a custom
  `lookup` with `options.all = true` and expects `callback(null,
  [{address, family}])`, not the single-address 2-arg form — my first
  implementation only handled the single-address form and every real
  connection failed with `ERR_INVALID_IP_ADDRESS: Invalid IP address:
  undefined`. Found via a standalone repro script against the installed
  `undici` before wiring it into the project; fixed by branching on
  `options.all`. This is exactly the kind of "resolve-and-pin" detail that's
  easy to get subtly wrong (the closure returns the right value in the
  common case, wrong in the Happy-Eyeballs case) — flagging for review since
  it's load-bearing for T-C3's actual protection, not just a test nicety.
- **Test cert/key committed as TS string constants, not `.pem` files.** The
  repo's `.gitignore` has a blanket `*.pem` exclusion (line 30, presumably
  to stop a real TLS private key from ever landing in git). I generated the
  fixture as `.pem` files first, then discovered `git status` silently
  dropped them — would have shipped a test suite that fails for anyone
  cloning fresh. Moved the (harmless, throwaway, loopback-only) cert/key
  into `src/test-utils/loopback-tls-fixture.ts` as plain string exports
  instead of touching `.gitignore`, which felt like the more surgical fix
  (zero risk of loosening the exclusion for a real cert elsewhere) versus a
  scoped negation pattern.
- **`assertSafeUrl` takes an `allowedPorts` override, defaulting to `{443}`
  only.** The threat model's "port 443 only" rule is absolute in production,
  but the loopback contract-suite lane needs an ephemeral test port (443
  needs root, collides across parallel runs). Rather than weaken the
  production check, added a narrow injectable override that
  `createLoopbackTestGuard({allowedPort})` sets to exactly the one ephemeral
  port of that one test server — proven scoped by its own test ("an
  unrelated allowedPorts override for a different port still rejects").
- **`OutboundWebhookSender.send()` self-contains the entire guard pipeline**,
  rather than expecting the caller (WI-6) to call `resolveAndPin` separately
  and pass a pinned IP in. Re-reading the port's own doc comment
  (`pinnedIp?: string // Set only by the real adapter's DNS-pin step
  (WI-5)`) confirmed this was WI-1's intended shape: the adapter resolves
  internally and *records* the pin onto the caller's request object for
  observability/testing, it doesn't *receive* one. This keeps "the only code
  allowed to fetch a user URL" (T-C3's phrasing) literally true of one
  function.
- **No new production "signer" file.** The plan's WI-5 file list is exactly
  three files (`ssrf-guard.ts`, `outbound-webhook-sender.ts`,
  `validate-outbound-url.ts`); WI-1 already built the pure crypto
  (`signHmacSha256Hex`, `parseOutboundSignatureHeader`) and building the
  full signed envelope needs the decrypted current secret, which is
  explicitly WI-6's job (attempt-time, DB-backed). I satisfied "T-L3
  (outbound header format)" as an end-to-end **verification** (test #11
  above) that the wire format WI-6 will produce is correct and
  round-trippable, using WI-1's existing primitives — not by adding new
  production surface WI-6 didn't ask for.
- **User-Agent is hardcoded by the sender and cannot be overridden by the
  caller**; every other header (`Content-Type`, `X-OMC-*`) passes through
  verbatim from `req.headers`. Treated the fixed transport identity string
  as the sender's own concern (same pattern a real HTTP client library
  would follow) and left the signed/business envelope entirely to WI-6,
  which has visibility into the secret, event id, and attempt count that I
  don't.
- **Bounded response read caps at 64 KiB** (well above the 512-char excerpt
  actually kept) rather than reading to completion — an oversized or
  streamed-forever response body is destroyed once the cap is hit rather
  than drained, so a malicious/misconfigured partner endpoint can't hold a
  worker socket open indefinitely via body size. This wasn't explicitly
  itemized in the plan's WI-5 bullet list but was named directly in my
  dispatch ("bounded timeout and response size") and is a natural extension
  of the same SSRF-adjacent DoS concern T-C3 is about.
- **DNS resolution failures classify as `dns_error` (transient)**; resolving
  successfully to a blocked address classifies as `ssrf_rejected`
  (permanent). These are semantically different failures — a name that
  temporarily won't resolve might work on retry, a name that resolves to
  `169.254.169.254` never should — and `delivery-outcome.ts`'s existing
  `PERMANENT_ERROR_TITLES`/`TRANSIENT_ERROR_TITLES` sets (WI-1) already
  anticipated exactly this split.
- **A fresh, unpooled undici `Agent` per delivery attempt**, never a shared
  pooled dispatcher. The plan's own prose ("dispatch with an undici Agent
  whose connect.lookup returns the pinned IP") reads as one Agent per
  attempt; more importantly, the pin is only valid for that one attempt, so
  reusing a pooled connection across attempts with different pins would be
  actively wrong. Given WI-6's low concurrency (2–4) and the 150 ms p95
  non-partner-response budget, a fresh TCP+TLS handshake per attempt is
  comfortably inside budget.

## Deferred / Tech Debt

- WI-6 (`deliverOutboundWebhook`) still needs to: fetch the integration's
  decrypted current secret, build the signed envelope headers (`X-OMC-
  Signature`, `X-OMC-Event-Id`, `X-OMC-Delivery-Attempt`, `X-OMC-Event-Type`,
  `Content-Type`) and pass them via `req.headers`, call `validateOutboundUrl`
  or `UndiciOutboundSender.send()` directly (both are ready), and drive
  retry/breaker/dead-letter off `classifyDeliveryOutcome`'s existing output.
- No raw-socket-level proof that a REAL DNS rebinding attack (a live
  authoritative DNS server that actually answers differently on two real
  lookups a few hundred ms apart) is defeated end-to-end — the acceptance
  suite proves the mechanism (pin-once, never re-resolve) is correct via
  dependency injection, which is the same class of test WI-1 used for its
  own concurrent-double-create proof, but it isn't a live-network
  integration test. Flagged as a gap, not silently accepted as covered.
- `assertSafeUrl`'s name blocklist is a fixed literal list
  (`localhost`, `metadata.google.internal`, `*.internal`, `*.local`,
  `*.localhost`) per the threat model's exact text; it does not attempt to
  catch every possible cloud-metadata-alias hostname a future provider might
  introduce (e.g. AWS's `169.254.169.254` IP is caught by the IP blocklist
  regardless of what name resolves to it, so this is defense-in-depth on
  top of the IP check, not the primary control).
- `undici@8.10.2`'s `engines: {node: ">=22.19.0"}` vs. prod's actual Node
  version is unverified — see Dependency Verdict above; flagging for the
  user/deploy-precondition check rather than guessing.
