## Key Decisions

- **`member-create-repository.ts` (WI-1's file) was missing `status:'active'`
  and `loyalty_token`.** Every OTHER member-insert path in the app
  (`register-member.ts`, `register-member-web.ts`,
  `import-members-with-consent.ts`, `import-contacts-batch-row-member.ts`)
  stamps both at insert — `loyalty-token.ts`'s own header states "Every NEW
  member gets one at insert so there is always a scannable persistent QR."
  Without this fix, every partner-API-created member would silently have no
  loyalty QR, and my own frozen parity test would have caught this as a
  real divergence, not a false negative. Fixed with a 2-line, additive
  change; existing `member-create-repository.test.ts` assertions
  (`toMatchObject`) were unaffected, and I added one new test case for it.
- **Parity test scope** (frozen suite item: "API path and `registerMemberWeb`
  produce identical `members` rows for the same inputs, excluding
  id/timestamps"). `registerMemberWeb(rawPhone, name, restaurantId)` has no
  `language` parameter at all — it never sets `preferred_language`. I
  compared the two paths on every field BOTH literally accept
  (`restaurant_id`, `name`, `status`, and `loyalty_token` by *shape*, not
  value, since it's random by design) rather than a byte-for-byte diff of
  the full insert payload, which would be meaningless given the two
  functions' different input surfaces. `preferred_language` is exercised
  separately (validator tests, job-processor tests). Flagged as a judgment
  call, not a literal reading.
- **The 202 response's `status` field on a post-completion resubmission
  (T-H3b).** The wire DTO (`CreateMemberAcceptedResponse.status`) only
  types `'queued'|'processing'` — it has no slot for a resubmission of a
  job that already `succeeded`/`failed`. I map both terminal statuses to
  `'processing'` on the `202` (closest non-terminal signal; the real
  outcome is one `GET .../jobs/{jobId}` poll away, which the partner
  already has via `poll_url`). Not explicitly specified in the plan/spec —
  flagged for review; a one-line change (`toWireStatus` in
  `enqueue-member-create.ts`) if the owner wants different behaviour.
- **Idempotency is two-layered, not one.** Redis `incrWindow('int001:idem:{jobId}', 1, 86400)`
  is a fast-path cache (T-H3b as literally described); Postgres's
  `job_id` PRIMARY KEY (`insertMemberJob`'s conflict-and-reselect, mirroring
  `member-create-repository.ts`'s own T-H6 pattern) is the actual
  correctness backstop for a race the Redis check can miss (e.g. two
  requests arriving inside the same millisecond, or a prior attempt that
  never got past the depth-cap reservation). On a Postgres conflict, the
  loser releases its speculative per-integration depth reservation and
  does **not** call `q.add` again (BullMQ's own jobId dedup would make a
  second call a safe no-op, but skipping it avoids a redundant call burst
  under a race).
- **"Redis down → 503, zero DB writes" holds by construction**, not by
  convention: every Redis call in `enqueueMemberCreate` happens strictly
  before the one Postgres write (`insertMemberJob`), and every Redis
  failure path returns before reaching it — verified directly by a test
  (`enqueue-member-create.test.ts`, "Redis unavailable at the very first
  check").
- **`decideWelcome`'s evaluation order deviates from the plan's literal
  prose ordering.** The plan lists "member unsubscribed or category latest
  `opted_out` → `skipped_opted_out`" BEFORE "resolved template missing →
  `skipped_no_template`" — but you cannot know a template's CATEGORY (and
  therefore cannot check that category's consent status) before the
  template itself has been resolved. I implemented the dependency-respecting
  order: existing → by_request → off → member-unsubscribed (no template
  needed) → resolve template → category-opted-out → consent-level →
  quality-paused → rate-capped. Documented in the file's own header;
  table-driven tests cover every branch and the stated precedence.
- **Welcome-template resolution is implemented INLINE in
  `process-member-create-job.ts`, not as the plan's named
  `resolve-integration-welcome-template.ts` file.** That file is explicitly
  in **WI-4's** Files (new) list, not mine — but `decideWelcome`'s
  `skipped_no_template`/`skipped_consent_level` branches genuinely need a
  resolved template at CREATE time (the architecture section's
  "Member-create job (worker)" step 6 is explicit about this, and is
  contextually my file). I implemented the exact resolution rule WI-4's own
  file description states (`'default'` → onboarding `welcomeCampaignId` →
  campaign `whatsappTemplateId` → `findByIdForRestaurant`; uuid →
  `findByIdForRestaurant` directly) as a private helper, not a new exported
  file, so WI-4 is free to extract/replace it into its own dedicated file
  per the plan without a naming collision. **WI-4 must NOT assume my
  create-time resolution still holds at send time** — its own
  `process-welcome-send-job.ts` must re-run the identical resolution (T-M11:
  a rename between create and send must be re-evaluated fresh), which is
  exactly what the plan already specifies independent of my choice here.
- **The hourly welcome cap is checked via a single `RateLimiterPort.incrWindow`
  call, gated behind a PROVISIONAL `decideWelcome()` call with
  `hourlyCapExceeded:false`.** This avoids consuming (and TTL-refreshing) the
  per-tenant-per-hour Redis counter for requests that were always going to
  skip for an earlier reason (no template, insufficient consent,
  quality-paused) — the counter is only touched once every earlier gate has
  already passed, exactly mirroring the per-integration depth-cap's
  reserve-then-commit pattern used in `enqueue-member-create.ts`.
- **OD-13 grade determination**: `consent_attestation_text` present AND
  `consent_attestation_ack_at` present on `integration_settings` → grade
  `strong`, `consent_text` copied from the attestation; either absent →
  grade `weak`, `consent_text` null. Matches the threat model's §11
  recommended resolution exactly.
- **`inbound-auth-response.ts` is one file beyond the plan's literal WI-3
  file list** — a small, justified DRY factoring (see Files Changed table).
  Not a redesign of anything; `verify-signature-v2.ts` itself explicitly
  says building the `NextResponse` "stays with the route, WI-3" — this file
  is exactly that, shared between my two routes instead of duplicated.
- **`getInboundRateLimiter()` and `getGlobalCeilingGuard()` singletons live
  in `integration-inbound-queue.ts`** (my file), not a new top-level
  redis-client file — avoids touching WI-2's `redis-rate-limiter.ts` and
  keeps the singleton's lifecycle tied to the queue module that already
  owns a Redis connection. Documented in that file's own header.
