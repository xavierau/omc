# CAMP-016 — Campaign audience quality + lapsed filters as tenant settings, Settings regroup (POC plan)

Learn-question: do restaurant owners keep "skip low-quality contacts" on and use the lapsed filter on tag campaigns, and does the regrouped Settings page stop feeling long? Owner (Xavier) sees it on the branch preview, then tenants in prod.

## Tasks (one `dev` work item)
1. Migration 085: `tenant_campaign_settings` + `skip_contact_quality text NOT NULL DEFAULT 'red' CHECK (off|red|red_yellow)`, `lapsed_after_days int NOT NULL DEFAULT 30 CHECK (1..365)`; the existing seed trigger/backfill (078) still yields a full row. `campaigns` + `audience_skip_quality text NOT NULL DEFAULT 'off'` (existing campaigns keep today's behaviour) and `audience_lapsed_days int NULL` (null = no lapsed filter), snapshotted at create.
2. One SQL resolver (REVOKE-locked, service role, paged like 067/079), with a count variant built on the same filter: active members of the audience (all | selected | tags) → optional `last_visit_at < now() - lapsed days` (members never visited count as lapsed) → optional quality exclusion that reproduces `classifyContactQuality` (window + thresholds passed as params from `contact-quality.ts`, not hard-coded in SQL; no data = never excluded; unreachable = red). It returns the per-step counts the summary needs.
3. `resolveTargetMembers` uses the resolver for every audience. The lapsed filter composes with tags (fixes tags-over-winback precedence). Win-back campaigns default the lapsed filter on with the tenant's days. The send uses the campaign's snapshot.
4. Tenant routes: GET/PUT `/api/dashboard/settings/campaigns` (GET any tenant member, PUT `requireTenantAdmin`, restaurant id from `getTenantContext` only) plus the quality distribution for the bar. Audience-count endpoint for the form returns counts only.
5. Settings regroup: `/dashboard/setup/<group>` routes, sub-nav (desktop) / index (phone) per the UX spec; existing sections move unchanged. New Campaigns group with legend meanings, skip toggle + level, lapsed days, read-only thresholds.
6. Campaign form Audience: lapsed + skip filters pre-filled from settings, colour key, recipient summary from the count endpoint; create persists the snapshot. Members-table badge tooltip gains the colour meaning (D4).
7. i18n en + zh-HK; test ids per spec into `ui-map/testid-registry.md`; kanban CAMP-016; poc-log line.

## Threat notes (main thread, authz-only slice; no payments; member data never leaves the tenant)
- R1 PUT settings: admin only, tenant from session, body never carries restaurant id; staff → 403, row unchanged (test).
- R2 Count/distribution endpoints: tenant-scoped by session; return aggregates only, no member ids or phones.
- R3 Resolver RPC: EXECUTE revoked from anon/authenticated; `p_restaurant_id` filter on every join (incl. whatsapp_messages).
- R4 Server re-validates enum/range on PUT and on campaign create; the client's pre-fill is a convenience, not trust.
