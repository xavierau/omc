# WI-15 — fix confirmed frontend defects from the WI-12 UI walk

## Outcome

Both defects from `tests/2026-09-10-int-001-ui-walk.md`'s Anomalies section are fixed. Root cause
for both was the same: `[id]/page.tsx` gated three unrelated UI slots (Settings-tab cards, paused
banner, Deliveries tab body) on a single `isAdmin && settings` truthy check, which could not tell
"not an admin" apart from "admin, but the settings fetch failed for an unrelated reason." Fixed by
adding a `settingsError` state to `useIntegrationDetail` and a pure resolver
(`resolveSettingsPanelState`) that the three slots now share.

## Defect -> test -> fix

**Defect 1 — silent card/banner failure.** `GET .../settings` failing (500 / network / any non-2xx
other than 403) made the three settings cards and the paused banner vanish with no error, no retry —
only the base-integration fetch had an error branch.

- Test: `settings-panel-state.test.ts` — `resolveSettingsPanelState(true, false, 500|502|400|404|0)`
  must be `'error'`, never `'roleMessage'` or `'ready'`. `settings-error-panel.test.tsx` — the new
  `SettingsErrorPanel` renders the mapped message (`settingsErrorMessageKey`, generic fallback for an
  unrecognized/free-text code such as the route's raw `'Failed to load settings'` 500 body) and fires
  `onRetry` on click. Both files imported not-yet-existing modules first — confirmed red (`Cannot find
  package ...`) before either implementation file was written.
- Fix: `useIntegrationDetail` now tracks `settingsError: { status, error } | null` alongside
  `settings` (clearing `settings` on a failed retry too, so a stale prior success can't keep
  rendering as "ready"). `[id]/page.tsx` renders `<SettingsErrorPanel errorCode={settingsError.error}
  onRetry={mutate} testId="..."/>` in place of the three cards, and in the paused-banner's slot, when
  `resolveSettingsPanelState` returns `'error'`. `InboundCredentialsCard` (doesn't depend on
  `settings`) was already unconditional and is untouched — confirmed still renders in every state.

**Defect 2 — misleading admin-only copy (Deliveries tab).** The same `isAdmin && settings` gate on
the Deliveries tab fell through to the "only tenant admins can view/manage these settings" message on
a non-403 settings-fetch failure, actively telling a real admin they lack permission.

- Test: `settings-panel-state.test.ts` — `resolveSettingsPanelState(true, false, 403)` must be
  `'roleMessage'` (a 403 from the admin-gated settings route means the caller isn't really an admin,
  regardless of the client's cached role); every non-403 status must be `'error'`, never
  `'roleMessage'`.
- Fix: the Deliveries tab now branches on `resolveSettingsPanelState`: `'error'` -> the same
  `SettingsErrorPanel` (testId `deliveries-fetch-error`) with Retry; `'roleMessage'` -> the existing
  `deliveries-admin-only` paragraph, now correctly scoped to "not admin OR settings 403'd" instead of
  "settings didn't load for any reason."

**Activity tab — audited, not changed.** It's gated on `isAdmin` alone (not `settings`), and
`ActivityLogTable` already does its own fetch with its own error state (the walk confirmed this
renders "無法載入活動記錄。" correctly to a real admin on failure). It does not share the defective
pattern, so no fix was needed there — this was verified by reading the component and the walk's PASS
result for that scenario, not assumed.
