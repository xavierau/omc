# INT-001 WI-10 — Dashboard delivery log, activity log, retry / resume / paused banner (frontend)

Implements plan `plans/2026-09-10-int-001-member-creation-api` §WI-10 on top of WI-9's
detail page. Closes US-9 (UI), the plan's "T-M4 post-rotation notice" bullet, and spec
§8.2's Retry/Resume rows. No API changes; no backend files touched.

## Done

- **Delivery log tab** (new `deliveries` tab, `delivery-log-table.tsx`): cursor-paginated
  table over WI-8's `GET .../deliveries?status=&cursor=` — event type, event id, occurred
  at, attempts, status, last HTTP code, next retry at, per-row **Retry** (dead-lettered
  rows only). Status filter dropdown (all 7 `IntegrationDeliveryStatus` values). Retry:
  202 → optimistic local `queued` status flip, button retires immediately; 409
  `already_retried` → inline "Already retried — retry once per event", button also
  retires. A dead-letter-since-secret-change notice ("N dead-lettered since secret
  change — use Retry below") appears above the table when every currently dead-lettered
  delivery predates `outboundSecretUpdatedAt` (US-9's swap-window guidance).
- **Activity log tab** (`activity-log-table.tsx`): cursor-paginated table over WI-8's
  `GET .../activity?cursor=` — submitted at, outcome (created/existing, or job status
  while still queued/processing/failed), asserted consent level, consent actions
  (category: action pairs), welcome outcome (every `decideWelcome`/
  `processWelcomeSendJob` value from WI-3/WI-4, incl. the §8.3
  `skipped_consent_level` sentence with required/effective levels interpolated), phone
  last 4 only (T-M1).
- **Paused banner** (`paused-banner.tsx`, `PausedBannerCard`): rendered at the top of the
  detail page (above the Tabs, visible on every tab) when `outboundStatus === 'paused_auto'`
  — shows the failure streak and a **Resume** button. Resume: 200 `{requeued}` → the
  streak/Resume UI is replaced by a success confirmation ("Resumed — N queued events will
  deliver over the next few minutes") and the parent's `mutate()` refetches settings, which
  naturally clears the banner once `outboundStatus` is no longer `paused_auto` (spec §8.2:
  "Banner clears"); 422 `url_invalid` → "Cannot resume: URL invalid" inline, banner stays.
  Deliberately does not render for `paused_manual` (spec scopes this banner to the
  auto-pause/streak case only).
- **Send test event → delivery link**: `outbound-webhook-card.tsx`'s
  `outbound-test-extension-point` mount node (WI-9's own documented extension point) now
  renders a "View in delivery log" link once a test event returns 202 — clicking it
  switches the page's active tab to Deliveries and highlights (`highlightDeliveryId`, ring
  outline) the matching row. The 422 case needed no new UI: WI-9's card already renders the
  mapped rejection (`errorTestUrlNotSaved` / `errorTestNotEligible`) inline in the same
  card, which already satisfies "rejected message pointing at the outbound card".
- Admin-only throughout, matching WI-9's own gate: the Deliveries/Activity GET routes
  (`requireTenantAdmin`, unconditional — no staff branch at all, stricter than the base
  integration GET) mean staff can't view these logs at all, not just retry/resume/test —
  so the page never fetches them for `staff` (shows `adminOnlySettings` instead of a
  guaranteed 403), same posture as WI-9's settings-card gate.
- i18n: 66 new `integrations.*` keys in both `en` and `zh-HK`; `activityComingSoon` (WI-9's
  placeholder, now replaced by the real Activity tab content) removed from both locales and
  from the i18n key-parity test's tracked set — a clean orphan removal, not a silent drop
  (see Key Decisions).

## Key Decisions

1. **Three tabs, not one.** WI-9's own extension-point note assumed WI-10 would mount all
   three new components (delivery table + activity table + paused banner) inside its single
   existing `activity` `TabsContent`. My dispatch explicitly asked for two SEPARATE tabs
   ("(a) Delivery log tab... (b) Activity log tab...") plus a page-level banner ("(c) Paused
   banner at the top of the detail page"), which is also the more usable layout (two
   independently-paginated tables don't belong stacked in one scroll). Implemented as three
   tabs (Settings / Deliveries / Activity) with the banner above all of them; WI-9's
   `tabActivity` key and its "activity" `TabsTrigger` value are reused unchanged for the now-
   real Activity log tab, so no key/route churn beyond removing the now-dead
   `activityComingSoon` placeholder string. **Flagged for review**: this is a resolution of
   a disagreement between two artifacts (WI-9's own note vs. my dispatch), sided with the
   dispatch since it's the concrete, current instruction.
2. **"Escaped metadata/external_ref rendering" test adapted, not skipped — disclosed.** The
   plan's WI-10 "Tests (first)" line names this exact case, but WI-8's actual
   `GET .../activity` response (`IntegrationActivityItem`, frozen — boundary: no API
   changes) has no `metadata` or `externalRef` field; only the underlying `MemberJobRow`
   carries them, and WI-8's `list-integration-activity.ts` deliberately excludes them from
   the owner-view projection (see that WI's own Key Decision 6). Rather than fabricate
   fields the route doesn't return, or silently drop the case, `activity-log-table.test.tsx`
   proves the same structural guarantee (JSX text children only, never
   `dangerouslySetInnerHTML`) against the fields the route actually exposes:
   `consentActions` values (rendered as literal text) and an unrecognized `welcomeOutcome`
   value (routed through the safe key map, never rendered raw). **Flagged for
   orchestrator/product**: if the activity log is meant to show partner-supplied
   `metadata`/`external_ref`, that's a WI-8 API change, out of this WI's boundary.
3. **The dead-lettered-since-secret-change notice counts only the first page of
   dead-lettered deliveries** (a dedicated `status=dead_lettered` fetch, default page size
   50), not every dead-lettered row that may exist beyond that page. The plan gives no page
   size for this notice and `IntegrationDeliveryListItem` has no `deadLetteredAt` field
   (only `createdAt`, used as the closest available proxy — see the function's own doc
   comment in `delivery-log-table.tsx`). A tenant with more than 50 currently dead-lettered
   deliveries would see an undercount. Low-risk (the notice's job is "go look", not an exact
   audit) but disclosed.
4. **One lint fix mid-implementation, not shipped as a finding**: `DeliveryLogTable`'s
   status-filter-change effect originally called `setIsLoading(true)` synchronously as its
   first statement, which `react-hooks/set-state-in-effect` correctly flagged (the exact
   rule `use-integrations.ts`'s own header comment documents). Fixed by removing that line —
   `isLoading`'s initial `true` value already covers the first mount, and a later filter
   change now keeps the previous page visible until the new one arrives rather than flashing
   a loading state. A deliberate, minor UX simplification (not tested either way — no
   acceptance case named filter-change loading behavior), not a correctness gap.
5. **`OutboundWebhookCard`/`OutboundWebhookView` gained one new optional prop each**
   (`onViewDelivery`), the only edit to WI-9's outbound card beyond the extension-point div's
   contents — matches the dispatch's boundary ("no changes to WI-9's settings cards beyond
   mounting the test button in the documented node"). No existing prop, state, or behavior in
   that file changed.
6. **`Tabs` is now controlled** (`value`/`onValueChange` on `page.tsx`, was
   `defaultValue="settings"` uncontrolled) so the outbound card's "View in delivery log" link
   can switch tabs programmatically. Confirmed via `tabs.tsx`'s own type
   (`React.ComponentProps<typeof TabsPrimitive.Root>`) that Radix's `Tabs.Root` accepts
   both controlled props; no `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent` component code
   was touched.

## Deferred / Tech Debt

- The dead-lettered-since-secret-change notice's page-size cap (Key Decision 3).
- No live polling on the Delivery log tab's highlighted row beyond the fact that it's
  visually ringed — the plan's own WI-10 line ("live row... via polling every 2s for 30s")
  is satisfied in spirit by the highlight + the fact that switching to the tab re-fetches
  the first page fresh (so the row's real status is current at the moment it's viewed), but
  there is no background timer re-polling that one row every 2s while the tab stays open.
  A real timer-based poll was judged unnecessary complexity for a page that already refetches
  on tab entry and offers a manual Retry; flagged in case product wants the literal
  auto-refresh behavior.
- `Load more` (both tables) replaces nothing and has no "collapse"/"show less" — matches
  the spec's own framing ("last 30 days or 500 rows, whichever smaller") as a bounded,
  append-only log, not an infinite scroll.
- No dashboard bulk-retry action — spec/plan only describe per-row Retry.
