# INT-001 WI-8 — Dashboard settings/secret/deliveries/retry/resume/test/activity APIs (backend)

Implements plan `plans/2026-09-10-int-001-member-creation-api` §WI-8 and the plan's
"API Contracts" dashboard section. All 7 routes role-gated (`requireTenantAdmin`),
scoped-lookup-gated (#111 pattern), and audited (who/what/when, old→new, secrets as
last4 only).

**Note on the dispatch's threat references**: the brief named T-M5, T-M14, T-M15,
T-L1, T-L2. The actual threat model (`threats/2026-09-10-int-001-member-creation-api.md`)
has no T-M14, T-M15, T-L1, or T-L2 — it tops out at T-M12 (Medium) and T-L3/T-L4 (Low).
The plan's own WI-8 "Closes" line names T-M5, T-M6, T-M11 instead, which is what this
work actually closes. Flagging the mismatch per house rule (stale/contradictory
artifacts get reported, not silently repaired) rather than guessing which items were
meant.

## Key Decisions

1. **The `/settings` route owns its own projection shape, not `public-integration.ts`.**
   The plan's "Dashboard read projection" section describes an aspirational unified
   `toPublicIntegration()` that nests a `settings` object — but WI-0's actual
   `toPublicIntegration()` (frozen, tested via an `Object.keys` equality assertion in
   its own route test) has no such field, and WI-1 didn't add it either (both
   deferred it, per WI-0's own Review Hand-off, to "once those columns exist").
   Retrofitting WI-0's base GET routes now would risk breaking that frozen test and
   exceeds my dispatch's own route list. Instead, `IntegrationSettingsView` is a new,
   self-contained shape returned only by my new `/settings` route — it carries the
   full field set from the plan's "Dashboard read projection" prose (status, failure
   streak, paused-at, secret last4/updatedAt) since WI-9/WI-10 will need those to
   render the cards spec §8.2/8.3 describe. **Flagged for WI-9's reviewer**: the
   settings card should call `GET .../settings`, not expect these fields nested
   under the base `GET .../[id]` response.
2. **`outboundEnabled: true` validated by reusing WI-1's own frozen
   `IntegrationSettings.fromProps()` invariant**, not a hand-derived rule. The merged
   candidate state (current row + this patch) is built in memory and passed through
   `fromProps`; a thrown invariant error maps to the one enabling-blocked code the
   plan's frozen contract provides, `pii_ack_required`. This one code fires for
   *any* of the three missing prerequisites (URL, PII ack, secret) — the plan's
   contract has no separate code for "no secret saved yet", and I chose not to
   invent one outside the frozen list. In practice a real UI would keep the toggle
   disabled until URL+secret are both present, so this collapsed case is unlikely to
   surface to an owner in the shipped flow. **Flagged for product/orchestrator
   sign-off**, same posture as WI-6's own disclosed judgment calls.
3. **`template_not_owned` vs `template_not_found` needs an unscoped existence
   check.** `whatsapp-template-repository.ts`'s own header comment says its unscoped
   `findById` is "only for ids derived from an already-tenant-scoped row... for
   anything derived from a request, use `findByIdForRestaurant`" — my use here IS
   request-derived (an admin pastes a template id). I used `findById` anyway,
   *after* `findByIdForRestaurant` already returned null, purely to decide which of
   the two codes to return — no template field beyond bare existence is read or
   exposed. This is a deliberate, narrow exception to that file's own advisory
   comment, made because the plan's WI-8 frozen test list explicitly names both
   codes as separately testable ("foreign template uuid → `template_not_owned`").
   Template ids carry no PII; the disclosure is "a template with this id exists
   somewhere," nothing about who owns it. **Flagged for review** as the one place
   this WI deliberately goes against an existing file's own stated convention.
4. **`sendTestEvent`'s third outcome, `not_eligible_for_delivery`, is surfaced as
   its own 422 code** rather than folded into `url_not_saved` (semantically wrong —
   the URL *is* saved) or dropped. The plan's literal API Contract for this route
   only lists two outcomes (`202` / `422 url_not_saved`), written before WI-6 built
   `sendTestEvent` and discovered the fan-out trigger also requires
   `outbound_enabled` + a PII ack. Since WI-6's service already ships this third
   return value (disclosed in its own handoff), I chose to expose it honestly rather
   than mis-map it. **Flagged for orchestrator/product sign-off** — the same class
   of plan-vs-shipped-code drift WI-6 itself disclosed twice in its own artifact.
5. **The retry route re-fetches the delivery once more than strictly necessary.**
   `retryDelivery(deliveryId)` (WI-6, frozen signature) takes only a delivery id and
   performs no integration/tenant scoping itself — WI-6's own handoff explicitly
   assigns that scoping to "its route." My route loads the delivery via
   `findDeliveryById` first, checks `integrationId === [id]` AND
   `restaurantId === ctx.restaurantId` (defense in depth, #111 lesson), returns 404
   on any mismatch, and only then calls `retryDelivery`, which reads the same row
   again internally. Two reads of one row by primary key, not a loop — no N+1
   concern — but flagging the redundancy in case a future refactor wants
   `retryDelivery` to accept a pre-loaded delivery instead.
6. **`list-integration-activity.ts` builds its wire shape directly from
   `MemberJobRow`, never through the `MemberJob` domain entity.** That entity's only
   serialisation method, `partnerView()`, is deliberately scoped ("the ONLY way this
   entity may be serialised back to a partner") and has no owner-view counterpart.
   Rather than add one to a frozen, partner-safety-critical entity, the owner
   projection is assembled as a plain mapping in the application layer — matching
   how WI-0's `toPublicIntegration()` also works directly off a plain entity/row
   without extra domain-entity machinery.
7. **Cursor design**: both list endpoints use the last row's own sort column
   (`created_at` for deliveries, `submitted_at` for activity) as an opaque,
   exclusive-`<` cursor — no existing cursor-pagination convention was found
   elsewhere in the dashboard API to follow, so this is a new pattern. `nextCursor`
   is returned only when a page came back full (a partial page proves no more rows
   exist without an extra count query).
8. **Delivery list avoids Supabase's embedded-resource select syntax** (e.g.
   `.select('..., integration_events(type)')`) even though the FK exists — no other
   repository file in this codebase uses that syntax; every existing multi-table
   read here batches ids into one `.in()` query instead (`pruneOrphanIntegrationEvents`
   is the closest precedent). Followed that established convention:
   `findDeliveriesForIntegration` returns delivery rows only, and
   `list-integration-deliveries.ts` does one batched `findIntegrationEventsByIds`
   call for the whole page, never per-row.

## Tests

**94 new tests across 12 files:**
- `integration-settings-validators.test.ts` (17) — allowlist rejection, every field's
  shape validation, valid-patch acceptance, secret-length boundary.
- `update-integration-settings.test.ts` (19) — the core business-rule surface: empty
  patch no-ops; `'default'` with no `welcomeCampaignId` → `no_default_welcome_template`;
  `'default'` resolved + tenant quality-paused → `warnings: ['tenant_quality_paused']`;
  foreign-but-existing uuid → `template_not_owned`; nonexistent uuid →
  `template_not_found`; owned-but-unapproved uuid → `template_not_approved`; every
  `validateOutboundUrl` error variant mapped to its specific code; a valid URL saved
  + audited old→new; enabling outbound with nothing saved → `pii_ack_required`,
  zero writes; enabling outbound with URL+secret already present and the PII ack
  granted in the *same* patch → success; `outboundEvents` change audited; ack
  true-then-false clears both `_at`/`_by`; an unchanged field in the patch writes no
  audit row.
- `set-outbound-secret.test.ts` (4) — too-short rejected (persists nothing),
  non-string rejected, valid secret returns last4 only (plaintext never in the
  response JSON), audit row carries old/new last4 only (plaintext never in the
  audit-call JSON).
- `list-integration-deliveries.test.ts` (3) — batches event lookups in ONE call
  across a 3-row/2-distinct-event page (explicit N+1 guard,
  `toHaveBeenCalledTimes(1)`); page-size cap at 500; `nextCursor` only on a full page.
- `list-integration-activity.test.ts` (3) — asserted wire shape contains no `phone`
  key and no 8+-digit run anywhere in the serialised JSON (the T-M1 "never the full
  phone" invariant, checked structurally, not just by field name); scoped by BOTH
  integrationId and restaurantId; `nextCursor` only on a full page.
- Route tests (7 files, 48 tests) — for every mutating/reading route: `staff → 403`,
  `admin → 200`, foreign-tenant id → `404` via the scoped `getIntegration` lookup
  before any application call, every documented error code mapped to its HTTP
  status, `Object.keys` equality on the settings GET/PATCH projection (fails on any
