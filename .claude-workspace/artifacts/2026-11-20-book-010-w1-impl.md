## Key Decisions

- **Room rules apply only when booking hours are set** (`roomApplies(hours)` in `booking-room.ts`, the one gate every channel calls). Periods and slots come from the hours, so with hours unset nothing reads counts or stops and every path is BOOK-009 exactly; the stops API answers `form: hours_not_set`. Coordinator note: when BOOK-009's `scheduleEnabled` merges, add it to `roomApplies` only.
- **Function signature** (decide_yourself): `insert_booking_request_if_room(p_row jsonb, p_period_key, p_period_first, p_period_last, p_slot_limit, p_meal_limit) → jsonb {ok, row} | {ok:false, refusal:{kind:'full', scope:'slot'|'meal', guests, limit} | {kind:'stopped', scope}}`. `p_row` is the plain insert's row (`bookingInsertRow`, shared), allow-listed in SQL (any other key raises 22023), inserted with dynamic `INSERT … SELECT FROM jsonb_populate_record` of exactly the keys passed, so defaults (status pending, ids, timestamps) apply as before. Counts come back with a refusal.
- **Lock**: `pg_advisory_xact_lock(hashtextextended('book010:room:<restaurant>:<date>'))` via `booking_room_lock`; promotion takes the BOOK-003 phone lock first, then the candidates' date locks in date order (no deadlock between promotions; inserts take one date lock only).
- **PAP code step**: a new function `promote_agent_booking_with_room` (084's function untouched); the repository reads the candidate slots first so TypeScript computes each period/limits (`p_rooms` keyed by id). A full candidate → `declined`, `decline_reason 'full'`, `decided_by` null; staff never act. `verifyAgentBooking` change is one argument + one branch (coordinator note); the reply is `agent-booking-full-reply.ts` (free-form, bilingual, ≤3 suggestions, the diner's chat booking link via `resolveBookingReplyTarget`).
- **PAP create** refuses `full` early (unverified rows hold no seats; the code step is the atomic check).
- **Period key**: the label, else `"first-last"`; that is what `booking_stops.period_label` stores.
- **Counting** (spec S1): pending + confirmed only; unverified, declined, cancelled, no_show never count; a change row counts at its new time while its original still counts.
- **Over limit**: a pending row already counts, so "after confirm" = today's count; for a change request the original (same date) comes off. Returns 409 `over_limit`; `guests` is the count after confirming (spec AC-10 "takes 19:00 to 34 / 30").
- **Suggestions** never include the refused time itself (a stale read could otherwise offer it back).
- **AC-15 placement**: the "some times may be full; always check with the tool" rule is in the booking rules (prompt section) whenever hours are set (stops can apply without limits), and in BOOKING RULES when limits are set. A W4 test pins BOOKING RULES byte-for-byte for hours without limits, so the line is not added there (test not changed).
- **Stopped by** = the staff member's email name (before `@`) via `auth.admin.getUserById`; there is no staff display-name field in the app (spec OQ2). `stopped_by` (uuid) is stored too.
- **Staff roles**: admin or staff (the only two `user_tenants` roles); anything else 403. Capacity GET uses the same check.
