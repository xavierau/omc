## Finding → test → fix

### N-1 — pre-auth throttle keyed on public `integrationId` alone

**Finding**: `checkPreAuthThrottle` gated ALL traffic to an integration on one bucket
keyed only on the URL's `integrationId`. An unauthenticated flood could exhaust it and
429 the partner's own signed traffic at the very first statement — the exact outcome
T-H5's "charge after signature" rule exists to prevent.

**Red**: added `integration-inbound-guard.test.ts`'s N-1 describe block against the
OLD 2-arg `checkPreAuthThrottle(rateLimiter, integrationId)` signature — a flood from
one attacker identity WOULD have exhausted the shared bucket and 429'd a concurrent
"partner" call, since there was only one bucket per integration.

**Fix**: `src/application/integration-inbound-guard.ts`
- `extractTrustedClientIp(request)` (new, :~113-135): reads nginx's own `X-Real-IP`,
  falling back to the RIGHTMOST `X-Forwarded-For` hop (the one nginx itself appends via
  `$proxy_add_x_forwarded_for`) — never the leftmost, client-supplied hop
  `audit-logger.ts`'s `extractIp` reads (fine for an audit-log column, unsafe for a
  security-relevant rate-limit key).
- `preAuthBucketKey(integrationId, clientIp)` (was `(integrationId)` only) — the
  PRIMARY defence: a flood from one real IP throttles itself without touching a
  different real IP's budget on the same integration.
- `preAuthCeilingBucketKey(integrationId)` (new) + `PRE_AUTH_CEILING_RATE_PER_MIN` /
  `PRE_AUTH_CEILING_BURST` (10x the per-ip limit, :~40-58) — the review's "much higher
  integrationId-only ceiling" kept as a last-resort guard against a genuinely
  DISTRIBUTED flood (many real IPs, each individually under the per-ip limit). Checked
  SECOND, only after the per-ip bucket allows — so a request already throttled by the
  per-ip bucket never also burns ceiling budget.
- `checkPreAuthThrottle(rateLimiter, integrationId, clientIp)` — new required 3rd param.
- Both route files (`members/route.ts:53`, `jobs/[jobId]/route.ts:30`) now call
  `extractTrustedClientIp(request)` and pass it through.

**Green**: `integration-inbound-guard.test.ts` — new `describe('N-1: ...')` block:
1000 unsigned requests with rotating (spoofed leftmost-XFF-equivalent) identities but
ONE real ip do not 429 a concurrent request from a DIFFERENT real ip on the same
integration; the same flood from one real ip IS throttled; the integrationId-only
ceiling still trips on a true distributed flood (many distinct real ips); a
per-ip-throttled request never also consumes the ceiling. Plus a dedicated
`extractTrustedClientIp` describe block (X-Real-IP preferred, rightmost XFF fallback,
leftmost-spoof immunity, `'unknown'` default). Route-level wiring proven in both
`members/__tests__/route.test.ts` and the jobs route's own test file (asserts the
`takeToken` key contains the trusted ip, not the spoofed leftmost hop).

**Nginx header assumption** (documented in `docs/integrations/member-api-ops.md`'s
Redis-key table, §4): nginx MUST set `X-Real-IP` to the real connecting peer, or append
it as the rightmost `X-Forwarded-For` hop. Without that, every request resolves to the
shared `'unknown'` bucket — a silent degrade back to pre-N-1 behaviour, not a crash, but
flagged explicitly in the ops doc as an ops precondition.

### N-2 — per-host throttle allegedly burns the BullMQ attempt budget

**Finding as written**: "BullMQ's `moveToDelayed` counts an attempt by default...
Fix: `job.moveToDelayed(ts, token, { skipAttempt: true })` ... check node_modules/bullmq
for the signature."

**Investigation (verify-before-fix — the premise is a claim about the repo, not just
the symptom)**: read the ACTUAL installed `bullmq@5.76.5` (`package-lock.json`):
- `node_modules/bullmq/dist/{cjs,esm}/classes/job.js`'s public `moveToDelayed(timestamp,
  token)` hardcodes `{ skipAttempt: true }` on the internal `scripts.moveToDelayed(...)`
  call, UNCONDITIONALLY, on every invocation. `job.d.ts`'s own type signature —
  `moveToDelayed(timestamp: number, token?: string): Promise<void>` — has no 3rd
  parameter in this version at all; `job.moveToDelayed(ts, token, { skipAttempt: true })`
  would be a TypeScript compile error, not a fix.
- `moveToDelayed-12.lua:367-369` only runs `HINCRBY jobKey atm 1` when `ARGV[6] == "0"`
  (skip-attempt false) — which the JS wrapper above never sends.
- **Empirically verified live** (not just read from source) against a real local Redis
  + real bullmq, scratch scripts under
  `/private/tmp/.../scratchpad/verify-movetodelayed-attempts{,-2}.cjs` (not committed —
  throwaway): 10 consecutive `job.moveToDelayed()` calls left `attemptsMade` at 0
  throughout; a following plain `throw new Error(...)` (BullMQ's own retry path via
  `moveToFinished` on failure — the ONLY place 5.76.5 increments `atm`) brought it to 1
  on the next pickup, exactly once.

**Conclusion**: N-2's premise does not hold for the pinned bullmq version.
`integration-outbound-processor.ts:83`'s throttle-path `job.moveToDelayed(ts, token)`
already never counts an attempt — there is no way to make it count via the public API,
so **no production code change was made**. This matches this repo's own
`principle_verify_issue_claims_before_planning` lesson: a review's symptom claim is
reliable, its prescribed fix is a claim about the repo that must be checked.

**Green (regression guard, not a fix-proving test)**: new
`src/infrastructure/queue/__tests__/integration-outbound-processor.n2-real-redis.test.ts`,
gated on `INT001_TEST_REDIS_URL` (same precedent as the C-2 real-Redis lane) — reproduces
the EXACT acceptance criterion from the dispatch ("10 consecutive throttle delays →
attemptsMade unchanged; a following transient failure counts 1") against real BullMQ +
Redis. Passes today with zero source changes; will FAIL the moment a future bullmq
upgrade ever changes this default, which is exactly the point it would need a real
`{ skipAttempt: true }` (or equivalent) fix re-added.

### G-3(a) / N-8 — CSV import misclassifies a legacy-format phone as `duplicate_active`

**Finding**: `import-contacts-batch-row-member.ts:54` called bare
`E164Phone.of(input.row.phoneE164)`; `phoneE164` is `PhoneNumber.create(raw).value` (the
SAME legacy, non-strict grammar the WhatsApp/web join paths already had a fallback for) —
a legacy-accepted format (dots, etc.) threw, landed in the generic catch, and was
rejected with `duplicate_active` — never imported, misleading reason code.

**Red**: `import-contacts-batch-row-member.test.ts`'s new N-8 describe block against the
unfixed file — a dotted phone would have thrown inside `createOrGetMember`'s call and
been rejected `duplicate_active` instead of created.

**Fix**: extracted `resolveLegacyMemberE164` (previously two near-identical copies in
`register-member.ts` and `register-member-web.ts`) into a new shared
`src/application/resolve-legacy-member-e164.ts` — DRY on the THIRD occurrence per this
repo's own `code-quality.md` rule, and directly the reason the CSV path was missed by
WI-14/WI-16 in the first place (three independent copies of correctness-sensitive
phone logic). `register-member.ts` and `register-member-web.ts` now `export {
resolveLegacyMemberE164 } from './resolve-legacy-member-e164'` — same public name/
signature, so `resolve-legacy-member-e164.property.test.ts`'s existing imports (`as
resolveWhatsappLegacyE164` / `as resolveWebLegacyE164`) are untouched.
`import-contacts-batch-row-member.ts`'s `createViaSeam` now resolves the phone in its
OWN try/catch, BEFORE calling the seam, so a genuine parse failure (reason:
`invalid_phone`) can never be confused with a DB/seam conflict (`phone_already_member`
/ `duplicate_active`) in the second catch.

**Green**: 3 new tests in `import-contacts-batch-row-member.test.ts` — dotted phone
imports via the fallback (`created: true`, not rejected); a letter-noised digit run
(genuinely unresolvable) rejects with `invalid_phone`, explicitly asserted `!==
'duplicate_active'`; a clean E.164 phone is unaffected (strict path, no behaviour
change for the common case).

### G-3(b) / N-9 — re-join with the same legacy phone 500s

**Finding**: on `register-member.ts` and `register-member-web.ts`, the pre-check SELECT
and (register-member.ts only) the race re-select still queried by the un-repaired
`phone.value` instead of the resolved E.164. A member first created via the G-3
fallback is stored NORMALISED; the same raw input on a second join misses the
pre-check, falls to the seam, hits its own 23505, and (register-member.ts) the
SEPARATE `findMemberByPhone` re-select (needed only to fetch profile fields the seam's
result doesn't carry) ALSO misses → throws `"race on create but no row found"` → 500.
(`register-member-web.ts` has no separate re-select — its seam call already used the
resolved value, so only its pre-check was affected.)

**Red**: new N-9 describe blocks in both `register-member.test.ts` and
`register-member-web.test.ts`, run against the unfixed code first — the pre-check test
asserted the WRONG (resolved) value was queried (would have failed pre-fix, since the
old code queried the raw dotted value); the race test asserted a returning-member
result instead of a thrown error.

**Fix**: both functions now call `resolveLegacyMemberE164` ONCE at the top and thread
`resolvedPhone.value` through the pre-check, the seam's `phoneE164` field, and (
`register-member.ts` only) the race re-select's `findMemberByPhone` call. The raw
`PhoneNumber` (`phone`) is still passed to messaging functions (`sendReturningWelcome`,
`onboardNewMember`) unchanged — those want the original contact identifier, which for
WhatsApp inputs is always already-strict E.164 anyway (bare digits from the webhook
`from` field, per the confirmation review's own WI-7 parity note); this fix only
touches DB lookups.

**Green**: `register-member.test.ts` — pre-check queries the resolved value for a
dotted phone; a genuine race (pre-check misses, insert 23505s, seam's own re-select
finds the row via `maybeSingle`, THIS function's own re-select now also finds it via
`single`) returns the returning-member result instead of throwing. `register-member-
web.test.ts` — pre-check finds a row created via the fallback on a second call with the
same raw dotted input.

**Test-infra note**: `register-member.test.ts`'s shared Supabase mock chain
(`mockEq2`) previously exposed only `.single()`. Extended (additively — no existing
test calls it) to also expose `.maybeSingle()`, since `insertMember`'s own 23505
re-select (`member-create-repository.ts`'s `selectMemberByPhone`) uses that method and
routes through the SAME shared `.from('members')` mock every query in this file uses.

### #6 (residual) — raw internal error text reaches the partner wire

**Finding**: `process-member-create-job.ts:371` persists a phone-redacted (I-3) but
otherwise raw caught-exception message under `code: 'internal'`; `member-job.ts:70`'s
`partnerView()` echoed it verbatim. Postgres/driver error text (T-M3 hygiene, not PII)
reached the partner.

**Red**: `member-job.test.ts`'s existing `'failed -> { status, error } only'` test
asserted VERBATIM passthrough of `message: 'boom'` for `code: 'internal'` — this
assertion was PROVEN WRONG by the finding and is the one existing test I changed (per
the dispatch's own carve-out). Narrowed to a known-safe code (`tenant_inactive`) to
keep testing verbatim passthrough where it's actually correct; the `code: 'internal'`
case moved into a new, explicit describe block.

**Fix**: `src/domain/entities/member-job.ts` — `partnerView()` now substitutes a fixed
`GENERIC_INTERNAL_ERROR_MESSAGE` whenever `p.error.code === 'internal'`; every other
code (currently only `PermanentJobFailure`'s `tenant_inactive` / `integration_paused`,
already fixed safe strings) passes through unchanged. Deliberately done ONLY in
`partnerView()`, not at the point of persistence (`process-member-create-job.ts:371` is
unchanged) — this keeps the raw detail intact in `snapshot.error.message` for the
owner's activity log (WI-8) and the Slack alert `process-member-create-job.ts` already
sends alongside it, satisfying "keep the raw one server-side" WITHOUT a schema change
or new migration (out of this dispatch's boundary either way).

**Green**: `member-job.test.ts`'s new `#6` describe block — a raw message containing a
phone-shaped substring and stack-like text is replaced with the fixed generic string in
`partnerView()`, and the JSON-stringified view contains neither; the entity's own
`snapshot.error.message` still carries the raw text (proves the split, not a
destructive redaction at the source).
