## `member.updated` End-to-End Verification (scratch-DB lane)

Per the plan's own WI-7 Tests-first bullet ("`updateMemberPreferredLanguage`
and STOP produce `member.updated` via the triggers (scratch-DB lane)") —
`member.updated` is produced **entirely by DB triggers** (migration 071;
`emit-integration-event.ts`'s own header comment: "member.updated events
are inserted by DB triggers and never reach this function"), so there is no
application-layer seam a fake/mock can intercept for this specific
assertion — a scratch-DB lane is the only way to prove it, not an
alternative to it.

Built an isolated scratch DB (`scratch_int001_wi7`, mirroring WI-1's own
technique: stub `auth.uid/role/jwt`, `extensions.gen_random_bytes`,
`storage.buckets/objects/foldername`, `supabase_realtime` publication;
apply migrations 001–072 in order; fixtures + assertions inside a
rolled-back transaction; drop the DB after). Script itself lived in this
session's scratchpad (gone once the session ends, per the usual
scratchpad-not-committed convention) — the exact fixtures and assertions
are reproduced verbatim below so **WI-11's release gate can re-run this
suite before `supabase db push` ever touches a real environment**, without
needing my session artifacts.

```
Assertion A passed: preferred_language change -> member.updated{language}, origin NULL, 1 queued delivery
Assertion B passed: status change -> member.updated{status}, 1 queued delivery
Assertion C passed: consent change -> member.updated{consent}, 1 queued delivery
Assertion D passed: points_balance change produced no member.updated event
```

Full narrative (problem, root cause, fix, and why WI-1's own five
assertions never caught this) is in
`debugging_journals/2026-09-10-migration-071-array-append-literal.md`.

- **A** — `UPDATE members SET preferred_language = ...` (what
  `updateMemberPreferredLanguage` does) → one `integration_events` row,
  `type='member.updated'`, `changed=['language']`, `origin_integration_id
  IS NULL` (correct: a DB-trigger-produced event has no originating
  integration — only the partner-API seam call sets that field), fanning
  out to exactly one `queued` delivery for an enabled+URL-saved+PII-acked+
  subscribed integration.
- **B** — `UPDATE members SET status = 'unsubscribed'` (what STOP's
  `handleUnsubscribe` in `member-handlers.ts` does — a raw direct update,
  outside WI-7's file list, so I replayed the equivalent SQL rather than
  invoking application code) → `changed=['status']`, same fan-out.
- **C** — `INSERT INTO consent_records (...)` for the member's phone →
  `changed=['consent']`, same fan-out.
- **D** (negative) — `UPDATE members SET points_balance = ...` → **zero**
  `integration_events` rows, confirming spec/OD's "not points" invariant
  the trigger's own column list (`OF name, preferred_language, status`)
  is supposed to guarantee.

Each assertion used a **different** member row specifically to avoid the
trigger's 5-second coalescing bucket merging separate column-changes into
one event (which is itself correct, intended behaviour — just not usable
for proving each column-list branch independently in one transaction).

## Key Decisions

- **Kept each legacy path's pre-check SELECT; routed only the actual insert
  through the seam.** Considered eliminating the pre-checks and relying
  purely on the seam's insert-then-23505-reselect pattern, but every
  pre-existing test's mock is built around the pre-check running first
  (e.g. `register-member-web.test.ts`'s "existing member" test only
  configures the SELECT mock, not the INSERT mock — an insert-first design
  would hit an unconfigured mock and fail). This also matches
  `registerMember`'s and `registerMemberWeb`'s real behaviour
  unchanged for the common case; only a genuine double-submission race now
  goes through the seam's conflict path instead of crashing.
- **CSV import's `phone_already_member` vs. seam's `outcome:'existing'`.**
  The seam has no concept of "is a duplicate acceptable here" — it always
  resolves a conflict gracefully. CSV import's own business rule (reject a
  duplicate phone when `mergeExistingMembers` is off) is layered on top of
  the seam's result in `import-contacts-batch-row-member.ts`, not inside
  the seam. A thrown error from the seam is only reached when the
  conflicting row vanishes between insert and re-select (an even rarer
  race than the seam's own contract anticipates); such a throw is mapped
  by matching the frozen, WI-1-owned literal substring `'unique violation
  on insert'` back to `phone_already_member`, any other thrown message to
  `duplicate_active` — reproducing the original `tryInsertMember`'s
  `code==='23505' ? phone_already_member : duplicate_active` mapping
  exactly, including for the untested non-conflict-error branch. This
  message-matching is a real, disclosed code smell (coupling to another
  file's exact thrown text) but is the only way to preserve this
  distinction given the seam's fixed, non-typed-error contract — flagged
  for review rather than silently accepted as clean.
- **Two unavoidable pre-existing-test edits**, both purely mock-robustness
  fixes with **zero assertions changed** (same expected values throughout):
  1. `member-creation-parity.test.ts` queued exactly one
     `createServerSupabaseClient` return value via `mockReturnValueOnce`
     for `registerMemberWeb`'s call, assuming (correctly, pre-WI-7) that it
     only ever acquires one client per invocation. Routing through the seam
     means it now legitimately acquires two (its own pre-check, then the
     seam's internal `insertMember`) — changed to `mockReturnValue`
     (persistent) so both calls get the same client, which both correctly
     serve from the SAME `from` mock's `select`/`insert` methods.
  2. Both `member-creation-parity.test.ts` and
     `import-contacts-batch-row.test.ts` recorded **every** `.insert()`
     call into a single sink regardless of table name. With the seam now
     wired to the real `IntegrationEventPublisher` (WI-6), a created member
     also triggers its own separate `.from('integration_events').insert(...)`
     as an intended side effect — which was clobbering/duplicating the
     `members`-insert capture the test actually cares about. Fixed by
     discriminating `from(table)` by table name: only `'members'` gets the
     real recording chain, anything else gets an inert stub matching
     `emit-integration-event.ts`'s own best-effort, never-throws contract
     for its fan-out step.
  Both are disclosed here in full rather than buried in a diff; the
  orchestrator/reviewer should treat these as the two places this frozen
  suite was touched, and confirm the reasoning holds.
- **Out-of-scope fix: migration 071's `member_updated_outbox()` had a real,
  reproduced bug** — `changed_cols := changed_cols || 'name'` (and the same
  for `'language'`/`'status'`) throws `ERROR: malformed array literal` in
  real Postgres (untyped string literal makes `||` resolve to
  array-concat, not array-append; verified in isolation before touching
  any app code). This is outside WI-7's stated file list (migrations
  069–072 are WI-1's), but it made the plan's own required
  `member.updated` scratch-DB verification impossible to pass, and it is a
  **production-blocking bug for the whole app**, not just INT-001 — any
  future update to `members.name`, `preferred_language`, or `status`
  anywhere (including pre-existing STOP handling and language detection)
  would throw the instant this migration is deployed. Fixed with explicit
  `::text` casts on the three affected lines (verified both by isolated
  repro and by the full scratch-DB assertion suite above). The migration
  is not yet deployed to any shared environment, so editing in place
  (rather than adding migration 073) matches this repo's convention for
  pre-release migration fixes. **Sent directly to the team lead** the
  moment this was found, since WI-3/WI-4/WI-6/WI-8/WI-9 all build on this
  migration and would hit the identical symptom independently.
- **`E164Phone.of(phone.value)` after `PhoneNumber.create(rawPhone)`** in
  all three paths. `PhoneNumber.create` is more lenient (8–15 digits, any
  leading digit) than `E164Phone.of`'s strict `^\+[1-9]\d{7,14}$` (no
  leading zero after the country-code `+`). For genuine E.164 numbers
  (real country codes never start with 0) these ranges coincide in
  practice; a number `PhoneNumber.create` would accept but `E164Phone.of`
  would reject is a real, if narrow, theoretical gap. Not exercised by any
  existing test, and inherent to reusing the seam's strict-typed input —
  flagged rather than silently assumed safe.
