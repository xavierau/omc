## Key Decisions

**I-4 mechanism, and a bug in my own first draft.** My first implementation only
recorded the digest key when a nonce reuse was ALREADY detected (`if (replayed) { ...
check digest ... }`). That fails on the very first same-nonce-same-digest pair: the
FIRST request never touches the digest key (replayed is false, so the branch is
skipped), so when the SECOND request arrives with the identical digest, the digest
key has never been written and looks "new" — incorrectly read as "different body" and
rejected. Fixed by recording the digest key on **every** request unconditionally, and
only *acting* on the comparison when `replayed` is true. Caught by my own frozen test
("same nonce + same digest (retry) -> accepted") going red before the fix — did not
weaken the test to route around it.

**`resumeOutbound`'s settings lookup — the ONE line where the addendum and I both
independently landed a fix, and mine happened to arrive last.** Per that artifact's
own note, it assessed `resumeOutbound`'s risk as materially lower than `retryDelivery`'s
(it operates on an already-tenant-verified `integrationId`, not a separate
foreign-object id) and left it as a lower-priority item; I completed it anyway per my
own brief's literal "resume" instruction. No conflict resolution was needed — I
landed second and the change was additive on top of what was already there.

**`digest` on `GuardInboundRequestInput` is a NEW required field**, not optional. A
call site that forgets it would silently accept ANY nonce reuse as a same-body retry
(the bug my own fix exists to close) — making it required means a future caller that
skips it is a compile error, not a silent security regression. The only two callers
(`verify-signature-v2.ts`'s POST/GET paths) already had the value in hand as
`AuthenticateV2Input.digest` (sha256hex(rawBody) / jobId, per that file's own existing
doc comment) — no new computation needed, just threading it one level deeper.

**Property-test gap (G-3).** I did not originate G-3's fix, but the dispatch brief
explicitly named the acceptance bar as a property suite, not examples, and one didn't
exist yet when I checked. Rather than silently leaving it, I added it, found the
residual gap above, and fixed it with the smallest possible change (the throw-shape
only — no new parsing logic, no widened acceptance).
