# INT-001 WI-13 — origin_integration_id on member.updated + depth-counter rebuild (backend)

Closes the two gaps WI-11's documentation pass disclosed
(`artifacts/2026-09-10-int-001-wi11-backend`): the partner doc's
`origin_integration_id` echo-suppression note and the ops playbook's §7
"known gap: per-integration depth counter has no rebuild."

## Done

- **Gap A**: `member.updated` events produced by a partner-API-driven
  consent upgrade/insert or `external_ref` change now carry
  `origin_integration_id` = the calling integration. Every non-partner

  `origin_integration_id` NULL.

## Mechanism Chosen (Gap A) + Why

**RPC that runs the write in one transaction with `set_config(...,
true)`, read back by the trigger via `current_setting(..., true)`** — the
plan's own first-listed option, not the "processor writes the outbox rows
itself" alternative.

Why not a plain `.update()`/`.insert()` preceded by a separate "set the
session var" call: this app's Supabase client
(`src/infrastructure/supabase/client.ts`) talks to Postgres over
PostgREST, and PostgREST runs **every HTTP request in its own
transaction**. A `SET LOCAL`/`set_config(key, value, true)` made in one
`.rpc()`/`.from()` call is gone before the next call's transaction even
begins — even on the same pooled connection. So the config-set and the
write a trigger needs to see it from **must** happen inside the same
function call. Three new RPCs do exactly that:

- `insert_consent_record_with_origin(p_row jsonb, p_origin_integration_id uuid)`
- `upgrade_consent_to_opted_in_with_origin(p_restaurant_id, p_phone_e164, p_category, p_origin_integration_id)`
- `upsert_member_ref_with_origin(p_member_id, p_integration_id, p_external_ref)` —
  `integration_member_refs` is always partner-job-owned data (confirmed:
  its only caller is the member-create job processor), so its own
  `integration_id` **is** the origin; no separate parameter needed.

All three are called ONLY from the two repository functions that are
themselves partner-API-only:

- `applyPartnerAssertedConsent` (`consent-record-repository.ts`) — its own
  header already states it's "the SOLE way the partner API path may write
  consent_records." Its `'inserted'`/`'upgraded'` branches now call new
  `insertConsentRecordWithOrigin`/`upgradeToOptedInWithOrigin` functions
  instead of the plain `insertConsentRecord`/`upgradeToOptedIn`. **The
  plain functions are untouched** and still used by `join-consent.ts`,
  `prompt-marketing-optin.ts`, `confirm-marketing-optin.ts`, and
  `import-contacts-batch-row.ts` — verified by grep before touching
  anything, confirmed by the scratch-DB Assertion J below.
- `upsertIntegrationMemberRef` (`integration-member-ref-repository.ts`) —
  its own header already states its sole caller is the member-create job.
  Its body was changed in place (same exported name/signature) to call the
  RPC instead of `.upsert()`.

The three outbox trigger functions (`member_updated_outbox`,
`consent_changed_outbox`, `member_ref_outbox`, migration 071, all
`CREATE OR REPLACE`d in 073) now read `current_origin_integration_id()`
(a small helper that safely parses `current_setting('app.origin_integration_id',
true)` to a UUID, returning NULL on unset/invalid rather than throwing)
and set it on the INSERT. On the `ON CONFLICT` coalescing branch (the
5-second bucket), origin is **sticky**:
`COALESCE(integration_events.origin_integration_id, EXCLUDED.origin_integration_id)`
— a later unattributed write landing in the same window never clears an
earlier attribution, but two independent origins in the same window can't
both be recorded (documented as a real, disclosed limitation in the
partner doc's new coalescing note).

`member_updated_outbox` (the `members` table trigger) was updated
identically for consistency and to honour the dispatch's requested
scratch-DB assertion ("partner-job update → origin id set"), even though
**no current application code path performs a partner-job-attributed
`UPDATE members`** — `createOrGetMember`/`insertMember` never update an
existing member's `name`/`preferred_language`/`status`, only SELECT. The
mechanism is proven generically (Assertion H below simulates it with a
raw `SET_LOCAL`-then-`UPDATE`); the partner doc's echo-suppression note is
explicit that `name`/`language`/`status` changes are "never changed by
this API today," so those `member.updated` events stay always-NULL,
correctly.

## Mechanism Chosen (Gap B) + Why

**Postgres `integration_member_jobs` non-terminal-row count, not BullMQ's
own queue counts.** This is what the plan's own architecture text already
names ("a counter is a cache, the table is truth"), and it's the only
option with a per-integration index: BullMQ's `getWaitingCount()`/
`getDelayedCount()` (already used by the UNRELATED global ceiling guard)
have no way to filter by `job.data.integrationId` without scanning every
job, and the `integration-inbound` queue also carries `welcome-send` jobs,
which never touch this counter at all — counting BullMQ jobs by name+data
would require reconstructing exactly the filter Postgres's `status`
column already gives for free.

Two new read-only aggregate RPCs (`count_non_terminal_member_jobs_by_integration`,
`count_non_terminal_member_jobs_for_integration`) do the `GROUP BY`
server-side rather than paging thousands of job rows over PostgREST to
count them client-side.

`RateLimiterPort` gained one new method, `set(key, value): Promise<void>`
— an **absolute** overwrite, deliberately distinct from `incr`/`decr`'s
relative deltas, so ordinary request-path code (which must never risk
clobbering another request's concurrent reservation) has no reason to
ever call it. Implemented in `RedisRateLimiter` (`redis.set`), `FakeRateLimiter`
(map overwrite), and the third, previously-unnoticed implementer
`ThrowingRateLimiter` (a test helper in `integration-inbound-guard.test.ts`)
— `tsc --noEmit` caught this one immediately as a compile error, not a
runtime surprise. Two new contract-suite cases cover `set()` against both
fake and real adapters (real-Redis lane run locally, `INT001_TEST_REDIS_URL=redis://127.0.0.1:6379`,
20/20 passing).

`src/application/reconcile-integration-depth-counters.ts` (new, 106
lines) holds the actual logic: `reconcileAllIntegrationDepthCounters(rateLimiter)`
(the batch path, bounded at `DEPTH_RECONCILE_BATCH_LIMIT = 200`
integrations/tick — the plan's own ~20-integration scale note is well
inside this) and `reconcileIntegrationDepthCounter(integrationId, rateLimiter)`
(the single-integration manual-recovery path). Both take `rateLimiter` as
an explicit parameter (no default), matching `enqueue-member-create.ts`'s
own DI style for anything touching `RateLimiterPort` — deliberately NOT a
default-parameter `getInboundRateLimiter()` call, so unit tests never risk
constructing a real Redis connection by omission. `sweep-integration-queues.ts`
wires the real one in at the one call site
(`reconcileAllIntegrationDepthCounters(getInboundRateLimiter())`), added
as a fourth private step in `runMaintenanceSweep()` alongside the existing
prune/prune/anomaly steps, wrapped in the same try/warn/never-throw
pattern the other three already use. `scripts/ops/reconcile-integration-depth.ts`
(new) exposes the single-integration path as `npx tsx
scripts/ops/reconcile-integration-depth.ts <integrationId>` — the ops
playbook's manual-recovery section now points at this instead of a raw
`SELECT` + `redis-cli SET` pair.

## Scratch-DB Command + Assertions

Built on an **isolated, standalone Postgres 16.13 cluster** (Homebrew
`initdb`/`pg_ctl`, NOT the shared local Supabase instance at
`127.0.0.1:54322` other concurrent WI-11/WI-6/WI-7 sessions already
flagged as foreign-migration-lineage and password-gated) — same
WI-1/WI-7 technique, but run to completion here rather than deferred:

```bash
SCRATCH=<scratchpad>/pgscratch
initdb -D "$SCRATCH/data" -U postgres --auth=trust -E UTF8
pg_ctl -D "$SCRATCH/data" -o "-p 5544 -h 127.0.0.1" -l "$SCRATCH/server.log" start
createdb -h 127.0.0.1 -p 5544 -U postgres scratch_int001_wi13
psql -h 127.0.0.1 -p 5544 -U postgres -d scratch_int001_wi13 -v ON_ERROR_STOP=1 -f 00_stubs.sql
for f in supabase/migrations/*.sql; do
  psql -h 127.0.0.1 -p 5544 -U postgres -d scratch_int001_wi13 -v ON_ERROR_STOP=1 -f "$f"
done
psql -h 127.0.0.1 -p 5544 -U postgres -d scratch_int001_wi13 -v ON_ERROR_STOP=1 -f 10_assertions.sql
```

`00_stubs.sql`: roles `anon`/`authenticated`/`service_role` (BYPASSRLS);
`auth.uid()/role()/jwt()`; `extensions` schema + `pgcrypto`
(`extensions.gen_random_bytes`, used by migration 024);
`storage.buckets`/`storage.objects`/`storage.foldername`; the
`supabase_realtime` publication — the same shape WI-1/WI-6/WI-7 all
independently derived, re-verified here by re-grepping every migration
(001→073, not the older 001→072 list) for `auth.|storage.|extensions.|supabase_realtime|gen_random_bytes`.

**Deliberate methodology note, since it changes WI-7's own pattern**:
`10_assertions.sql` is **NOT** wrapped in one `BEGIN...ROLLBACK` — every
statement runs in its own psql-autocommitted transaction instead. First
attempt used one wrapping transaction (WI-7's exact pattern) and Assertion
H **failed**: `set_config(key, value, true)` ("SET LOCAL" semantics) is
undone only at the end of the CURRENT transaction, so wrapping every
statement in one transaction let Assertion E's origin setting leak into
Assertion H's "no session var set" check. Splitting into separate
autocommitted statements is actually the MORE faithful simulation of
production (each RPC call is its own PostgREST transaction, per the
Mechanism section above) — not a workaround, a correction. Cleanup is
`DROP DATABASE scratch_int001_wi13` (done) rather than `ROLLBACK`, since
nothing here is shared with any other session.

## Deferred / Tech Debt

- **Residual gap Gap B doesn't (and can't cheaply) close**: if BullMQ
  itself loses a job entirely (not just a worker crash — an actual Redis
  data loss with no persistence, or manual job removal) after
  `markMemberJobProcessing` set Postgres to `'processing'`, that row stays
  `'processing'` forever (nothing will ever call `completeMemberJob*` for
  it), so reconciliation will keep the Redis counter self-consistent WITH
  Postgres but Postgres itself stays permanently wrong for that one job.
  This is a different, larger problem (BullMQ↔Postgres job-status
  consistency, not a Redis-counter cache-vs-truth problem) and genuinely
  outside this dispatch's scope — flagged, not fixed.
- The coalescing-bucket stickiness rule for `origin_integration_id`
  (COALESCE keeps the FIRST non-null value in a 5s window, not a merge of
  multiple origins) is a real, disclosed simplification — documented in
  the partner doc's new coalescing note, not silently accepted as
  obviously correct.
- `member_updated_outbox`'s origin attribution is mechanically proven
  (Assertion H) but has no real application caller yet (no code path
  performs a partner-job-attributed `members` UPDATE today) — ready for
  whenever one is added, not exercised end-to-end by any current route.
