# INT-001 WI-18 — CSV merge-mode pre-check phone normalisation + stale partner-doc paragraph (backend)

Closes both items flagged in `artifacts/2026-09-10-int-001-wi17-backend`'s "Deferred /
Tech debt" section.

## Item 1 — merge-mode pre-check queried the raw, un-normalised phone

**Finding**: `import-contacts-batch-row-member.ts`'s `resolveMemberId` called
`findMemberId(supabase, restaurantId, input.row.phoneE164)` with the RAW legacy-accepted
string (`PhoneNumber.create(raw).value` — dots etc. preserved), not the normalised E.164
value `resolveLegacyMemberE164` (WI-17) produces and the create path actually stores. The
same class of bug N-9 fixed for `register-member.ts`/`register-member-web.ts`'s
pre-checks, left unfixed here.

**Verify-before-fix** (per this repo's own `principle_verify_issue_claims_before_planning`):
WI-17's deferred note called this "create a duplicate member instead of merging." Traced
the actual consequence first: `insertMember` (the seam's frozen repository function)
catches a `23505` on the real unique index (`idx_members_restaurant_phone`) and re-selects
by the RESOLVED value it was given — which `createViaSeam` already computes correctly. So
when the raw-value pre-check misses, the row falls through to the seam, the seam's own
insert collides, and the reselect finds the existing row — `resolveMemberId`'s final
*outcome* (`created: false`, correct `id`) was already right. **No literal duplicate row
was possible in production** given the unique index — WI-17's "duplicate" framing
overstated the symptom. The REAL defect: the pre-check silently relies on that downstream
collision-and-reselect as a safety net, on every merge-mode re-import of a legacy-format
phone, instead of finding the row directly — a wasted DB round trip (insert attempt +
error + reselect vs. one select) every time, and a correctness bug in its own right (the
pre-check's job is to find matches directly; that it happens to be masked by another
layer's unrelated defence is not a reason to leave it broken).

**Red**: new `import-contacts-batch-row-member.test.ts` describe block ("WI-18:
merge-mode pre-check…") — a stateful `members`-table fake (`buildStatefulMembersClient`,
tracks real insert-conflict-reselect behaviour across multiple `resolveMemberId` calls,
unlike the existing static `buildClient`) proves the create → merge-mode-reimport
sequence resolves to the SAME member (`created: false`, matching id) either way, but
counts `insertAttempts()`: **2** before the fix (one for the original create, one wasted
attempt on the "merge" that should have been a pure read), **1** after.

**Fix**: `src/application/import-contacts-batch-row-member.ts` — moved phone resolution
(`resolveLegacyMemberE164(PhoneNumber.create(...))`) out of `createViaSeam` and up into
`resolveMemberId`, resolved ONCE up front (removes a duplicate resolution + duplicate
try/catch that used to live inside `createViaSeam`, a small DRY win alongside the fix).
The merge pre-check (`findMemberId`) now queries `phoneE164.value` (the resolved,
normalised string) instead of `input.row.phoneE164` (raw). `createViaSeam` now takes the
already-resolved `E164Phone` as a parameter instead of re-deriving it.

**Green**: same describe block — `insertAttempts()` is `1` after the create, stays `1`
after the merge-mode re-import (the pre-check now finds the row directly, no seam insert
attempted at all).

**Regression guard**: new describe block ("WI-18 regression: create-mode duplicate
rejection is untouched") — a true duplicate phone in create mode (`mergeExistingMembers:
false`, which never touches `findMemberId` at all) still rejects with
`phone_already_member`, unchanged.

## Item 2 — stale partner-doc paragraph (auth-failure bucket described as IP-keyed)

**Finding**: `docs/integrations/member-api.md:425-428` still said "10 consecutive
authentication failures per `(integrationId, your IP)` per 60 seconds" — WI-14's I-2 fix
removed the IP dimension from that bucket entirely (keyed on `integrationId` alone now,
specifically because the IP visible at that point in the pipeline was a client-controlled,
spoofable header), and WI-17's N-1 added a whole new pre-auth throttle pair ahead of it
that the doc never mentioned at all.

**Fix**: cross-checked every number and keying claim against
`src/application/integration-inbound-guard.ts` directly (not against WI-14/WI-17's prose)
before writing. Rewrote the paragraph into three explicitly-numbered throttles, matching
the guard code exactly:

1. **Pre-auth, per source IP** — `preAuthBucketKey(integrationId, clientIp)`:
   `PRE_AUTH_RATE_PER_MIN` (300/min), `PRE_AUTH_BURST` (50). Named the exact trust
   mechanism (`extractTrustedClientIp`: `X-Real-IP` first, then the rightmost
   `X-Forwarded-For` hop nginx itself appends) without using the word "nginx" (this is a
   partner-facing doc; described it as "the platform's edge proxy" instead, since the
   partner doesn't configure or see that proxy — same underlying fact as the ops doc's
   nginx-specific wording).
2. **Pre-auth, integration-wide ceiling** — `preAuthCeilingBucketKey(integrationId)`:
   `PRE_AUTH_CEILING_RATE_PER_MIN` / `PRE_AUTH_CEILING_BURST` (10x bucket 1 —
   `PRE_AUTH_CEILING_MULTIPLIER`), 3,000/min burst 500.
3. **Auth-failure bucket** — `authFailureBucketKey(integrationId)`: `AUTH_FAILURE_LIMIT`
   (10) / `AUTH_FAILURE_WINDOW_SEC` (60), keyed on `integrationId` alone (WI-14 I-2) —
   explained WHY (the old per-IP key read a client-supplied header an attacker could
   rotate) rather than just asserting the new keying.

Checked `docs/integrations/member-api-ops.md` (the internal ops doc, out of this
dispatch's named file but explicitly allowed as a cross-reference) for the same staleness
— it does NOT need a correction: its Redis-key table (§4) already documents all three
buckets accurately (WI-17 updated it directly when N-1 landed). The partner doc
(`member-api.md`) was the only stale copy. Also checked `member-api.md`'s nonce/replay
paragraph (line 40, §2) against the same file's I-4 digest-based ruling — already
accurate (WI-16 must have updated it directly when that ruling landed), no change needed
there.

## Key Decisions

- **Resolved the phone ONCE in `resolveMemberId`, not twice** (pre-check + seam) — beyond
  fixing the bug, this removes a small pre-existing duplication (`createViaSeam` used to
  re-derive the same value on every call, including the ones that never needed a merge
  pre-check at all). A minor DRY improvement riding along with the fix, not scope creep —
  same function, same two call sites, no new abstraction introduced.
- **Did not add a literal Redis-key table to the partner-facing doc.** The ops doc
  (`member-api-ops.md`) already carries the literal `int001:preauth:*` / `int001:rlf:*`
  key strings for internal/ops use; the partner doc names each bucket by what it's keyed
  on and its numbers instead, which is what a partner integrating against this API
  actually needs — internal Redis key naming isn't partner-relevant and isn't documented
  elsewhere in this file for the existing `int001:rl:*` bucket either (consistency with
  the file's own existing style).
- **Used "the platform's edge proxy" rather than naming nginx** in the partner doc, since
  partners don't configure or see that layer — the underlying trust mechanism (real
  connecting IP, not a client-supplied header) is the fact that matters to them; the ops
  doc is where the literal nginx directive belongs (and already has it).
