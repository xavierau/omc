## Key Decisions

- **Signature verification stays entirely in `verify-signature-v2.ts`; the guard never sees a secret.** `guardInboundRequest` takes a pre-computed `signatureValid: boolean` instead of the integration's secret. This keeps all crypto (and the DUMMY_SECRET constant-time trick for an unknown integration) in one place, and lets the guard's steps 3–8 be tested with zero mock of `webhookSecret`/HMAC — the 18 guard tests never construct a real signature.
- **The nonce-replay mechanism (T-H2 step 8) does NOT try to cache/return a full response.** The plan's prose ("SET int001:replay:{id}:{nonce} <jobId> ... Hit → return the cached 202") implies knowing the real content-addressed `jobId` at auth time — but that's only computed after WI-3 validates the body (T-H3b explicitly assigns "record written in WI-3"). Reusing `RateLimiterPort.incrWindow(key, limit=1, windowSec=600)` gives a clean boolean "already seen this (integration, nonce) pair" signal with **zero port changes**, and is sufficient for T-H2's actual threat (a captured signed envelope being replayed) because T-H3b's own content-addressed idempotency record *already* makes a legitimate resubmission retry-safe regardless of nonce, even a genuinely new one. **Flagged for WI-3's reviewer**: `guardInboundRequest`'s decision carries `replayed: boolean` (no cached value); WI-3 decides policy per endpoint — for POST, a `replayed:true` need not special-case anything since the content-addressed `int001:idem:{jobId}` lookup independently returns the same `202` for identical bodies; for GET (naturally idempotent), a replayed nonce is likely inconsequential and can just proceed.
- **The global queue-depth ceiling (T-M7) is a generic, injectable primitive (`GlobalQueueCeilingGuard`), not wired to a real queue.** The `integration-inbound` BullMQ queue doesn't exist until WI-3 (`src/infrastructure/queue/integration-inbound-queue.ts`). WI-2 builds the cached (1s TTL), ceiling-checking logic against an injected `QueueDepthSource { getDepth(): Promise<number> }`; **WI-3 must construct one from the real queue's `getWaitingCount() + getDelayedCount()` and call `.check()` before `q.add`** — this wiring is NOT done yet and is the single most important open item for WI-3.
- **`extractIp` was reused, not reimplemented.** `src/infrastructure/supabase/audit-logger.ts` already exports `extractIp(request: Request): string` (`x-forwarded-for` → `x-real-ip` → `'unknown'`). WI-3's route should call that directly for `clientIp` rather than duplicating it.
- **Client IP threading is WI-3's job.** `guardInboundRequest`/`authenticateIntegrationV2` both take `clientIp: string` as a plain parameter rather than a `NextRequest` — kept infra-agnostic per the port-based design, and matches "no member creation" / no route ownership boundary.
- **Admin limits route validation uses 400, not the partner API's 422 field-list shape.** `SimpleErrorResponse`'s `422`-with-`fields` contract (WI-1's DTO file) is specific to the partner-facing member-creation API; this is a platform-admin-only route in the SAME family as `/api/admin/tenants/[id]/campaign-settings` (PUT), which uses a plain `400 { error: message }` — matched that precedent for consistency within the admin-route family rather than importing the partner DTO shape into an unrelated surface.
- **Bounds chosen for the three admin-settable fields** (`inboundRatePerMin` 1–6000, `inboundBurst` 1–1000, `inboundQueueCap` 1–100000) are not specified numerically anywhere in the spec/plan/threat docs beyond the *defaults* (60/20/500) — I picked generous-but-sane ceilings consistent with the load-test/perf-budget scale discussed in the plan (10k waiting jobs across ~20 integrations). **Flagged**: if the owner wants tighter admin-settable bounds, this is a one-line change to `FIELD_BOUNDS` in the route file.
- **`buildMemberJobIdFromEnv` exists but is unused by anything in this WI** — it's the real call-site wrapper for WI-3, which is the first WI with a validated body + e164 phone to actually build a job id from. Only `buildMemberJobId` (explicit-key, directly testable) is exercised by my own tests, per the frozen bullet "different `INT_JOBID_KEY` → different id."
- **base32 is a small hand-rolled RFC4648-shaped (lowercase, unpadded) encoder** inside `build-member-job-id.ts` — no `base32` npm dependency exists in the repo and the plan doesn't specify a variant; this keeps the job id URL-safe and dependency-free. If WI-11's docs need to show partners how to decode/verify job ids (they don't need to — job ids are opaque), this is the reference implementation.

## Deferred / Tech Debt

- The real `RateLimiterPort.takeToken`/`incrWindow` Lua scripts are **not** `defineCommand`-registered on the ioredis client (I call `.eval()` directly each time) — functionally identical and fully atomic, but a high-throughput future optimisation would use `defineCommand` to avoid re-sending the script body on every call (Redis caches EVAL scripts server-side by SHA, so this is a minor client-side string-transfer cost, not a correctness issue).
- No load test yet for the Lua token bucket under real concurrency (WI-11's job, per the plan).
- `GlobalQueueCeilingGuard` has no test proving its cache survives across genuinely concurrent callers (single-threaded Node makes this moot for correctness, but a note for whoever reviews the eventual WI-3 wiring).

## Env Vars Introduced (not yet in `.env.example` — that file is WI-11's per the plan)

- `INT_JOBID_KEY` — HMAC key for `buildMemberJobIdFromEnv`; no length constraint enforced (unlike `INT001_SECRET_KEY`'s 32-byte requirement), but must be set before WI-3's route can mint a real job id (throws otherwise, fail-loud, same posture as `secret-box.ts`).
- `INT001_GLOBAL_QUEUE_CEILING` — optional, default `5000`, read by `globalQueueCeilingFromEnv()`.
- `REDIS_URL` — already an existing env var (email-queue.ts precedent); `redis/connection.ts` reads it with the same default (`redis://localhost:6379`).
- `INT001_TEST_REDIS_URL` — integration-lane-only, gates the real-Redis test invocations (per WI-1's own convention).
- `INT001_DISABLE_INBOUND` is READ by `guardInboundRequest`'s caller as a plain boolean (`inboundDisabled` input) — WI-2 does not itself read `process.env` for this; WI-3's route should do `process.env.INT001_DISABLE_INBOUND === '1'` and pass the result in.
