## AC-2: ordering, scope, errors, not newly refused

**Order.** `rerun-evidence-guard.ts:31-32` reads queued, then failed, and both run before the failed-to-active CAS at `rerun/route.ts:74`.

**Can a row still slip through any ordering? No.** There are three cases:

| Row state at the queued read | Outcome |
|---|---|
| Queued with no wamid | Refused by the queued count |
| Already swept | Still `failed` at the next read, so the failed count refuses it. It has no wamid, so the webhook cannot move it (`applyStatusUpdate` looks up by wamid), and `attachKapsoMessageId` only matches `queued` |
| Inserted after the queued read | Needs a run sending while the route reads the campaign as `failed`. No path allows that |

The third case rests on the status writers. Every write of campaign status `failed` happens after that run's sends have settled, or with no run holding the campaign:

| Writer | Why no body send is in flight |
|---|---|
| `updateCampaign` in `finalizeCampaignRun` (`execute-campaign.ts:109`), `failCampaignRunIfSending` (`campaign-repository.ts:231`) | Both run after `sendInBatches`, whose sub-batches wait on `Promise.allSettled` |
| `retract_campaign_sent` (migration 064) | Flips only from `completed` |
| `markCampaignFailed` (`:293`), `restoreCampaignFailure` (`:338`) | Both are scoped to `status = 'active'`, so a run that holds `sending` cannot be failed under itself. A stalled BullMQ job's retry loses the claim while the first run holds `sending`, and that exhaustion then writes nothing |
| PATCH | Refuses `status: 'failed'` (`patch-helpers.ts`, `validatePatchStatus`) |

PostgREST here is one client and each count is its own committed read, so the queued-then-failed order holds. A read replica would break that; none is configured in `client.ts`, though the prod Supabase setup was not read.

One remaining transition is not a finding. A `sent` row that Meta rejects by webhook after the click leaves the ledger and is re-sent. Meta decided that row, which is what a re-run is for, and the guard's docstring says so.

**Scope.** I ran the real `@supabase/supabase-js` with a stub fetch. It sends HEAD with `Prefer: count=exact` and this query, after decoding:

`select=id&campaign_id=eq.c-1&restaurant_id=eq.r-1&status=eq.queued&message_type=in.(template,text)&kapso_message_id=is.null`

The column is `kapso_message_id TEXT` (`035_whatsapp_messages.sql:33`). A QR `image` row is excluded, which matches the ledger's body types.

**Query error.** A query error throws at `whatsapp-message-campaign-queries.ts:138`, and the route's `catch` answers 500. The route test covers this count: status 500, no leaked message, no guardrail call, no writes. Removing the throw fails its test.

**A failed campaign with an all-numeric history is not newly refused.** A scratch test on the real pipeline shows:
- A normal run leaves every row `sent` with a wamid. Setting those rows to numeric Meta failures gives guard null and a 200.
- A Kapso throw leaves rows `failed`, never `queued`.
- `recordOutboundSend` attaches the wamid and sets `sent` in one update, and any other outcome writes `failed`. A row stays queued with no wamid only if saving was lost or the process died.

The new check also cannot add a permanent refusal while the sweep runs. The sweep has no lower age bound, so any such row becomes `internal_orphan`, and the existing filter refuses that anyway.

**Bicho stays accepted.** A scratch test used the shape recorded in the first re-review: 250 template rows failed 131042 and 250 image rows failed 131047. The result is guard null and 200 through the route. Adding a stuck QR image row, queued with no wamid, still gives null.
