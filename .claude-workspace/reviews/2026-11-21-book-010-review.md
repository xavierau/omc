## 🟡 Important (Should Fix)

### P2-1 — Rules-refusal suggestions ignore room: dead `fits` plumbing on three surfaces

**Where.** `src/domain/services/agent-booking.ts:74-84` gained `requested.fits` in this range, but no caller passes it:
- PAP create: `src/application/booking/create-agent-booking.ts:265`;
- AI propose / create / confirm-change: `src/application/agent/agent-booking-rules.ts:54-55` (`parseWith`);
- PAP code step reply: `src/domain/services/agent-booking-recheck.ts:30-31`, reaching the diner through `recheck-agent-bookings.ts:72` `timeUnavailableText`.

**Problem.** A request that the booking hours refuse gets "bookable" alternatives that are rules-only. Under BOOK-010 those can be full or stopped times.

**Failing scenario (PAP / AI).**
- Setup: limits 30 per slot. Sat 2026-11-28 19:00 has 30 guests. Fri 2026-11-27 is a closed special date.
- A personal agent POSTs Fri 19:00 for a party of 4. It gets 400 `closed_day` with `suggested_times` starting `2026-11-28 19:00`, which is full.
- The agent retries that time and gets `full`.
- On the AI channel, the model is told by `SUGGESTED_NOTE` to "offer these suggestedTimes", so it proposes a full time to the diner.

**Failing scenario (code step).** The same shape reaches the diner as free text: "仍可預訂：…" in `timeUnavailableText`. I-010 saw this shape in `tests/evidence/2026-11-21-book-010-i/pap-code-step.log` case B, harmless only because 12-02 had room there.

**Risk.** It contradicts spec AC-4's "suggested_times that fit the party" and BOOK-009 AC-12's "bookable alternatives". The diner gets wrong information in a WhatsApp message, plus extra agent round-trips. No data is corrupted, so P2 rather than P1.

**Fix.** When `roomApplies`, build `fits` once with `fitsInRange(reader, ctx, {from: max(date, today), to: windowEnd}, partySize)` (or `fitsFor` over a `readRoom`) and pass it as `requested.fits` at all three call sites. The AI path has `call.booking.room`, PAP create has `deps.room`, and the code step has `deps.room.reader` (recheck runs before promote, so it reads once per message).

**How to show it fails.** In `create-agent-booking` tests, use `world.room` counts `{ '2026-11-28': { '19:00': 30 } }` with `limits.perSlot = 30` and a closed special date 2026-11-27, then POST 2026-11-27 19:00 party 4. Expect `suggestedTimes` not to contain `{date:'2026-11-28', time:'19:00'}`; today it does. Add the same for `propose_booking` and for `recheckAgentBooking`.

## 🟢 Minor (Optional)

### P3-1 — A refusal reads the whole booking window twice

`src/application/booking/booking-room-check.ts:51-54` → `:46-47` → `:39-40`. `earlyFull` reads `readRoom` for today..window end (≤ 91 days, a counts RPC plus a stops select). On refusal, `fittingSuggestions` reads the same window again. That misses the plan budget "BOOK-010 count = one grouped query per request" on every `full` answer (page, PAP, AI propose).
- **Show:** a spy on `readRoom` in `earlyFull` on a full slot counts 2 calls.
- **Fix:** pass the state already read into `fullWith`/`fittingSuggestions`. The `insertWithRoom` path legitimately reads once after the RPC.

### P3-2 — Period stops are keyed by label: a rename silently lifts the stop, and it cannot be removed

`booking-room.ts:81` (`periodKey`), `application/booking/booking-capacity.ts:82-85`.
- **Scenario:** staff stop 晚市 on 2026-11-22, then an admin renames the period to 晚餐.
- **Result:** `roomFor` no longer matches the stored `period_label`, so diners and agents can book dinner on 11-22. `DELETE /stops {scope:'period', periodLabel:'晚市'}` answers 400 `unknown_period`, so the orphaned row stays. An interval change does the same to slot stops.
- **Status:** the spec doesn't cover hours edits after a stop.
- **Fix:** warn on the settings save when future stops reference a key that disappears (or carry them over), and let DELETE remove any stored stop for the tenant without validating it against the current hours.

### P3-3 — A repeated stop POST reports the caller as the stopper, not the stored stop

`application/booking/booking-capacity.ts:118-121` with `booking-room-repository.ts:80`.
- **Scenario:** Amy stops 19:00 at 14:02, then Ben POSTs the same stop at 14:10. Ben's response says `stoppedBy: 'ben', stoppedAt: 14:10`, while the row says amy · 14:02.
- **Impact:** the UI reloads after success, so the screen corrects itself; the API response is wrong.
- **Fix:** on 23505, select and return the stored row.

### P3-4 — SECURITY DEFINER functions set `search_path = public` without `pg_temp` last

`092:176` and `092:256`. Unqualified `booking_requests` / `booking_stops` can resolve to a same-named temp table in the calling session first.
- **Exposure:** EXECUTE is granted to `service_role` only (verified), so this is not reachable from anon or authenticated.
- **Fix (hardening):** `SET search_path = public, pg_temp`, per the Postgres guidance for SECURITY DEFINER.

### P3-5 — Staff "已滿" month badge and the diner's day state differ today

`domain/services/booking-capacity.ts:121-127` uses every grid slot (`periodSlotTimes`), including past slots and slots inside the notice period. The diner and `/availability` use `slotsFor` (`slot-picker-model.ts:34-38`, `get-agent-availability.ts:106`).
- **Scenario:** today at 20:00 Hong Kong time, 2 h notice, lunch slots empty, every dinner slot from 22:00 full. The diner and agents see the day as 已滿 / `open:false`, but the staff cell shows no badge.
- **Impact:** today's date only.
- **Fix:** for `date === today`, judge the staff badge over `slotsFor(hours, date, clock)`, or document that the staff badge is capacity-only.

## ✅ Strengths

- **The atomic step is right.** A transaction-scoped advisory lock per (restaurant, date) is shared by inserts and promotions. Each holds under real concurrency: insert vs insert (committed test), insert vs promotion in both orders, and same-transaction multi-candidate promotion (probes P1 and P2).
- **The dynamic insert is safe.** It refuses unknown keys before building SQL, binds values, and keeps one shared row builder (`bookingInsertRow`). A schema-contract test pins the allow-list to it.
- **One gate, one rule.** `roomApplies` is the single switch. `roomFor`/`fitsFor` is the single rule behind the page, PAP, AI, staff and availability. The diner page only compares a server-computed number, so it cannot disagree with the server's counting.
- **The token survives a refusal.** The page token is released on a database refusal and on any throw. The early check runs before the claim.
- **The code-step full path is clean.** `declined` `full` with `decided_by` null; staff never see it as a request; the free-form reply is best effort and never undoes the decline.
- **Authorization is scoped in the query.** Stop/capacity authz is role plus session tenant, filtered inside every query (`principle_authorize_by_scoped_query`), with RLS on and no policies.
- **Real-database evidence exists.** Scratch Postgres plus a real PostgREST smoke (`ac3-race.log`, `ac3-postgrest.log`), as the spec's risk section required.

## Open Questions

1. **Postgres version:** `UNIQUE NULLS NOT DISTINCT` (`092:33`) needs Postgres 15+. `supabase/config.toml` says 17 and the scratch image is 17.6, but the version on the DEV and prod projects is unconfirmed (looked in: config.toml, scratch-db.sh). 092 is the first migration using it.
2. **Perf budget:** "Diner page TTFB unchanged ±100 ms" was not measured. BOOK-010 adds `readRoom` (counts RPC plus stops select over up to 91 days) and the `slotRoomOf` compute to every booking-page render (`resolve-booking-link.ts:144-155`). It is probably small, but no evidence was found in the I-010 walk.
3. **Deploy order:** with code deployed before 092, any tenant whose schedule switch is on breaks everywhere:
   - page submit returns `failed`;
   - the AI create tools throw;
   - `/availability` and the stops/capacity APIs return 500.
   The handoff says "091 then 092 before any deploy". The release runbook should make that a hard precondition.
4. **Product: change requests counted conservatively.** A new change request is checked with its original still counted (spec S1). So a diner at a full slot cannot raise the party by one, or move within a full meal, even when the net change fits. This conforms to the spec, but the product call is worth confirming.
5. **Stop timing:** a stop added while a request's RPC is already past its stop check does not refuse that request. This satisfies "from the next request on" (AC-8); noted only.
