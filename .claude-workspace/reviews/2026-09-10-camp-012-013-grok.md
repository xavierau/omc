## 🟡 Important (Should Fix)

### I-1 — `src/application/__tests__/resolve-campaign-members.test.ts:441` (also :411, :426)

**Problem.** Three rewritten tests assert properties the mock cannot see, so the #162 checklist items
they stand in for are not actually tested in CI.

1. `'cross-tenant scoping'` (line 411) only checks the TS caller passes `p_restaurant_id='r-1'`; a
   poisoned `member_tags.restaurant_id` is never inserted. The comment defers that proof to
   "migration 079 + the scratch-DB run", but no scratch-DB/SQL test for 078/079 is in the repo
   (unlike INT-001). The 079 contract test is a regex over the same file the implementer wrote —
   valuable where it compares two independent sources (079 WHERE vs 067 WHERE, `RETURNS TABLE` vs
   `MEMBER_COLUMNS`), not where it greps its own REVOKE strings.
2. `'yields one recipient per member'` (line 426) feeds `pagingRpc` a single pre-deduped row, so
   `DISTINCT ON` is not exercised; only "one RPC with both tag ids" is real.
3. `'returns no unsubscribed member (status filtered server-side)'` (line 441) mocks an empty RPC
   result and expects `[]` — that passes even if the SQL dropped the status predicate.

**Risk.** A later migration edit that keeps the substrings `m.restaurant_id = p_restaurant_id` /
`m.status = 'active'` / `DISTINCT ON (m.id)` but changes join/boolean structure (e.g. OR-ing a
predicate, dropping `mt.restaurant_id`, `DISTINCT ON` a different column) still satisfies the
contract regex and all three unit tests, then a tag send can double-message or leak a cross-tenant
member. The production SQL in 079 is currently correct; this is a false-green regression hole on the
exact isolation/dedup/status ACs.

**Fix.** Commit a scratch-DB (or supabase test) that: inserts tenant A/B, a `member_tags` row with
`restaurant_id=A` and `member.restaurant_id=B`, asserts `active_members_by_tags(A, ...)` returns 0;
inserts one member with two selected tags, asserts the RPC returns one row; inserts an unsubscribed
tagged member, asserts 0 rows. Rewrite the three unit tests so they only claim what the mock proves
(caller passes `p_restaurant_id` / both tag ids in one call / empty RPC → `[]`). Keep the 067 WHERE
and `MEMBER_COLUMNS` parity tests — those are real two-source contracts.

## ✅ Checked and found sound

Migration 078 (#161):
- **Q1(a) ON CONFLICT vs hand-tuned row.** `ON CONFLICT (restaurant_id) DO NOTHING` on both the
  trigger INSERT and the backfill INSERT never updates an existing row, so Kushiro's hand-tuned
  `monthly_send_limit=10000` is not overwritten and `updated_at` is not bumped (the `updated_at`
  trigger in 016 is BEFORE UPDATE only). If no row exists, backfill creates one from
  `restaurants.plan`.
- **Q1(b) RLS interaction / plain-plpgsql trigger.** `tenant_campaign_settings` INSERT policy is
  `WITH CHECK (is_platform_admin())`. The trigger is plain plpgsql (NOT SECURITY DEFINER), matching
  077 exactly. `createRestaurant` → `createServerSupabaseClient` uses `SUPABASE_SERVICE_ROLE_KEY`
  (BYPASSRLS). `create-tenant.ts` is the only app inserter. `scripts/seed-demo-data.ts` upserts as
  service_role. No SQL `INSERT INTO restaurants` in `supabase/`. `restaurants_insert` is
  `is_platform_admin()`, and `campaign_settings_insert` is the same, so a platform-admin JWT INSERT
  also satisfies the settings policy. Invoker is the right choice: making it SECURITY DEFINER would
  introduce the CVE-class mutable `search_path` issue that 045/033 pin with
  `SET search_path = public, pg_temp`; 077 also omits that pin because it is not DEFINER.
  Documented residual: a future non-admin INSERT path would fail the trigger and roll back the
  restaurant row (fail-closed).
- **Q1(c) ELSE branch.** `CASE p_plan WHEN 'starter'/'growth'/'pro' ELSE 1000`: a NULL plan matches
  no WHEN (`NULL = text` is unknown) and takes ELSE 1000. `restaurants.plan` is NOT NULL DEFAULT
  'starter' with CHECK (starter, growth, pro) (017), so NULL/unknown is unreachable from the table.
  ELSE = starter is fail-safe and matches `planCampaignQuota` via the 078 contract test.
- **Q1(d) re-runnability.** No `DROP TRIGGER IF EXISTS`; `CREATE TRIGGER` is not idempotent on a raw
  re-run of the file. `supabase db push --linked --include-all` applies pending migrations not
  already in `supabase_migrations.schema_migrations` (deploy/README.md), and each file runs in a
  transaction, so a failed apply rolls back. 077 made the same choice. 047/035 use
  `DROP TRIGGER IF EXISTS` only when replacing an existing trigger.

Migration 079 (#162):
- **Q2(a) cross-tenant predicates.** Tags RPC: `mt.restaurant_id = p_restaurant_id AND
  m.restaurant_id = p_restaurant_id` (parallel to 067). Selection RPC: `campaign_members` has no
  `restaurant_id` (015 PK is `(campaign_id, member_id)`); scopes via `c.restaurant_id =
  p_restaurant_id AND m.restaurant_id = p_restaurant_id`. A poisoned `campaign_members` row linking
  a foreign member cannot pass both.
- **Q2(b) DISTINCT ON + paging.** `DISTINCT ON` is applied before LIMIT/OFFSET; `ORDER BY m.id`
  matches `DISTINCT ON (m.id)` and is a unique total order, so pages are stable and a member cannot
  appear twice or be skipped by the DISTINCT. Concurrent inserts between pages can shift OFFSET
  (inherent); same class as the old `.range()` walk.
- **Q2(c) `status='active'` semantics.** `members.status` CHECK is `('active','unsubscribed')` in
  001; no later migration widens it; the column is NOT NULL. The RPC's `m.status='active'` ≡
  `execute-campaign.ts`'s `filter(status !== 'unsubscribed')`. The old tag path already filtered
  active; the old selected path deferred to `:47`. D4 is observationally equivalent and ships less
  unsubscribed PII to the worker.
- **Q2(d) STABLE / SECURITY INVOKER.** `LANGUAGE sql STABLE`, default SECURITY INVOKER.
  `members` / `member_tags` / `campaigns` have RLS; service_role bypasses it, so the worker sees all
  rows. A future non-service caller with EXECUTE would get an RLS-filtered empty set rather than an
  error — but EXECUTE is revoked, so PostgREST returns a permission error, not empty. INVOKER is
  correct (DEFINER would be the leak).
- **Q2(e) REVOKE/GRANT signature completeness.** Postgres stores ONE `pg_proc` row for a function
  with defaults; the signatures are `(uuid, uuid[], int, int)` and `(uuid, uuid, int, int)`. The
  REVOKE/GRANT statements name those exact types (`int` ≡ `integer`). There is no 2-arg overload to
  miss. Matches 067/064 style.
- **Q2(f) `p_limit NULL` vs PostgREST max-rows.** `LIMIT NULL` in Postgres means no SQL limit;
  PostgREST `max-rows` would then truncate the HTTP body. The only TS callers always pass
  `p_limit: to - from + 1` (1000). No caller passes NULL.

Application layer:
- **Q3(a) `resolveSettings` fallback.** `getRestaurantPlan` throw is not caught →
  `checkCampaignGuardrails` rejects (fail-closed, A6). `console.warn` fires once per
  `resolveSettings`/`planDerivedDefaults` invocation. Missing restaurant → `null ?? 'starter'`
  (conservative 1000). Other `DEFAULT_SETTINGS` fields (`dailyCampaignLimit=1`, etc.) stay;
  `PLAN_QUOTAS` only defines `monthly_send_limit` — acceptable for a missing-row degradation that
  also warns.
- **Q3(b) `>=` → `>` knock-on.** `checkMonthlyLimit` now allows `sends + target == limit` (D2).
  `isApproachingLimit` is unchanged (`currentMonthSends/limit >= 0.8`, target not included) —
  pre-existing. At 800/1000 a 200-send campaign is now allowed AND warned (was blocked by `>=`); at
  1000/1000 `target=0` (cron) is allowed with a warning; `target>0` is blocked.
  `enforce-campaign-guardrails` throws on violations before logging warnings. No warning/block
  contradiction. The admin campaign-settings route duplicates the 0.8 ratio independently and was
  not required to change.
- **Q3(c) `readAllPages` against a set-returning RPC.** `readAllPages` stops only on an empty page
  and advances `from += page.length`. If `max-rows < p_limit`, the client receives a prefix of the
  ordered RPC result and the next OFFSET continues from there — no gap, no duplicate. An RPC error is
  thrown as `` `${label}: ${error.message}` `` (covered by the B7 tests).

Domain alignment and security:
- **Q4 #161 delivered**: idempotent backfill, AFTER INSERT seed, plan-derived fallback, warn on
  fallback, inclusive limit. **Q4 #162 delivered in product code**: one RPC per page, no member UUID
  in the request, paging past 1000, WHERE parity with 067, both `restaurant_id` predicates,
  `DISTINCT ON`, `fetchSelectedMembers` converted, `MEMBER_ID_CHUNK_SIZE`/`chunk`/
  `fetchTaggedMemberIds`/`fetchMembersByIds` gone, tests rewritten not deleted, REVOKE
  PUBLIC/anon/authenticated + GRANT service_role. The cross-tenant/status/dedup ACs are implemented
  in SQL but not behaviourally tested (see Important I-1).
- **Q5 no new cross-tenant enumeration.** A dashboard anon/authenticated session cannot EXECUTE
  either RPC (REVOKE on the exact 4-arg signatures; the default PUBLIC execute is removed). Even if
  EXECUTE leaked, INVOKER + RLS on `members`/`campaigns` would not return another tenant's rows
  (empty, not a leak). `p_restaurant_id` in TS comes from `executeCampaign`'s worker `restaurantId`
  (a service-role job); `resolveTargetMembers` is not called from any API route. Passing a mismatched
  `(campaignId, restaurantId)` pair yields an empty set, not a cross-tenant dump.
- **Architecture.** `getRestaurantPlan` lives in `restaurant-repository.ts` (reads
  `restaurants.plan`); `domain/campaign-guardrails.ts` and `tenant-plan.ts` import nothing from
  infrastructure. The application layer already imported infra repos; no new layer violation.
- **Absence pass (Integration Map).** I-1..I-11 present. I-12 verified: no `src/app/api/**` caller of
  the old `.in('id')` helpers; `create-tenant`/`createRestaurant` covered by the trigger;
  `seed-demo-data` service-role upsert covered on first INSERT; no generated `Database['Functions']`
  types to update; `tag-audience-repository` correctly still calls `count_active_members_by_tags`;
  `deploy.sh` already runs `supabase db push --linked --include-all`.
