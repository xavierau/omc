## 🟡 Important (Should Fix)

### P2-1: Terms, info or any window option, saved without weekly periods, closes booking on every channel, and the UI cannot undo it
- **Where:** `src/hooks/use-booking-settings.ts:88-92` (`hoursPayload` never returns `null`, and sends the object as soon as anything differs from `EMPTY_BOOKING_HOURS` or hours were ever stored); `src/domain/value-objects/booking-hours.ts:40-51` (terms and info are fields of `BookingHours`, plan D1); `src/application/booking/resolve-booking-link.ts:103` (hours set + no bookable time → off page).
- **Problem:** Spec S1 presents terms (block 7) and restaurant info (block 8) as blocks of their own, and AC-5 makes hours opt-in. Because they are fields of `bookingHours`, an admin at a tenant with no hours who types only an address, only terms, or only changes the table time saves a `bookingHours` with every weekday `[]`. From then on:
  - the diner page renders the off page;
  - PAP refuses every date (`closed_day`) and `/availability` shows every date closed;
  - the AI agent's summary reads "目前沒有可訂座時間" and its tools refuse.
  Clearing the field and saving again does not revert: `hoursConfigured` is now true (after reload), so the form sends `EMPTY_BOOKING_HOURS`, not `null`. Nothing in the settings UI sends `null`, the only way back to BOOK-001 "any time".
- **Failing scenario:** probe `parseBookingSubmission({...body, acceptTerms:true}, bookingRulesAt(now,{maxPartySize:8,bookingHours:{...EMPTY_BOOKING_HOURS, terms:{zh_hk:'',en:'No pets'}}}))` → `{"ok":false,"errors":{"date":"closed_day"}}`. In the UI: Settings → Booking (Simple, no hours), type an address, Save, open `/b/<token>` → off page. Delete the address, Save, reload `/b/<token>` → still off.
- **Risk:** A live tenant (Bicho / omc pilot) loses page, PAP and AI booking entirely after a harmless-looking edit, with no self-service undo. The `booking-settings-hours-warning` line is the only signal. The spec's warning row allows the save, but it does not cover terms-only or info-only intent.
- **Fix (pick one, owner call):** (a) add a "Use booking hours" switch whose off state sends `bookingHours: null`, and show terms/info only when it is on; or (b) treat a value with no periods on any weekday and no special periods as `null` in `hoursPayload`, and say on the form that terms/info need hours. (b) loses terms-only, which today closes booking anyway.

### P2-2: The PAP confirm-code step promotes without re-checking hours or terms; the AI path re-checks at agreement
- **Where:** `src/application/booking/verify-agent-booking.ts:76-90` (`promote` with no `parseBookingSubmission`) and `:49-51` (reply falls back to current terms).
- **Problem:** The brief lists the PAP confirm-code step as a booking channel. `createBookingRequest` and `confirmChange` re-parse the stored proposal at the diner's agreement (`agent-booking-tools.ts:142`, "Re-checked now … left the hours"). The PAP flow checks only at POST. Up to `AGENT_VERIFY_TTL_MS` (30 min, `booking-request.ts:33`) can pass before the diner sends the code, and `promote` turns `unverified` into `pending` regardless.
- **Failing scenario:**
  - Notice 2 h. An agent POSTs at 17:00 HK for 19:00 → 202. The diner sends the code at 17:25 → the booking is promoted to `pending` 1 h 35 min ahead (`checkSlot` would now say `too_soon`).
  - Same if the admin closes that day between POST and code.
  - Terms: a tenant with no terms; agent POST → row with `terms_text` null. The admin adds terms; the diner confirms → `pending` booking with no acceptance stored, and `confirmedText` appends the current terms (`booking.termsText ?? termsSnapshot(...)`, line 50), as if they applied.
- **Risk:** Not exploitable by an agent (POST is checked) and staff still decide. But the rules bind PAP less strictly than AI chat, and the staff "Terms accepted" record can disagree with what the diner was told. BOOK-010 D4 already plans to route the code step through `insert_booking_request_if_room`, which makes it a natural place to close this.
- **Fix:** In `verifyAgentBooking`, before `promote`, re-run `checkSlot` (via `bookingRulesAt(now, config)`) on each candidate's date/time and leave a refused one unverified, or promote and tell the diner the time is no longer available. Append terms only when `booking.termsText` is set. Or record an owner ruling that the code step is exempt (then the spec Explicitly Not Handled list needs the line).

## 🟢 Minor (Optional)

### P3-1: `mapUrl` is not re-validated when the stored blob is resolved (BOOK-001 R14 precedent)
- `src/domain/value-objects/booking-hours.ts:144` keeps any string ≤ 2,048, and `src/components/booking/restaurant-info.tsx:28` renders it as `href`. `externalUrl` is re-checked at read with `isSafeHttpsUrl` (`booking-config.ts:181`).
- Probe: `resolveBookingHours({weekly:{}, info:{mapUrl:'javascript:alert(1)'}}).info.mapUrl` → `'javascript:alert(1)'`.
- Only reachable by writing `booking_config` outside the validated PUT, so it is defence in depth.
- Fix: `mapUrl: isSafeHttpsUrl(m) ? m : ''` in `resolveInfo`.

### P3-2: Page and PAP store the terms text current at submit, not the text the diner was shown
- `submit-booking-request.ts:82-85` and `create-agent-booking.ts:197-200` snapshot `config.bookingHours` at submit.
- If the admin edits terms between page load (or the agent's OpenAPI / `/availability` read) and submit, the stored "exact text accepted" (AC-10) is text the diner never saw. The AI path guards this with `terms_changed`.
- Fix: the page / agent sends a terms hash (or the text) and the server refuses `terms_changed` on mismatch, like the AI path.
- Narrow race; spec Explicitly Not Handled covers re-acceptance only for edits after a booking.

### P3-3: Terms switched on mid-form → silent refusal on the page
- If terms become required after the page loaded (no `TermsBlock`, `termsRequired` false), the server answers `acceptTerms: terms_required`.
- `timesChanged` ignores that code (`slot-picker-model.ts:93`), so there is no refresh. `TermsBlock` is not rendered, so the error has nowhere to show (`booking-slot-form.tsx:85`), and `BookingFormNotice` ignores `fields` (`booking-form.tsx:39`). The diner taps submit and nothing visible happens.
- The BOOK-001 form has the same gap when hours are switched on mid-form (date/time codes it cannot recover from).
- Fix: add `terms_required` to the refresh set (a refresh brings the terms block), or show unplaced field errors in the notice.

### P3-4: `/availability` query edges
- `get-agent-availability.ts:73` puts no upper bound on `from`. Probe: `from=9999-12-31&days=3` (hours null) → dates `"9999-12-31"`, `"+010000-01"`, `"+010000-01"` (`addDays` past year 9999).
- `agent-booking.ts:94-95` caps `days` at `aheadDays`, but the window is `aheadDays + 1` dates (today … today+aheadDays, `booking-hours.ts:44-46`). Probe: aheadDays 7, `days=8` → `too_large`, so one call cannot cover the window. Spec AC-11 says "N ≤ window".
- The 404 gate omits POST's "no confirmable WhatsApp number" check (`create-agent-booking.ts:226`). The two conditions spec AC-11 names (agent booking off, unknown publicId) do match.
- Fix: refuse `from > today + max(aheadDays, 90)`, and use `aheadDays + 1` in the cap.

### P3-5: The settings summary lists special dates outside the window; agents do not
- `settings/booking/route.ts:41-46` uses `summarize` on all future special dates. The OpenAPI and AI use `summarizeForAgents` (window-filtered, `agent-booking.ts:86-90`).
- Spec S1.9: "the admin reads exactly what the agents get". A special date 60 days out with aheadDays 30 shows in settings but not to agents.
- Fix: use `summarizeForAgents` in `hoursView`.

### P3-6: Release-order hazard: 091 must be applied before this code is deployed, or every tenant's PAP POST and staff list fail
- `AGENT_BOOKING_COLUMNS` (`agent-booking-repository.ts:27-28`) and `STAFF_COLUMNS` (`booking-request-repository.ts:41`) select `terms_accepted_at, terms_text` unconditionally, hours-null tenants included.
- Deploying before the migration → PostgREST 42703 on `insertAgentBooking` / `promoteAgentBooking` / staff lists.
- Documented in the migration header and all three handoffs, but no mechanical gate.
- Fix: release checklist / deploy record step "apply 091 to whatsapp-crm-pro first" (repo memory `incident_int001_fakes_hid_schema_mismatch`).

## ✅ Strengths
- **One rule engine.** `slotsFor` / `checkSlot` are pure and shared by the server parser, the diner calendar (`slot-picker-model.ts`), `/availability` and the suggestions, so the page cannot offer a slot the server refuses at the same clock.
- **Opt-in default holds.** `bookingRulesAt` accepts a bare number for old callers, but every production caller now passes the config (grep).
- **Error mapping.** Per-path errors (`bookingHours.weekly.wed.0`, `special.<date>`) map one-to-one to UI rows (`hours-errors.ts`).
- **AI agreement re-check.** At the diner's agreement the AI path re-checks both the slot and the terms text (`parseAgreed`); this is stricter than the spec asks.
- **Additive storage.** Inserts write 091's columns only when terms were accepted, and the CHECK constraint enforces "both or neither".
- **Hours-null proofs.** Hours-null byte-identity is pinned by fixtures (OpenAPI, system instruction, BOOK-001 submission table).

## Open Questions

2. **P2-2, confirm step.** Should the PAP confirm-code step be exempt from hours and terms (staff decide anyway)? If yes, add it to the spec's Explicitly Not Handled.
3. **Times-changed recovery.** After a refusal, the page keeps the now-closed date selected (I-009 review_focus). This review did not judge the UX (not in the focus list).
4. **AI model behaviour.** Behaviour under the new BOOKING RULES section is untested (no eval runner, W4/I-009 unverified). Spec Dependencies asks for a shadow run on omc before a live tenant switches on.
