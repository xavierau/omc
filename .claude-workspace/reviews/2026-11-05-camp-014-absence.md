# Code Review: CAMP-014 failed-campaign reason, re-run and QR visibility (99c1f6b3..1a9e1da5)

## Summary

The nine plan items and the wiring are all present, reachable and tested. Tenant isolation holds. The reason text is correct and fits its budget.

One blocker: plan item 4 refuses re-run when delivery is unknown, but the most dangerous unknown case is recorded as an ordinary failure. A Kapso network error or timeout marks the row `failed`, the run reads "All N message sends failed", re-run is offered, and the ledger re-sends to those members. The cases `rerunBlock` does refuse (`errored` members) are the ones the ledger already protects.

Seven important findings cover the tracking kill switch, an unrefused unknown path, the 500 after the compare-and-set, a warning that blames Meta for our storage failure, a list API with no time bound, a re-run after coupon expiry that reads as success, and a QR warning that cannot be acted on from a failed card.

Checked at HEAD `1a9e1da5` by reading the code. The 13 touched test files pass (302 tests). No browser, prod or live Meta run, and the finding chains were traced by reading, not executed.

## 🔴 Critical (Must Fix)

**C1. A send whose outcome is unknown is recorded as failed, so re-run re-sends it.**

Files:
- `src/infrastructure/kapso/template-client.ts:306-313,319-327`
- `src/infrastructure/kapso/client.ts:26-34`
- `src/application/record-outbound-send.ts:77-80`
- `src/application/execute-campaign-broadcast.ts:168-171`
- `src/domain/services/campaign-rerun.ts:20`

Problem: the sender catches every exception from the Kapso call, including network resets and timeouts, and returns `ok:false, kapso_send_error`. A 2xx response with no message id returns `kapso_no_message_id`. Both mark the row `failed` and throw `SendFailedError`, so the tally counts `failed`, not `errored`. The run then stores "All N message sends failed", which `isDeliveryUnknownReason` does not match. The ledger skips only non-failed rows, so those members are sent again.

Risk: a Kapso incident returns a gateway timeout after the request reached Meta. Customers received the message, the card says all failed, and the tenant fixes nothing and clicks re-run. Up to the whole audience gets a duplicate marketing message, and the confirmation sheet has just told the tenant that customers who already received it are skipped. Eager coupons are minted only after a success, so a first-run code in a delivered message was never minted, and the re-run sends a different code.

Before CAMP-014 this needed an operator PATCH, so this diff is what makes it a tenant action. The ledger comment states the same policy for `queued`: "delivery is unknown, and a duplicate marketing blast is the worse error".

Likelihood is low and impact is high. That Kapso forwarded a timed-out request cannot be observed from this repo, which is what "unknown" means here.

Fix:
1. Mark the outcome as unknown for any error that is not a definite HTTP 4xx, meaning non-`GraphApiError` exceptions, 5xx responses and `kapso_no_message_id`. The SDK types expose `GraphApiError.httpStatus`; how it reports network errors is (unconfirmed — looked in: `dist/index.d.cts` only).
2. In `invokeAndPersist`, leave that row `queued` so the ledger counts it, and throw something other than `SendFailedError` so the tally records `errored`.
3. The existing delivery-unknown wording and refusal then apply.

How to show it fails: make `client.messages.sendTemplate` reject with `TypeError('fetch failed')` for every member and run `executeCampaign`. The stored reason passes `rerunBlock` as `null`, and a second run calls `sendTemplate` again for every member. Expected: the reason satisfies `isDeliveryUnknownReason`, and the second run sends nothing.

## 🟡 Important (Should Fix)

**I1. Re-run ignores the tracking kill switch.** `rerun/route.ts:44-59`, `execute-campaign-rerun-prefetch.ts:35-37`, `execute-campaign.test.ts:1939`.

With `WAQ_TRACK_MESSAGES=0` the ledger is an empty set, so a re-run re-sends to the whole audience, while `rerunConfirmBody` (`en.json:251`) says customers who received it are skipped. A run that failed through `markCampaignFailed` after partial sends then double-sends for real.

Fix: refuse in the route when `!isMessageTrackingEnabled()`.
Show it: set the flag to `0`, call `/rerun` on a failed campaign. Today it answers queued.

**I2. A run with `errored` members can still be re-run and reads "rejected every message".** `execute-campaign.ts:119-120,133-141`.

Plan item 4 refuses delivery unknown, but `failRunRetractedByMeta` never sees `counters.errored`. The ledger prevents the double send, so this is a refusal and wording gap, not a duplicate. The retract RPC path has the same gap and cannot be fixed without persisting the count.

Fix: pass `counters` in, and use `deliveryUnknownReason` when `errored > 0`.
Show it: counters `{sent: 1, errored: 2}`, `completeCampaignRunIfCounted` false, latest failure 131042. Today the stored reason says "re-run the campaign".

**I3. A failure after the CAS tells the tenant it failed, then customers are messaged anyway.** `rerun/route.ts:52-60`, `campaign-card.tsx:40-42`.

Scenario: Redis is down when the job is added, on a campaign with a past `scheduled_at`. The route answers 500 "Failed to queue campaign". The campaign is already `active` with its reason erased, and the lease was taken, so the cron enqueues it about 5 minutes later and it sends with no further action.

The card does not refetch on error, so it still shows Re-run. Clicking it answers 400 "Only a failed campaign can be re-run". The dev raised this in `review_focus`; it is not among the brief's ruled items.

Fix: on a lease or job error, CAS `active -> failed` back with the original reason, then answer 500. Also refetch on any non-OK response.
Show it: make `addCampaignJob` reject, then assert the row is still `failed` with its reason. `route.test.ts:189` pins only the 500.

**I4. The QR failure warning blames Meta for OhMyClient's own failure.** `en.json:254`, `zh-HK.json:254`, `campaign-card-view.tsx:103`, `execute-campaign-send.ts:81-84`.

Item 8 now records upload failures in the same count item 7 displays. A Supabase Storage outage writes `send_threw` image rows, and the card says "WhatsApp (Meta) did not deliver 30 coupon QR images". This breaks the repo's rule that an error names the deciding system (WAQ-014).

Fix: neutral wording, for example "30 coupon QR images could not be delivered. Those customers did not receive their code." Same in zh-HK.
Show it: `uploadCouponQr` rejects on a counted campaign. The row is `send_threw`, and the warning still names Meta.

**I5. The list API has no time bound on the count.** `build-campaign-qr-states.ts:37-47`, `with-qr-status.ts:33-42`, `src/infrastructure/supabase/client.ts:11-16`.

The count runs for every campaign with counted sends, for the tenant's whole history, in sequential batches of 10. It also runs for campaigns with no `couponConfig`, which can never have a QR image. `Promise.all` waits for all of it and the client has no fetch timeout, so one hung count hangs the list; degrading covers errors only. The template read also duplicates the one in `safeCampaignTemplateReviewStates`.

Unmeasured, so at most 🟡: no prod timing or per-tenant campaign count was available.

Fix: filter to `c.couponConfig`, and race the enrichment against a short budget that degrades off.

**I6. A re-run after the coupon expiry reads as success with nobody reached.** `execute-campaign-broadcast.ts:97-104`, `execute-campaign.ts:115-117`.

Eager re-run: the member's coupon has expired, so the outcome is `skipped_already_sent` even though the first send was rejected. With all members skipped, the run becomes `completed` with no reason, and the failure banner disappears. Bicho's 250 coupons expire 2027-01-03, and clearing a Meta restriction can take time. The investigation says this kind of outcome must not read as clean success.

Fix: tally dead-coupon skips separately, and when they are the whole audience fail with a reason that says to create a new campaign.
Show it: all members hold expired coupons with failed body rows. `executeCampaign` writes `completed`.

**I7. On a failed card the QR-only warning cannot be followed, and the last step omits it.** `en.json:253`, `campaign-card-view.tsx:68,105`, `rerun-campaign-dialog.tsx:25`.

Bicho's own card after this fix shows:
- Banner: "Clear the restriction..., then re-run the campaign."
- Warning: "Use a template with a quick-reply (claim) button instead."

Plan item 2 rests on failed cards being unable to change their template, so the second instruction cannot be done there, and the first leads to 250 charged sends with no usable code. The investigation says not to re-run this template as is. The confirmation sheet does not repeat the warning.

Warn-only stays as decided; this is wording only.

Fix: on `failed`, word the remedy as "create a new campaign", and pass `qrOnlyCoupon` into the sheet.
