## 🟢 Minor (Optional)
- **`src/application/execute-campaign-broadcast.ts:104` (Latent Inconsistency in Eager Path)**: As asked in the prompt, the diff highlights a discrepancy in counting behavior. For the new marketing-only path, a successful WhatsApp send guarantees a counter increment. In the pre-existing eager path (`sendEagerToMember`), the body is sent *before* the coupon mint, but the counter is incremented *after* the mint. If the database mint fails (non-unique constraint), the WhatsApp message is still delivered, but the failure skips the counter increment—resulting in an under-count of actual messages sent. While defensible (the recipient didn't get their promised QR), it causes a mismatch with Meta billing. Consider a follow-up ticket to unify counting guarantees across both paths.

## ✅ Strengths
- **Safe Auto-Execute Deletion**: The `#136` fix purely deletes the faulty `/execute` auto-trigger rather than adding complex state logic. Gemini verified `getDueCampaigns` explicitly requires `scheduled_at IS NOT NULL`, confirming that deleting this code correctly drops `execution: 'now'` campaigns into a safe holding state until the user clicks the manual button.
- **Clean Precedence Order**: The `sendToMember` routing cleanly prioritizes claim-mode over marketing-mode, ensuring that even if a campaign lacks a `couponConfig`, a claim template won't accidentally be sent without its required metadata.
- **Robust Event Shape Compatibility**: The marketing-only path omits the `couponCode` field in the emitted `campaign` event. This seamlessly integrates with the rest of the application since the pre-existing claim path (`sendClaimToMember`) already emits the exact same shape (without a `couponCode`), proving consumers are already tolerant of it.
- **Targeted Test Coverage**: The new tests strictly validate the ACs without demanding refactoring of out-of-scope legacy tests.

## Open Questions
- **Tracking Off Re-run Idempotency**: When send tracking is ON, the `prefetch.countedMemberIds` ledger effectively prevents double-sending for all paths. However, when tracking is OFF, the marketing-only path loses its idempotency. The eager path had a database-level backstop (the `UNIQUE` constraint on coupon mints) that aborted a re-run if tracking was off. Since marketing-only campaigns don't mint coupons, a re-run with tracking OFF will double-send the WhatsApp body and double-increment the sent counter. Given that turning tracking off inherently drops per-message persistence, is this regression acceptable, or do we need a separate mechanism to ensure idempotency for couponless sends?
