## 🟡 Important (Should Fix)

**I9. A row still `queued` at the click passes the guard, and a sweep tick before the ledger read sends it twice. → plan (main thread).**

Files:
- `src/application/rerun-evidence-guard.ts:14-15` (docstring: "Non-failed body rows do not refuse, because the per-member ledger skips those members")
- `src/infrastructure/supabase/repositories/whatsapp-message-campaign-queries.ts:116` (`.eq('status', 'failed')`)
- `src/infrastructure/supabase/repositories/whatsapp-message-ledger-queries.ts:29`
- `src/application/execute-campaign-batch.ts:87` (ledger is read per chunk, at send time)

The ruled predicate covers failed rows only. The ledger's protection for a `queued` row ends when the sweep flips it, and the guard checks at click time while the ledger is read later.

Failing scenario:
1. Kapso accepts a send and Meta delivers it, but saving the wamid fails. The row stays `queued` with no wamid.
2. The campaign reaches `failed` before the next sweep. The two routes are those in C2: the retract RPC, or a job that exhausts its retries. The same database blip can cause both the lost wamid and the exhausted job.
3. The tenant clicks Re-run. The row is not `failed`, so the guard returns null and the route answers 200.
4. The job waits, or reaches that member's chunk late. Worker concurrency is 1 (`campaign-queue.ts:124`), so it can sit behind another tenant's campaign.
5. A sweep tick flips the row to `failed/internal_orphan`. The ledger stops counting it and the member gets a second send.

Exposure: the row stays `queued` for 5 to 15 minutes, because the sweep runs `*/10` (`deploy/README.md:284`; the Forge schedule itself was not read). A tenant reacting to a failure can easily click inside that time. The duplicate also needs a tick between the click and that chunk's ledger read, so with an idle queue and a small audience the odds are low. The worst case is the same as C2's: in-flight sends per blip, not a whole audience. Prod count unknown.

How it was shown failing: `src/application/__tests__/race-queued-at-guard.test.ts` in the scratch copy above, built on the dev's test with a queue that delivers after a sweep. Result: guard null, 200, 2 sends to m-2, with rows `failed/internal_orphan` and a new `queued`. The control in that file has no tick and gives 1 send, so the tick is the cause. The control's job swallows a harness error (the fake has no `.order` for the finalizer's latest-failure read), which comes after the send decision and does not affect the count.

Fix, if the main thread wants it: in the guard, also refuse when a body row is `queued` with a null `kapso_message_id`. That is one more head count, with no ledger or sweep change, and it makes the docstring true. It only refuses, up to 15 minutes earlier, a row the guard would refuse anyway once swept, so it adds no new permanent refusals. Bicho's rows are all `failed` with numeric codes, so Bicho is unaffected. Add the scratch test above as the proof.

Alternative: accept it and add it to the separate issue for open question 2, since a ledger fix would close this too. That is reasonable given the odds, but the issue should name this tenant-route case, because the previous review said that route was closed.

I recommend the guard fix: it is small, stays inside the guard's existing purpose, and leaves the accepted ledger and sweep ruling alone.
