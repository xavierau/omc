# Code Review: CAMP-012 / CAMP-013 — guardrail defaults (#161) + recipient RPCs (#162)

Second independent lane (standing in for the Gemini CLI reviewer, failing at account level).

14 product files, 941 insertions. Reviewed against the plan, both issues, and the cited

## Summary

The design is right and the execution is unusually careful: the RPC shape is the correct
permanent fix for #162 (not a chunk-size retune), the count/send parity with 067 is asserted
structurally rather than by comment, the 064 lockdown is complete and proven by `SET ROLE` on a
scratch DB, and the 078 trigger+backfill faithfully mirrors 077 for an identical bug class.
Column types in both `RETURNS TABLE` lists match `members` exactly, so `supabase db push` will
not fail at `CREATE FUNCTION`.

One real behavioural regression blocks a clean approve: **the client-side dedupe that guarded
page-boundary duplicates was deleted along with the id round-trip, and nothing replaced it.**
Everything else is documentation accuracy, one test-coverage hole, and a pre-deploy verification
step the release notes are missing.

## 🟡 Important (Should Fix)

### I-1 — Cross-page duplicate recipients are no longer deduped (double send)

`src/application/resolve-campaign-members.ts:108-118` (tag branch), `:80-90` (selected branch).

**What changed.** The deleted `fetchTaggedMemberIds`
(`resolve-campaign-members-chunks.ts`, removed in this diff) ended with:

```ts
return [...new Set(rows.map((r) => r.member_id))]
```

That `new Set` deduped across *all* pages of the walk. The new code is
`return rows.map(mapRowToMember)` with no dedupe at any level. `DISTINCT ON (m.id)` in migration
079 dedupes only **within one page** — it cannot see rows returned by a previous request.

**Failure scenario.** A tag audience above one page (>1,000 members, or lower if the project's
PostgREST `max-rows` is below 1,000) is walked with `LIMIT/OFFSET` over `ORDER BY m.id`. If any
`member_tags` row matching the selection is inserted between page *k* and page *k+1* — a merchant
tagging members while a large send runs, a CSV tag import, the bulk tag route — every row at or
after the new member's `m.id` shifts down by one offset position, so the row that sat on the page
boundary is returned **twice**. `execute-campaign.ts:47` filters only `status`, and
`bulkCheckMarketingCooldown` composes one decision per `phoneE164` from a single pre-batch count
(`check-marketing-cooldown.ts:56-77`), so two duplicates landing in the same 100-member pacing
chunk both evaluate to *allowed* and both send: two marketing templates to one recipient,
double-counted in `chargeable_sent_count`, and a WhatsApp quality-rating hazard.

This is a regression, not a pre-existing exposure: the old tag path could *skip* a member under
the same concurrency (offset paging always could, and the plan accepted that), but it could never
*duplicate* one. The selected branch was previously unpaged, so it had no cross-page exposure at
all. Issue #162's acceptance list names "a member carrying two selected tags receives exactly one
message", and the plan's own domain model calls the recipient set a set.

**Fix (minimal, one place).** Dedupe by `id` after `readAllPages` in both branches — e.g. a
`Map<string, Member>` keyed on `row.id`, or a `Set` guard in the map step. Add a test that feeds
`pagingRpc` an overlapping second page and asserts unique ids out.

**Fix (durable, if you'd rather not carry the offset window).** Keyset-page the RPCs:
`p_after uuid DEFAULT NULL` with `AND (p_after IS NULL OR m.id > p_after) ORDER BY m.id LIMIT
p_limit`, driven by the last id received. That removes both the duplicate and the skip, at the
cost of a `readAllPages` variant. Larger than this PR needs; the dedupe is sufficient to close
the regression.

### I-2 — The 078 contract test cannot see trigger↔CASE drift

`src/infrastructure/supabase/repositories/__tests__/plan-quota-migration-contract.test.ts:42-101`.

The parity block proves `plan_monthly_send_limit`'s CASE matches `planCampaignQuota`. The shape
block proves a trigger exists, that two `ON CONFLICT (restaurant_id) DO NOTHING` guards are
present, and that the backfill selects from `restaurants`. **Nothing asserts that the trigger or
the backfill actually calls `plan_monthly_send_limit`.**

**Failure scenario.** A future edit (or a bad merge) changes 078:58 to
`VALUES (NEW.id, 1000)` while leaving the helper function in the file. Every assertion in this
test still passes, the parity suite is still green, and every new `growth`/`pro` tenant is seeded
at the starter cap forever — the exact #161 bug, re-shipped under a green "red on drift" test.
The scratch-DB run does catch this, but the scratch run is not in CI.

**Fix.** Two `toMatch` assertions: the trigger body contains `plan_monthly_send_limit(NEW.plan)`
and the backfill contains `plan_monthly_send_limit(plan)`.

### I-3 — The backfill promotes cosmetic `restaurants.plan` values into enforced quotas; no pre-deploy capture of the plan distribution

`supabase/migrations/078_...sql:73-75`; release notes in
`plans/2026-09-10-camp-012-013-guardrail-defaults-and-recipient-rpc` ("Release notes").

Issue #161 states the premise plainly: *"`restaurants.plan` is cosmetic on its own."* Until this
migration, nothing enforced it, so a `plan` value set during a demo, a trial, a migration, or a
manual poke had no billing consequence. The backfill converts every one of those values into a
real monthly quota in a single statement: a row that says `pro` becomes 100,000 sends/month.

**Failure scenario.** A tenant whose `plan` column was set to `growth`/`pro` cosmetically (or a
suspended/trial tenant — `restaurants.status` is not consulted by the backfill) silently gains
10–100× the send headroom the business intends, and nobody notices because the change is
invisible until they use it.

The release notes' post-deploy check 3 (`GROUP BY plan, monthly_send_limit`) would show the
resulting pairs, but only *after* the quotas are live and only as a consistency check — by
construction every pair will match `PLAN_QUOTAS`, so it cannot flag an unintended entitlement.

**Fix (ops, not code).** Add a **pre-deploy** capture to the runbook and have a human sign it off:

```sql
SELECT plan, status, count(*), array_agg(name ORDER BY name) FROM restaurants GROUP BY 1, 2;
```

Any non-`starter` row other than Kushiro is an entitlement decision, not a data fix. If one turns
up, correct `restaurants.plan` **before** the deploy (the backfill reads it) rather than editing
`tenant_campaign_settings` after.

## 🟢 Minor (Optional)

### M-1 — 078's header over-claims migration-level idempotency

`supabase/migrations/078_...sql:68-72` says "re-running this migration is a no-op the second
time". The backfill statement is idempotent; the **file** is not — `CREATE TRIGGER` at :64 has no
`DROP TRIGGER IF EXISTS` / `OR REPLACE`, so a second apply aborts with *trigger already exists*.
Harmless under `supabase db push` (it tracks applied migrations) and identical to the 077
precedent, but the sentence will mislead the next person who re-runs the file against a scratch
or restored DB. Either scope the claim to the backfill statement, or add
`DROP TRIGGER IF EXISTS trg_restaurant_seed_campaign_settings ON restaurants;` above :64.

### M-2 — The documented RLS risk is narrower and louder than the header says

`supabase/migrations/078_...sql:34-39`. Checked: `restaurants_insert`
(`011_multi_tenant_platform_admin.sql:86-87`) is `WITH CHECK (is_platform_admin())` — the *same*
predicate as `campaign_settings_insert` (`016:29-30`). So any non-service-role principal able to
perform the triggering insert also satisfies the settings-insert policy; the plain-plpgsql trigger
cannot fail under RLS today, and would only do so if the two policies were ever allowed to
diverge (e.g. self-serve tenant signup). And if they did diverge, the failure mode is an aborted
`restaurants` INSERT — loud, not a silently missing settings row. Worth saying so: the header
currently reads as an open silent-failure risk. (No `FORCE ROW LEVEL SECURITY` anywhere in
`supabase/migrations/`, so the backfill running as the migration role is unaffected.)

### M-3 — Trigger function is unqualified and carries no `SET search_path`

`supabase/migrations/078_...sql:54-62`: `restaurant_seed_campaign_settings()` is created without
a `public.` prefix and references `tenant_campaign_settings` / `plan_monthly_send_limit`
unqualified, with no `SET search_path = public`. As a non-`SECURITY DEFINER` function this
resolves against the caller's `search_path`. Not exploitable here (only platform-admin/service
roles can insert into `restaurants`, and `anon`/`authenticated` cannot `CREATE` in any schema on
Supabase), and it matches 077 exactly — but `SET search_path = public, pg_temp` on both new
functions is free hardening if you touch the file for M-1.

### M-4 — 079 contract test is whitespace-coupled to the migration text

`recipient-rpc-migration-contract.test.ts:93-101, 132-136, 150-154` assert with `toContain` on
exact strings (`'m.restaurant_id = p_restaurant_id'`, `'LIMIT p_limit OFFSET p_offset'`). Aligning
079's predicates the way 067 aligns its own (`m.restaurant_id  = p_restaurant_id`, two spaces)
would turn the suite red on a pure reformat. It fails in the safe direction, and `normalisedWhere`
already shows the right technique — worth normalising the other assertions the same way if the
suite ever costs someone a false red.

### M-5 — `resolve-campaign-members-chunks.ts` no longer chunks anything

The module now exports only `READ_PAGE_SIZE` and `readAllPages`; the doc comment
(`:1-8`) is honest about it. The plan explicitly deferred the rename as churn. Mentioning only —
`resolve-campaign-members-paging.ts` next time this file is opened for another reason.

### M-6 — `daily_campaign_limit` stays at 1 for every plan

078:73-74 seeds only `monthly_send_limit` from the plan; `daily_campaign_limit` takes the
column default of 1 (016:6). Issue #161's opening line names *both* caps ("1,000 sends/month
**and 1 campaign/day** regardless of the plan"), and its suggested fix 1 says "from its
`restaurants.plan` value" without narrowing to the monthly quota. There is no
`planDailyCampaignLimit` in `tenant-plan.ts`, so delivering it would mean inventing a number —
correctly out of scope for this PR. Flagging so the half that was not fixed is a decision on the
record rather than an omission. See Open Questions.

## ✅ Strengths

- **The right fix, not the cheap one.** The issue offered a chunk-size retune as a mitigation;
  this ships the RPC and *deletes* `MEMBER_ID_CHUNK_SIZE`, `fetchMembersByIds`, `chunk()` and
  `fetchTaggedMemberIds` so the shape cannot come back. `grep` confirms zero orphaned references.
- **Count/send parity is structural, not aspirational.** `normalisedWhere` compares 079's tags
  WHERE clause against 067's actual file text
  (`recipient-rpc-migration-contract.test.ts:142-148`). That is the assertion that stops the
  dashboard from counting an audience the send path cannot reproduce, and it survives whitespace.
- **Migration↔TS drift is a test, not a comment.** The `PLAN_QUOTAS` ↔ SQL `CASE` parity test
  (subject to I-2) plus `DEFAULT_SETTINGS.monthlySendLimit === planCampaignQuota('starter')`
  (`tenant-plan.test.ts:38-42`) close the loop that made #161 invisible in the first place.
- **The lockdown is complete and proven.** Both functions carry 3 `REVOKE` + 1 `GRANT` on their
  exact 4-arg signatures, byte-matching the 064 pattern; the test counts them per signature; and
  the scratch run re-granted Supabase's baseline public-schema grants *first* and still got
  `permission denied` for `anon` and `authenticated` on both functions. No
  `ALTER DEFAULT PRIVILEGES` or blanket `GRANT ... ON ALL FUNCTIONS` exists in the migration set
  to undo it.
- **`RETURNS TABLE` types verified against the schema.** `id/restaurant_id uuid`, `phone/name/
  status/preferred_language text`, `points_balance int`, `joined_at/last_visit_at/
  pmm_throttled_until/unreachable_at timestamptz` all match `001:14-23`, `030:4`, `036:11-12`.
  A mismatch here would have failed `supabase db push` mid-deploy.
- **`readAllPages`' hard-won contract survived the port.** Ends on an *empty* page, advances by
  rows *received*; the mock reproduces a server whose `max-rows` is below the page size and the
  test asserts offsets `[0, 500, 1000, 1200]` — the case that skips rows if you advance by
  `p_limit`. The comment rewrite at `:18-36` correctly generalises "must impose a total order"
  from `.order()` to the RPC's internal `ORDER BY`.
- **Fail-closed fallback with a real signal.** `planDerivedDefaults` warns with tenant id, plan
  and limit; A5 asserts the fast path neither reads `restaurants.plan` nor warns; A6 asserts a
  throwing plan read rejects the whole guardrail check. `getRestaurantPlan` coerces an
  out-of-CHECK value to `'starter'` rather than propagating garbage.
- **`setupMocks` was made stricter mid-flight, not looser.** Commit `fdd478f8` changed
  `opts.settings ?? makeSettings()` to an explicit `undefined` check so a deliberate `null`
  reaches `resolveSettings` as `null` — the opposite of weakening a suite to fit an
  implementation. TDD order holds across the branch (`86144768`/`89c3829c` precede `10dfa76a`/
  `2022e545`).
- **Honest scoping.** The three same-shape `.in()` sites are audited and reported rather than
  half-fixed, and the `created_at`-keyed counter bug from #161's secondary observations is
  written up as a follow-up instead of being smuggled in.

## Checked and found sound

Explicitly verified, no finding:

1. **078 `ON CONFLICT` vs a hand-tuned row.** `DO NOTHING` against the `UNIQUE (restaurant_id)`
   constraint (016:4); the `updated_at` trigger is `BEFORE UPDATE` only (016:41-43, rebound
   035:85-88), so an `INSERT … DO NOTHING` cannot touch Kushiro's timestamp. Scratch run confirms
   0 rows inserted on re-run, `lim=10000, daily=5, updated_at unchanged`.
2. **Backfill defaults vs `DEFAULT_SETTINGS`.** Every column the backfill leaves to its DB default
   matches the TS constant it replaces: `daily_campaign_limit` 1, `max_unsubscribe_rate` 0.0500,
   `campaign_paused` false (016), `per_user_marketing_cap` 1 (040), `auto_throttle_factor` 1.00 /
   `auto_pause_active` false (042), `pacing_strategy` `engagement_tier` / `probe`+`scale` 100 /
   `10:00:00`–`22:00:00` / `Asia/Hong_Kong` (043). Materialising the row changes nothing except
   the monthly quota.
3. **`plan_monthly_send_limit` ELSE branch.** Returns 1000 = `planCampaignQuota('starter')`;
   asserted. Unreachable in practice — `chk_plan` (017:2) restricts the column to the three
   values — so it is a defensive floor, and the safe one.
4. **Deploy ordering window.** `deploy.sh` runs `supabase db push` before the app restart, so
   there is a window of new rows + old code. Old `resolveSettings` returns the row it finds, which
   now carries the *correct* plan quota — a loosening in the intended direction; old `>=` costs at
   most one send at the exact boundary. 079 is inert until the new build calls it. No misbehaviour.
5. **Partial-upsert safety now that the row always exists.** `mapSettingsToUpsert`
   (`campaign-settings-mapper.ts:122-131`) emits only keys the caller supplied, so
   `changeTenantPlan`'s `upsertSettings(id, { monthlySendLimit })` updates that one column and
   cannot clobber a tenant's `campaign_paused` / pacing / cap overrides. This mattered more after
   078 (the row is no longer usually absent) and it holds.
6. **Cross-tenant isolation of the selection RPC.** `campaign_members` genuinely has no
   `restaurant_id` (015:7-14), so scoping through `campaigns.restaurant_id` is the only option;
   079 carries *both* `c.restaurant_id = p_restaurant_id` and `m.restaurant_id = p_restaurant_id`,
   so neither a mis-tenanted campaign row nor a mis-tenanted member leaks. Scratch: `(B, cA)` → 0
   rows. Tags RPC keeps both 067 predicates; both poison rows were killed on the scratch DB.
7. **`DISTINCT ON` + `ORDER BY` + `LIMIT/OFFSET` semantics.** `ORDER BY m.id` leads with the
   `DISTINCT ON` expression (required by Postgres); dedupe happens before `LIMIT/OFFSET`, so
   offsets index the deduped set. Every projected column comes from `m`, so which duplicate row
   survives is irrelevant. `m.id` is the PK — a genuine total order, no ties.
8. **`status='active'` added to the selection path is behaviour-preserving.**
   `members.status` CHECK is still `('active','unsubscribed')` (001:20; no later migration widens
   it), and `execute-campaign.ts:47` already dropped unsubscribed rows before the guardrail count,
   so `activeMembers.length` and the send set are unchanged. Net gain: unsubscribed members' phone
   numbers no longer leave the database. `:47` correctly left in place as defence in depth.
   `resolveTargetMembers` has exactly one caller.
9. **`p_limit` NULL.** Never sent by the app (`to - from + 1` is always 1,000); `LIMIT NULL` means
   "no limit" in Postgres, exercised on the scratch DB (`limit NULL → 1500`). Safe as a manual /
   psql default.
10. **PostgREST `max-rows` on a set-returning RPC.** Handled by the empty-page/advance-by-received
    loop and asserted with a simulated cap of 500. No gap or duplicate from truncation itself.
11. **Error labels.** `fetchTagMembers:` / `fetchSelectedMembers:` prefixes are applied by
    `readAllPages`' `label`; the `fetchMembersByIds:` string that identified the incident is gone
    with the function. Both asserted (B7).
12. **No orphaned callers of the deleted helpers.** `grep` over `src` for `MEMBER_ID_CHUNK_SIZE`,
    `fetchMembersByIds`, `fetchTaggedMemberIds`, `chunk(`: zero hits outside comments.
    `READ_PAGE_SIZE`/`readAllPages` still have live importers.
13. **Trigger-function exposure.** `restaurant_seed_campaign_settings()` is left executable by
    PUBLIC, but a `RETURNS TRIGGER` plpgsql function raises when called outside a trigger context;
    `plan_monthly_send_limit` is a pure CASE over a text argument that reads no data. Neither
    warrants the 064 treatment, as the header argues.
14. **Test fitness against the reported failures.** #162's failure ("ids in a URL") is proven
    absent structurally (B3: no member id appears in `JSON.stringify(mockRpc.mock.calls)` on
    either branch) rather than by re-measuring a header size, which is the right proof for a unit
    test; 1,200 / 2,500 / exact-multiple / max-rows-500 audiences all page to completion. #161's
    failure (missing row on a `growth` tenant) is A3: settings `null` + plan `growth` + 5,000
    sends + 4,000 target → allowed, `monthlyLimit` 10,000 — the Kushiro case, inverted.
15. **Suite integrity.** 155 tests green locally across the 7 touched files. The `>=`→`>`
    boundary case was *rewritten* in place with its rationale, not deleted, and backed by an
    11-point `it.each` grid over `sends + target <= limit` including `(1000,0,1000)`,
    `(0,1000,1000)`, `(1,1000,1000)`, `(1,0,0)`.
16. **`>` change side effects.** `checkMonthlyLimit` has exactly one caller
    (`collectViolations`, against `effectiveMonthly`). `isApproachingLimit` is independent
    (`>= 0.8` of the limit) and correctly untouched — at exactly the limit the send is now
    allowed *and* warned. `checkDailyFrequency` keeps `>=`, which is correct for a
    "campaigns already executed today" counter and not an inconsistency.
17. **Layering.** `check-campaign-guardrails.ts` (application) imports the domain VO and an
    infrastructure repository — allowed; `campaign-guardrails.ts` (domain) gained a comment and an
    operator only. New file sizes are all inside budget; edits to the 500+ line
    `restaurant-repository.ts` match the file's existing `getRestaurantTenantStatus` shape
    (Surgical Changes).
18. **Integration Map.** I-1…I-12 all present in the tree; backend-only, so no route, nav,
    i18n key, feature flag, DI binding or permission was owed. `MEMBER_COLUMNS`' new export has
    exactly one consumer (the contract test), which is the stated purpose (D8).

## Verdict: CONDITIONAL

proven on a scratch DB, and the app layer is a faithful, well-tested implementation of the plan.

`plan_monthly_send_limit` so the drift it exists to catch is actually caught). **I-3** is an
ops precondition, not a code change, and must be signed off before the deploy rather than after.
