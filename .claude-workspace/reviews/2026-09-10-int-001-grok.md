## 🔴 Critical (Must Fix)

**`package.json:32` (and `package-lock.json`) — Next.js CRITICAL advisory unpatched, blocking-item #13 not done**
- Problem: Required blocking change #13 is not done — Next is still `16.2.1`, and SEC-005 (upgrade to a patched 16.3.x / at least 16.2.5) is still backlog. The threat model forbids shipping the new public partner routes on this version.
- Risk: An unauthenticated client can hit known Next App Router advisories on this exact version — GHSA-q4gf-8mx6-v5v3 Server Components DoS (affected through 16.2.3) and a middleware/prefetch bypass patched in 16.2.5. The HMAC partner routes are not themselves the bypass target; the dashboard App Router is. Shipping `/api/integrations/.../members` on this binary ships the vulnerable Next to the same origin.
- Fix: Bump `next` (and lockfile) to a patched release covering those GHSAs (SEC-005's 16.3.x, or at minimum 16.2.11+), re-run tsc/eslint/vitest and an off-box `next build`, then smoke dashboard auth and the partner routes before merge.

## 🟡 Important (Should Fix)

1. **`src/application/process-member-create-job.ts:267`** — Member-create worker is not idempotent for welcome on retry. After `createOrGetMember` returns `created`, a crash/retry before `completeMemberJobSucceeded` re-runs the job, sees `existing`, and `decideWelcome` returns `skipped_existing` — welcome is never enqueued. Concrete sequence: partner POST creates member + consent + `join` event → worker dies before `addWelcomeSendJob` → BullMQ retries → `createOrGetMember` returns `existing` → welcome skipped. OD-2/OD-15 fail on the retry path, not the happy path. Fix: persist "this attempt created the member" on the job row (or key welcome off `integration_member_jobs.welcome_outcome IS NULL` plus a created-by-this-job flag); decide welcome from that, not from a fresh `createOrGetMember` outcome.

2. **`src/infrastructure/supabase/repositories/coupon-repository.ts:87`** — `type='welcome'` coupons have no unique index; `mintWelcomeCouponIdempotent`'s campaign-less path is check-then-insert only, used whenever `new_join_template_id` is a specific template UUID. Risk: a stalled BullMQ lock lets two workers run `processWelcomeSendJob` for the same `wel:{memberId}:{createJobId}`; both see no existing row, both insert — member gets two welcome codes (this is the CAMP-style duplicate-coupon risk the review focus explicitly asked to probe). Default `'default'` template uses the campaign/promo path and is safe. Fix: add a partial unique index on `(restaurant_id, member_id) WHERE type='welcome' AND member_id IS NOT NULL`, treat 23505 as idempotent re-select; prefer resolving a campaign for UUID templates so the existing promo unique index applies.

3. **`src/application/register-member-web.ts:59`** (and `register-member.ts:94`) — WI-7 wraps `PhoneNumber.create` output in `E164Phone.of`. `PhoneNumber.create` only strips `[\s\-()]` and keeps dots/letters; `E164Phone.of` requires `^\+[1-9]\d{7,14}$`. Previously-accepted web/WhatsApp numbers now throw uncaught. Risk: QR join with e.g. `+852.9123.4567`, or WhatsApp sending a dotted value, 500s the join with no member created — a legacy-path regression from the WI-7 seam refactor (exactly the review-focus concern #7). Partner API is unaffected (real parser at the edge). Fix: on legacy paths, don't call `E164Phone.of` on `PhoneNumber.value` — pass the existing string into `insertMember`, or run `parseE164Phone` and return the old validation error instead of throwing.

4. **`src/infrastructure/queue/integration-inbound-queue.ts:37`** — Inbound `member-create` jobs store `phoneE164`, `name`, `externalRef`, `metadata` in Redis, with `removeOnFail: { count: 1000, age: 7d }` on a Redis shared by other sites. T-H7 closed this for outbound (`{deliveryId}` only) and welcome-send (ids only) but not for inbound create. Risk: a failed inbound job retains full E.164 + name in Redis for up to 7 days, up to 1000 jobs — PII exposure to anyone with Redis access on the shared VM (review-focus concern #6). Postgres job rows correctly store `phone_last4` only, so the worker currently has no other place to re-materialise the phone. Fix: store the already-parsed E.164 on `integration_member_jobs` (encrypted or access-controlled) and enqueue `{ jobId, integrationId, restaurantId }` only, matching outbound; shorten `removeOnFail` until then.

5. **`src/app/api/dashboard/pos-integrations/[id]/deliveries/[deliveryId]/retry/route.ts:32`** — Retry loads a delivery via unscoped `findDeliveryById` (service role, no restaurant filter) then compares `integrationId`/`restaurantId` in JS; `retryDelivery` loads by id again and mutates. Sister mutations (`updatePosIntegration`, `deletePosIntegration`, `rotateInboundSecret`, `resumeOutbound`, `updateIntegrationSettingsFields`, `persistOutboundSecret`) follow the same pattern — scoped existence check, then unscoped UPDATE/DELETE by id. This is the SEC-001/#111 fetch-then-compare pattern this codebase has a named principle against (`principle_authorize_by_scoped_query`). Today the compare is used so a tenant-B UUID 404s, but the service-role read still materialises tenant B's row in tenant A's request, and a missed compare on any future caller retries/mutates another tenant's data. Fix: replace with `findDeliveryByIdForIntegration(deliveryId, integrationId, restaurantId)` (null on mismatch); put `.eq('restaurant_id', restaurantId)` on every UPDATE/DELETE; thread `restaurantId` into `retryDelivery`/`rotateInboundSecret`/`resumeOutbound`.

6. **`src/application/process-member-create-job.ts:331`** — On the final attempt, raw `Error.message` is written to `error_message` and returned by `MemberJob.partnerView()`. `insertConsentRecordWithOrigin`'s 23505 path uses `ConsentImportError`, whose message embeds `phoneE164`; Slack `details.error` gets the same string. Risk: partner GET job after a concurrent-consent 23505 exhaustion receives `{error:{code:'internal', message:'consent already exists for (<restaurantId>, +85298765432, marketing)'}}` — restaurant id + E.164 on the partner wire, violating OD-11/T-M3. Fix: map final failures to stable codes (`conflict`, `internal`) with a generic message; log the exception server-side; strip phone/restaurant from `ConsentImportError`.

7. **`src/application/process-member-create-job.ts:279`** — OD-13's labelled default is grade `strong`. The job actually sets `strong` only if `consent_attestation_text` AND `consent_attestation_ack_at` are both set; otherwise `weak`. Risk: a partner with `consent_level: all` and no owner attestation writes marketing `opted_in` at grade `weak` — campaigns still send (`checkMarketingConsent` only requires `opted_in`), but analytics/WAQ reporting treat these as weak, and owners who never open the attestation card silently get weak, not the spec default. Fix: either keep OD-13's always-`strong` default and use attestation only as extra evidence, or (if the WI-3 attestation-gated model is the real decision) update spec §11 and owner-facing copy so "strong" is not promised without attestation. (Flagged as Open Question below too.)

8. **`src/application/resume-outbound.ts:47`** — Resume loads every paused delivery id, then `Promise.all` of per-id `findDeliveryById` + `saveDelivery`, up to `inbound_queue_cap` (default 500). Risk: an integration paused after a partner outage can accumulate hundreds of paused rows; one Resume click fires up to 500 parallel PostgREST reads+writes on the shared 4GB VM, competing with inbound/outbound workers (a queue-exhaustion angle from review-focus concern #2, applied to the dashboard resume path rather than the inbound API). Fix: bulk `UPDATE ... SET status='queued' WHERE integration_id = $1 LIMIT cap`, with a bulk dead-letter for the remainder.

## 🟢 Minor (Optional)

1. **`src/app/api/integrations/[integrationId]/members/route.ts:61`** — `authenticateIntegrationV2` returns `replayed` but POST ignores it and always calls `enqueueMemberCreate`. Same-body retries are still saved by T-H3 job-id idempotency (same 202, no second job); the unused flag just skips a cheap short-circuit. Fix: if `authResult.replayed`, look up the existing job and return 202 without touching depth/ceiling/insert.
2. **`src/domain/entities/member-job.ts:57`** — In-flight `partnerView()` adds `submitted_at` and `attempts` beyond OD-11's listed fields (status, member_id, outcome, error). Not a PII leak, but a partner can observe attempt count and queue delay — a contract extra. Fix: drop the fields or amend OD-11/US-2 if intentional.
3. **`src/application/send-test-event.ts:5`** — A "ping" test event fans out to every outbound-enabled integration on the restaurant (migration 071 trigger), not only the one being tested (disclosed in the file header). A restaurant with two partners testing integration A also delivers `ping` to B. Fix: scope ping fan-out to `NEW.origin_integration_id`, or insert the delivery row directly for the target integration.
4. **`supabase/migrations/072_consent_partner_guard.sql:22`** — The absorbing trigger SELECTs latest status without `FOR UPDATE` / advisory lock; app-level `applyPartnerAssertedConsent` only INSERTs when latest is null, so STOP resurrection is not currently reachable through the partner path, but a future `partner_api` insert that skips `applyPartnerAssertedConsent` could race an in-flight STOP UPDATE. Fix: lock the `(restaurant_id, phone_e164, category)` identity in the trigger before allowing INSERT.
5. **`src/domain/services/ip-range.ts:125`** — IPv6 blocklist covers `::1`, `::`, `::ffff:0:0/96`, `fc00::/7`, `fe80::/10`, `2001:db8::/32` but not NAT64 `64:ff9b::/96` or 6to4 `2002::/16`, either of which can embed `169.254.169.254`. Only material if the GCE VM uses DNS64/NAT64 (typical e2-medium does not). Fix: block `64:ff9b::/96` and `2002::/16`, extract and check the embedded IPv4 against the v4 list.

## ✅ Strengths

- Single member-insert seam with 23505-as-existing and a grep boundary test; WhatsApp/web/CSV all actually call it.
- `opted_out` is absorbing in one policy function plus a `partner_api`-only trigger, with STOP-then-create and member-deleted tests.
- SSRF control is real: resolve-and-pin, all-answers-public, https/443, no redirects, enforced at save time and attempt time, with rebinding tests against a mocked resolver.
- Inbound auth v2 is domain-separated, timestamped, fail-closed, and does not charge the partner rate-limit bucket on unsigned junk.
- OD-11 partner projection correctly omits coupon, consent, and welcome; outbound jobs are ids-only and signed at attempt time; outbound secret lives in a dedicated encrypted column.
- Welcome mint happens inside the send job after re-checks; the campaign/promo path is uniquely indexed; quality-pause and hourly cap are both re-checked at send time.
