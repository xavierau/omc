# Code Review: INT-001 bidirectional member-creation API (branch `feature/int-001-member-api`, 17 commits vs `main`)

Scope: full branch diff (231 files) excluding workspace/docs/lockfile. Gate-covered dimensions (size, complexity, types, dead code) are out of scope. This is the independent second lane (Gemini CLI unavailable); the Grok artifact was not read.

## Summary

The security design the threat model demanded is present and, on the parts I traced end to end, correct: `opted_out` is absorbing on every partner path (application decision + `status='pending'`-conditioned upgrade RPC + `BEFORE INSERT` trigger + partial unique index together leave no resurrection path, including under concurrent jobs); the HMAC v2 pipeline charges the partner bucket only after a valid signature and fails closed on Redis; the SSRF resolve-and-pin is wired into a real undici connector whose `lookup` honours both the Happy-Eyeballs `{all:true}` array form and the two-arg form, with no redirect following; the outbound secret is AES-GCM at rest, excluded at the SQL column level from every entity read, and `readOutboundSecret` is imported only by the delivery path; every WI-8 dashboard route scopes by `restaurantId` in the query and the retry route re-checks both ids before the unscoped `retryDelivery`; domain imports nothing from infrastructure/Next and application imports nothing from Next.

Two correctness defects in the outbound delivery lifecycle block approval. Both are in WI-6 and both leave delivery rows permanently stuck with no alert and no owner recovery path, contradicting spec US-6/US-9 and the kanban CONSTRAINT (b): (1) transient exhaustion after 5 attempts never dead-letters, and (2) Resume after a breaker trip is a silent no-op for any delivery whose BullMQ job already completed as `paused` inside the `removeOnComplete` window, because the relay re-adds with the same `jobId` and BullMQ dedups it. The `next` CRITICAL advisory (item 13) is not patched on this branch (`package.json` still `16.2.1`); it is tracked as SEC-005 and remains a release precondition.

## 🔴 Critical (Must Fix)

### C-1. Transient exhaustion on the outbound queue never dead-letters — rows stick in `retrying` forever, no Slack, not manually retryable
- **Where**: `src/infrastructure/queue/integration-outbound-processor.ts:88-100` (`handleDeliverJob`), `src/application/deliver-outbound-webhook.ts:156-181`.
- **Problem**: the transient branch persists `retrying` and throws a plain `Error` for BullMQ to back off. Nothing checks `job.attemptsMade + 1 >= job.opts.attempts` (5). After the 5th transient failure BullMQ moves the job to its failed set; the `integration_deliveries` row stays `retrying` permanently. `retryDelivery` (`src/application/retry-delivery.ts:16`) requires `dead_lettered`, so the owner's Retry button is disabled for it; `alertDeadLettered` never fires; the relay ignores it (`status='queued'` only). The email queue precedent the plan cites (`email-job-processor.ts:112-118 handleExhaustedRetries`) does exactly this final-attempt handling; it was not carried over.
- **Failure scenario**: partner endpoint returns 503 for ~90 s (5 attempts at 3/6/12/24/48 s). Every `member.created` delivery in that window is lost from the operator's and owner's view: dashboard shows "retrying" indefinitely, no Slack, the 30-day pruner eventually deletes them. Spec US-6 AC line 470 ("Exhausted → dead-letter + Slack alert") and kanban CONSTRAINT (b) ("dead-letter on exhaustion with a Slack alert") are unmet. Breaker streak is also not reset/advanced for these rows after exhaustion.
- **Fix**: in `handleDeliverJob`, on a `transient` result compute `isFinal = job.attemptsMade + 1 >= (job.opts.attempts ?? 5)`; when final, transition the row `retrying → dead_lettered` (`deadLetteredAt`, keep last status/error), call the existing `alertDeadLettered`, and throw `UnrecoverableError`. Cleanest is to pass `isFinalAttempt` into `deliverOutboundWebhook` so the dead-letter branch there is reused. Add the test the plan named ("5 transient failures → `dead_lettered` + Slack").

### C-2. Resume after a breaker trip silently drops deliveries whose BullMQ job already completed as `paused` (jobId dedup)
- **Where**: `src/application/sweep-integration-queues.ts:38-48` (`relayOne`), `src/infrastructure/queue/integration-outbound-queue.ts:49-66` (`addDeliverJob` uses `jobId = deliveryId`), `src/application/resume-outbound.ts:53-57`, `integration-outbound-processor.ts:91` (`paused` → return normally → job completes).
- **Problem**: when the breaker trips (or `INT001_DISABLE_OUTBOUND=1` is set), every in-flight job's next attempt hits step 1, marks the row `paused` and **returns**, so BullMQ records the job (id = deliveryId) as *completed* and keeps it for `removeOnComplete {count:200, age:3600}`. Resume flips those rows `paused → queued, enqueued_at NULL`; the relay then calls `queue.add('deliver', …, { jobId: deliveryId })`. BullMQ dedups on an existing job id in any state, so no job is created, but `relayOne` then stamps `markEnqueued`. The row is now `queued` with `enqueued_at` set: excluded from the relay forever, never delivered, never alerted. The WI-6 author knew about this dedup for the dead-letter case (`addRetryDeliverJob` uses `:r1`) but not for the paused-then-resumed case. Rows that were `paused` at fan-out time (created after the trip) are unaffected, which is why the happy-path tests pass.
- **Failure scenario**: partner outage → 10 transient failures → `paused_auto` → owner fixes endpoint and clicks Resume within an hour → the ≤10 deliveries that were mid-backoff (plus any that arrived while the switch was flipping) are silently lost; the dashboard shows them as "queued". Spec US-9 ("Resume re-enqueues them") and the plan §Outbound Retry/resume are unmet in exactly the scenario the breaker exists for.
- **Fix**: make the re-enqueue job id unique per generation — e.g. `jobId = \`${deliveryId}:${attemptsOrResumeSeq}\`` or `\`${deliveryId}:${enqueuedAt-epoch}\`` — for relay adds of rows that were previously enqueued (or unconditionally, since the row-level `enqueued_at IS NULL` guard already provides relay idempotency). Alternatively call `queue.remove(deliveryId)` before re-adding, but a unique id is simpler and race-free. Add a test: "deliver → paused → resume → relay produces a NEW job".

## 🟡 Important (Should Fix)

### I-1. Unauthenticated requests trigger two Postgres reads and a full-body buffer before any throttle
- **Where**: `src/app/api/integrations/[integrationId]/members/route.ts:45-58` (`request.text()` before the 16 KiB check; `findIntegrationSettingsById` before auth), `verify-signature-v2.ts:120` (`findPosIntegrationById` before signature), `integration-inbound-guard.ts:90-108` (auth-failure bucket only shapes the 401→429 response, it does not gate the lookups).
- **Risk**: an unauthenticated flood costs 2 DB round-trips + 1 HMAC per request with no backpressure; `request.text()` buffers an arbitrarily large body (Next route handlers have no body-size limit) before the 413 check runs. The T-H5 partner budget is correctly protected; the DB is not.
- **Fix**: (a) reject on `content-length > 16384` before reading the body; (b) check the auth-failure bucket read-only (`get`) before the DB lookups and short-circuit to 429 when already exhausted; (c) move the settings load after `authenticateIntegrationV2` (only `limits` need it — pass defaults first, or load once and reuse). See also I-2.

### I-2. Auth-failure bucket keyed on a client-controlled header
- **Where**: `src/infrastructure/supabase/audit-logger.ts:30-35` (`extractIp` returns the raw `x-forwarded-for` header), used at `members/route.ts:43` and `jobs/[jobId]/route.ts:24` → `int001:rlf:{integrationId}:{ip}`.
- **Risk**: behind nginx with `$proxy_add_x_forwarded_for` (append), the attacker chooses the first XFF hop, so each request lands in a fresh bucket — the 10/min auth-failure limiter is bypassable. Pre-existing helper, but this is its first use as a security boundary.
- **Fix**: derive the client IP from the last trusted hop (rightmost XFF entry, or `x-real-ip` as set by nginx) in a dedicated helper for the partner routes; or key the auth-failure bucket on `integrationId` alone (an unauthenticated caller cannot burn a *partner's* budget with that bucket anyway).

### I-3. `applyPartnerAssertedConsent` read-then-write races surface as PII-bearing errors that reach the job row, Slack and worker logs
- **Where**: `src/infrastructure/supabase/repositories/consent-record-repository.ts:150-155` (new `insertConsentRecordWithOrigin` builds `ConsentImportError` whose message embeds `phoneE164`), `src/application/process-member-create-job.ts:331-343` (message copied into `integration_member_jobs.error_message` on the final attempt — partner-visible via `partnerView().error.message` — and into `notifyOpsAlert.details.error`), `integration-inbound-queue.ts:131-133` (`worker.on('failed')` logs `err.message` on every failed attempt).
- **Scenario**: two concurrent creates for the same new phone with different bodies (two job ids) both read `latest=null`, both attempt the insert; the loser gets 23505 → `ConsentImportError('duplicate_active', 'consent already exists for (rest, +852…, utility)')` → logged with the full phone; retry then resolves as `noop`, so correctness holds but T-M1 ("row never carries the full phone") and T-H7 ("no PII in Slack") are violated on the error path.
- **Fix**: drop the identity from the `ConsentImportError` message (reason code + last4 at most); in `processMemberCreateJob` persist/alert a sanitised code rather than `err.message`; treat `duplicate_active` in `applyPartnerAssertedConsent` as a benign `noop` (re-read latest) instead of throwing, which also removes a wasted retry.

### I-4. Nonce-replay verdict is computed and never consumed
- **Where**: `integration-inbound-guard.ts:171` returns `replayed`; `members/route.ts:60-82` and `jobs/[jobId]/route.ts:29` ignore it.
- **Risk**: low today — a replayed POST envelope is content-addressed to the same job id and short-circuits on the idempotency record, and a replayed GET only reads. But the 600 s replay cache costs a Redis call per request for no effect, and any future endpoint added to this pipeline that is not content-addressed would be replayable without anyone noticing.
- **Fix**: decide and document: either reject `replayed:true` with 409/401 (partners must mint a fresh nonce per attempt — the doc already says so), or remove the check. Do not leave it as a dead signal.

### I-5. Welcome message can be sent twice on a retry after a successful send
- **Where**: `src/application/process-welcome-send-job.ts:162-211`.
- **Scenario**: `recordOutboundSend` succeeds (WhatsApp message delivered), then `updateMemberJobWelcomeOutcome(...,'sent')` at `:211` throws (DB blip) or the worker dies → BullMQ retries → all gates pass again → a second template message and a second `whatsapp_messages` row. The coupon mint is idempotent (OD-15 satisfied) but the send is not, and each retry also consumes another hourly-cap token.
- **Fix**: at job start, read the create job row and return early if `welcome_outcome === 'sent'`; or check for an existing `whatsapp_messages` row with the `[welcome_partner_api]` preview for this member/campaign before sending. Also consider `updateMemberJobWelcomeOutcome` before the send with a `sending` marker.

### I-6. `member-create` job payloads (phone, name, metadata) are retained in BullMQ's failed set for 7 days
- **Where**: `src/infrastructure/queue/integration-inbound-queue.ts:82-91` (`removeOnFail {count:1000, age:7d}`), payload shape `:37-48`.
- **Risk**: T-H7's "no PII in the dead-letter set" is satisfied for outbound but the inbound failed set is a 7-day Redis store of partner-submitted phone numbers, names and free-form metadata, outside the Postgres RLS/audit story. The Postgres row already holds everything needed for triage (phone_last4, error code).
- **Fix**: on the final attempt in `processMemberCreateJob` call `job.updateData({ jobId, integrationId, restaurantId })` before rethrowing (requires passing the job through the processor), or set `removeOnFail` for `member-create` to a short age (e.g. 1 h). Keep the 7 d retention for `welcome-send`, which is ids-only.

### I-7. Sticky COALESCE on `origin_integration_id` can attribute a member's own STOP to the partner that shares the 5 s bucket
- **Where**: `supabase/migrations/073_integration_event_origin_attribution.sql:88-91, 122-125, 153-156` (`COALESCE(existing, EXCLUDED)`).
- **Scenario**: partner A's job inserts a `utility` pending row (origin A) and, inside the same 5 s bucket, the member texts STOP (marketing row → `opted_out`, origin NULL). Both writes coalesce into one `member.updated {changed:['consent'], origin_integration_id: A}`. A partner following the documented "ignore events whose `origin_integration_id` is yours" rule drops the STOP. The reverse order (STOP first, then A) gives the same result because `COALESCE(NULL, A) = A`. The non-sticky alternative has the mirror problem, so neither single-origin choice is safe.
- **Fix**: on conflict, keep the origin only when both writers agree: `origin_integration_id = CASE WHEN integration_events.origin_integration_id IS NOT DISTINCT FROM EXCLUDED.origin_integration_id THEN integration_events.origin_integration_id ELSE NULL END` (NULL = mixed/unknown, which partners must not ignore). Document that a coalesced event may carry NULL even when the partner contributed to it.

### I-8. Breaker streak is a non-atomic read-modify-write
- **Where**: `src/application/deliver-outbound-webhook.ts:139-141, 167-178`; `integration-settings-repository.ts:248-261` writes an absolute value.
- **Risk**: with `INT001_OUTBOUND_CONCURRENCY` 2–4 and several deliveries to one integration failing concurrently, two attempts read streak N and both write N+1, so the breaker trips later than 10; a success racing a failure can reset a streak that should have tripped. Not a security issue, but the spec's "10 consecutive failures" is approximate under load.
- **Fix**: make the write relative in SQL (`outbound_failure_streak = outbound_failure_streak + 1 RETURNING …` via a small RPC, or `GREATEST(0, …)`) and decide the trip from the returned value.

## ✅ Strengths

- The consent invariant is enforced at three independent layers (pure decision, `status='pending'`-conditioned RPC, BEFORE INSERT trigger) and the trigger is correctly scoped to `source='partner_api'` so the member's own re-opt-in paths are untouched. Tests cover STOP-then-create and STOP-then-delete-then-create.
- The inbound guard is structurally unable to touch Postgres (`integration-inbound-guard.ts:19-22`), so "Redis down → 503, zero DB writes" holds by construction; `enqueueMemberCreate` orders every Redis call before the single Postgres write.
- Content-addressed job ids include `consent_level`, so OD-2's "existing → apply consent upgrade" cannot be swallowed by idempotency; the Postgres PK is the correctness backstop behind the Redis fast path.
- `IntegrationSettings.fromProps` carries the `outbound_enabled ⇒ url + pii ack + secret` invariant and the PATCH use case validates the merged state through it (`update-integration-settings.ts:296-308`), so the client-side "Enabled" gate is not the only enforcement.
- The fan-out trigger (`071:93-111`) requires `outbound_enabled AND outbound_url AND outbound_pii_ack_at` at the DB level, so a mis-wired settings write cannot leak PII to an unacknowledged destination.
- `retryDelivery`'s missing tenant scoping is compensated exactly where the WI-8 handoff said it would be (`retry/route.ts:32-35` checks both `integrationId` and `restaurantId` after a scoped `getIntegration`).
- Legacy-path parity after WI-7: `register-member.ts`, `register-member-web.ts`, `import-contacts-batch-row-member.ts` each keep their post-create behaviour (returning-member flow, web coupon, CSV merge/reject rule) and the two pre-existing test edits changed only mock plumbing (table-discriminated `from` mocks), no assertion values.

## Open Questions
