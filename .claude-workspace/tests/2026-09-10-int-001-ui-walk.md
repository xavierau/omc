## Root cause (diagnosed, not just observed)

`GET /api/dashboard/pos-integrations/[id]/settings` throws in
`integration-settings-repository.ts`'s `findIntegrationSettingsById`:
`Could not find the table 'public.integration_settings' in the schema cache`. Same for
`/activity` (`integration_member_jobs`) and, by direct probe, `/deliveries` would hit
`integration_deliveries` too.

Diagnosis performed (not assumed): a small one-off script (run from this worktree, then deleted —
never committed) queried each new INT-001 table via `supabase-js` with the service-role key
(`.select('*',{count:'exact',head:true}).limit(0)`) and got **no error** for all six new tables —
they exist in Postgres. But a plain `curl` GET straight against
`${SUPABASE_URL}/rest/v1/integration_settings` (both anon and service-role key, 5 consecutive
retries over several minutes) consistently 404s with `PGRST205`, while the same probe against
`pos_integrations` (pre-existing) returns 200. This is PostgREST's schema cache being stale for
tables added after it last loaded — the migrations exist and ran, but the REST layer the app
actually calls hasn't picked them up. No DB password and no Supabase Management API token are
available in this worktree to force a reload (`NOTIFY pgrst, 'reload schema'` or the dashboard's
"Reload schema cache" button) — this needs a human with that access, or a `supabase db push` cycle
against this project that triggers Supabase's own auto-reload.

## Anomalies (confirmed defects, independent of the environment cause)

1. **Silent card failure (Settings tab).** `src/app/dashboard/integrations/[id]/page.tsx` gates the
   Welcome template / Consent attestation / Outbound webhook cards on `isAdmin && settings`, with no
   `else` branch for "isAdmin but the settings fetch failed." When it fails, all three cards and the
   paused banner simply don't render — no error text, no retry button, nothing. This is a real
   defect independent of the DEV-only root cause: any settings-fetch failure in prod (a transient DB
   blip, etc.) produces the identical silent void for a real tenant admin. The same component
   already has a correct `error` branch two lines above (for the base integration fetch) — the
   settings fetch needs the same treatment.
2. **Misleading copy (Deliveries tab).** The same gate on the Deliveries tab falls through to
   `deliveries-admin-only`, i.e. "只有租戶管理員可以查看及管理這些設定。" ("Only tenant admins can view and
   manage these settings") — shown to a user who **is** the tenant admin. Worse than silent: this
   actively tells an authorized user they lack permission when the real cause is unrelated. Should
   distinguish "not admin" from "admin, but couldn't load."
3. Console: one repeated `[error] Failed to load resource: 500` per broken endpoint (settings ×2,
   activity ×2) — all attributable to the root cause above, nothing unexpected beyond it.
4. No unexpected console errors or failed requests on any of the flows that DID complete (create,
   rotate, nav).
